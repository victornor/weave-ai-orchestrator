# Weave AI HTTP API (v1)

Base: `/api`. Workspace-scoped routes: `/api/w/:ws/...` where `:ws` is the workspace id (slug). JSON in/out. Errors: `{ error: { code, message, details?, retryable } }` with the status from `OcError.status(code)`.

Auth: `Authorization: Bearer <token>` (CLI/presenter) or the `ac_session` httpOnly cookie (web). Loopback listener accepts run tokens (`Bearer rt_...`) for `/mcp/runs/:runId` and `/api/w/:ws/agent/*` only.

## Daemon-level
- `GET /api/health` → `{ ok, version, pid, release: { version, path, sha }, workspaces: [{id, name, status}], operatorConfigured, tlsMode, publicUrl, transcription: { configured, backend: 'chrome'|'voxtype' }, host: { platform, hostname, tools: { git|gh|openspec|wt: { available, version, path, need, purpose } } } }` — `version` (and `release.version`) is the short git sha of the release this process is executing, or `unknown` when it cannot be determined — never a hardcoded package version. `pid` is this process's own pid (VS-316), so an upgrade's restart runner can confirm the process that answers is the one that replaced the one being restarted, not merely a daemon that happens to answer on the target release. `transcription.backend` is the web composer's dictation backend (`chrome` default); `configured` is true only when host transcription will actually run (Voxtype selected and installed, or a yaml `command` provider). `host.tools` is the daemon host's tool detection (cached 60 s), which is what a remote `weave doctor` reports. `release` is the release directory **this process is executing** (never what `current` points at, which an upgrade swings before the restart); `release.sha` is `null` when it could not be determined.
- `POST /api/auth/setup` `{ username, password }` (only when no operator) · `POST /api/auth/login` `{ username, password, totp?, deviceName?, kind }` → `{ token, sessionId, expiresAt }` or `{ totpRequired: true }` (401 `auth_totp_required`) · `POST /api/auth/logout` · `GET /api/auth/me` → `{ operator, session, totpEnabled }`
- `GET /api/auth/sessions` · `DELETE /api/auth/sessions/:id` · `DELETE /api/auth/sessions` (all others)
- `POST /api/auth/totp/setup` → `{ secret, otpauthUrl, recoveryCodes }` · `POST /api/auth/totp/enable` `{ code }` · `POST /api/auth/totp/disable` `{ password }` · `POST /api/auth/password` `{ current, next }`
- `GET /api/workspaces` → `[{ id, internalId, name, ticketPrefix, root, projects, needsYou }]` — `id` is the slug, `internalId` is the workspace row's ULID (what a run token's claim and records minted from it carry, VS-403); `needsYou` is that workspace's count of open decisions owned by the human, so the web app's sidebar can badge every workspace from one request instead of one per workspace · `POST /api/workspaces` `{ path }` (register existing) · `POST /api/workspaces/init` `{ path, id, name, ticketPrefix }` · `POST /api/workspaces/import` `{ path, target }` (stage an export into `target`, register it, import its tickets as `backlog`) → `{ id, path, created, roles, knowledgeFiles, tickets, skipped }`
- `GET /api/incidents[?reporter=weaver|worker][&limit=]` → `{ items: [Incident], total }` — system incidents agents filed through `weave_incident` (VS-174), newest first, resolved or not (VS-271 adds no `status` filtering to this route — that default lives only in the `weave_incident_list` MCP tool). `Incident` is `{ id, reporterKind: 'weaver'|'worker', title, whatFailed, tryingToDo, evidence, workspaceId, projectId, ticketId, agentId, runId, roleId, createdAt, resolvedAt, resolvedByAgentId, resolvedByWorkspaceId, resolution, resolutionTicketId }` — the last five are null until `weave_incident_resolve` is called (`resolvedByWorkspaceId` is the resolving run's workspace, distinct from `workspaceId`, where it was filed — VS-499). `limit` default 100, max 200. Run tokens cannot list. · `GET /api/incidents/:id` → one `Incident` (`not_found` if unknown).
- `GET /api/runtimes` → `[{ id, displayName, detection, capabilities, models }]` · `GET /api/runtimes/:id/models` → `RuntimeModel[]`. Each model may carry `efforts?: string[]`: a non-empty list is the thinking levels that model accepts, `[]` means it is known to take none, and omitting `efforts` means unknown (free text). Values come from the same discovery path as `source` (`detected` | `static`).
- `GET /api/daemon/update[?refresh=1]` → `{ configured, running: { version, path, sha }, source, ref, targetSha, updateAvailable, checkedAt, error }` — resolves `upgrade.source` at `upgrade.ref` with `git ls-remote` (no clone) and compares it with the running release. `configured: false` when no `upgrade.source` is set: not an update and not an error. Cached for `upgrade.updateCheckIntervalSec` (default 900); `?refresh=1` resolves again. A check that fails sets `error` and leaves `updateAvailable` false.
- `GET /api/daemon/upgrade` → `{ upgrade, waitingFor: [{ workspace, running, runIds }] }` — the latest upgrade record, and (only while it is still cancellable) the work holding it. `upgrade.state` is one of `queued|waiting|building|switching|restarting|completed|failed|cancelled`; `upgrade.log` is a bounded tail (200 lines) of the build output; `upgrade.reason` is one of `build_failed|backup_failed|switch_failed|restart_unverified|restart_failed|abandoned`; `upgrade.drainedRuns`/`upgrade.interruptedRuns` are how many runs were still executing when dispatch was held, and how many of those were still executing when the bound to wait for them expired (the upgrade proceeds either way — see `docs/OPERATIONS.md`).
- `POST /api/daemon/upgrade` `{ ref?, source?, test? }` → 202 with the record — queue a deferred upgrade: dispatch is held at once, in-flight turns finish, and only then does the daemon build, back up, switch `current` and hand the restart to a detached runner. 409 `conflict` while one is already in flight, 400 `validation` when no source is configured.
- `POST /api/daemon/upgrade/cancel` → the cancelled record — only from `queued` or `waiting` (409 `conflict` from `building` on, 404 when nothing is in flight). Resumes dispatch on every workspace that is not itself paused.
- `POST /api/daemon/drain` `{ timeoutSec? }` → `{ drained, running: [{workspace, runId}], workspaces }` (stop dispatching everywhere, wait for in-flight turns up to the timeout; used by `weave daemon upgrade` before a restart) · `POST /api/daemon/undrain` → `{ resumed }` (start dispatching again on workspaces that are not paused)
- `POST /api/transcribe` (multipart audio, 16 kHz mono WAV when using Voxtype) → `{ text }` or 501 when no host backend will run
- `GET /api/daemon/transcription` → `{ backend: 'chrome'|'voxtype', model, voxtype: { installed, models: [{ id, engine, installed }], error? } }` — daemon dictation setting plus the host Voxtype probe. Session auth.
- `PUT /api/daemon/transcription` `{ backend, model? }` → same shape as GET. Persists to `daemon.yaml` and takes effect without a restart. `voxtype` backend requires the binary; `model` must be an installed id. 400 `validation` otherwise.
- `GET /api/daemon/models` → `{ weaver: ModelSetting | null, workers: ModelSetting | null, workerOptions: WorkerModelOption[] | null }` — optional overlays (VS-185, ADR 0013). Null (and an empty catalog) means no overlay for that control. A worker option may have `runtime: null` (unconfigured; VS-236, ADR 0019). Session auth.
- `PUT /api/daemon/models` `{ weaver?, workers?, workerOptions? }` — omitted key leaves that overlay; `null` or `workerOptions: []` clears; a value sets. Persists to `daemon.yaml` and takes effect without a restart. Duplicate option ids are `validation` 400. `runtime: null` on an option is stored as unconfigured, not coerced to `claude`. Naming that option on a ticket is `model_unconfigured` 400. The body also accepts the legacy key name `conductor` (VS-263); the response is always `weaver`, but `daemon.yaml` on disk keeps the legacy spelling for now (rollback safety) — see `config-key-compatibility` in the project knowledge base.
- `GET /api/daemon/host-tools` → `{ paths: string[], tools: [{ id, available, version, path, need, purpose }] }` — the daemon host's git/gh/openspec/wt detection plus the configured `hostToolPaths` (VS-318). Session auth; operator-only like the rest of `/api/daemon`.
- `PUT /api/daemon/host-tools` `{ paths: string[] }` → the same shape, re-probed — persists `hostToolPaths` to `daemon.yaml`, re-resolves the daemon's `PATH` live (no restart) and clears the 60 s detection cache. `paths` must be absolute directories; a relative entry is `validation` 400 (a relative entry would let a clone's own `node_modules/.bin` reach the daemon). An unusual layout only, since the daemon already resolves the user's login-shell `PATH`.
- `GET /api/daemon/scratch` → `{ count, bytes, workspaces: [{ id, name, count, bytes, trees: [{ path, bytes, legacy }] }] }` — the scratch landing worktrees the daemon currently holds, per workspace and in total (VS-383). Under `<workspace state>/scratch/<project>/`; `legacy` marks a pre-VS-383 `/tmp/ac-land-*` tree. Read-only; the supervisor sweeps stale ones at boot and on a period, and `weave doctor` reports the figure. Session auth; operator-only like the rest of `/api/daemon`.
- `GET /llms/api.txt` (agent-readable summary) · `GET /api/openapi.json`

## Workspace
- `GET /api/events?after=<base64url cursor map>` SSE stream for all loaded workspaces (`event: <type>`, `id: <base64url workspace cursor map>`, `data: WorkspaceEvent`); one connection per document, heartbeat comment every 15 s; invalid or oversized cursors start at the current tail
- `GET /api/w/:ws` → workspace + config summary · `PATCH /api/w/:ws/config` (partial `workspace.yaml`; a `defaults.yolo` key is refused — YOLO is per project, set through `PATCH /api/w/:ws/projects/:id` as `policies.yolo`, VS-382) · `POST /api/w/:ws/pause` · `POST /api/w/:ws/resume`
- `GET /api/w/:ws/events?after=<seq>` SSE stream (`event: <type>`, `id: <seq>`, `data: WorkspaceEvent`); heartbeat comment every 15 s
- `POST /api/w/:ws/export` `{ out? }` → `{ path, workspace, roles, knowledgeFiles, tickets }` (portable package: `workspace.yaml`, `roles/**`, `knowledge/**`, `tickets/*.md`; no db, no runs, no secrets)
- `GET /api/w/:ws/briefing`

### Models
`GET /models` → `{ weaver: { runtime, model, effort? }, workers: { runtime, model, effort? }, workerOptions: [{ id, description, runtime, model, effort? }], source: { weaver, workers, workerOptions } }` — effective values after a daemon overlay (VS-185, ADR 0013), plus, for each control, where the effective value came from (VS-356): `'workspace'` when this workspace stores its own value, `'daemon'` when it does not but a filled daemon overlay governs, `'default'` otherwise. The weaver runs on the first; a worker runs on the option its ticket names, or on `workers` when it names none. An option with `runtime: null` is unconfigured (VS-236): create/assign/launch with that id is `model_unconfigured` 400, not a silent `claude`. Roles, projects and agent rows still cannot choose a runtime or a model.
`PUT /models` changes only the controls it names, and each control is independent (VS-356): a setting overrides, `null` clears it back to inherit, and omitting the key keeps the stored value. For `workerOptions`, an array (including `[]`) replaces the catalog and `null`/`[]` clears it to inherit the daemon catalog; omitting it keeps the stored one. An old body carrying both `weaver` and `workers` still writes both. The body also accepts the legacy key name `conductor` in place of `weaver` (VS-263); the response is always `weaver` and `workspace.yaml` on disk keeps the legacy spelling for now (rollback safety) — see `config-key-compatibility` in the project knowledge base. The response is the same sourced view as `GET`. `model: null` means the runtime chooses; on a worker option, `runtime: null` means the adapter is not chosen yet. `effort` is optional and is the only place it can be set. An empty `runtime` on weaver/workers is a `validation` 400. Changing a runtime retires that agent's session, so its next turn starts a new one. Duplicate option ids and more than 16 options are a `validation` 400.

### Channels
`GET /channels/telegram/token` → `{ configured, source: 'secret' | 'env' | null, botUsername: string | null }` — never a token value. `source` is which precedence branch is in effect (VS-125): `secret` when the workspace secret store holds it (set from Settings), `env` when it comes from an `${ENV_VAR}` reference already resolved in `workspace.yaml`, `null` when nothing resolves.
`POST /channels/telegram/token` `{ token }` → `{ ok: true, botUsername }` — calls Telegram's `getMe` before accepting the token; on success registers it in the workspace secret store (never `workspace.yaml`, never the database) and restarts the Telegram channel with it, no daemon restart. On failure (`validation` 400, Telegram's own message) nothing is written and any previously-working token is untouched.
`DELETE /channels/telegram/token` → `{ ok: true }` — clears the stored token and stops the Telegram channel if it was running from it.
`GET /channels/telegram/pending` → `{ pending: Array<{ externalUserId, username: string | null, displayName: string | null, firstSeenAt, lastSeenAt, attemptCount }> }` (VS-135) — everyone who has messaged the bot while not on the allowlist, identity only; never the message text. Capped at 50 entries per workspace and expired 7 days after their last attempt.
`POST /channels/telegram/pending/:externalUserId/approve` → `{ allowedUserIds: number[] }` — adds the id to the allowlist, clears its pending row, and restarts the Telegram channel so their next message is accepted, no daemon restart. Approving an id already on the allowlist is a no-op that still returns the current list.
`POST /channels/telegram/allow-all/disable` → `{ ok: true }` — turns off a workspace's `allowAll` grandfathering (VS-125) in favour of the allowlist, and restarts the channel. There is no route that turns `allowAll` on; it can only ever be true for a workspace that already had it set before VS-135.

### Scheduled tasks (routines)
Human-facing name is **Scheduled tasks**; HTTP/CLI/MCP identifiers stay `routines` / `routine` (VS-220). Recurring alarms that wake the weaver with an instruction via the existing wake queue. Default action is `report` (look, then reply); `file_work` is the only filing licence. Cap `maxTicketsPerFire` ≤ 8 (defaults 0 / 3).

`GET /routines` → `{ items: [Routine] }` · `POST /routines` `{ name, trigger, instruction, action?, maxTicketsPerFire?, projectId? }` → **201** `Routine`. `trigger` is `{ kind: 'schedule', timezone?, daily: { hour, minute } }` or `{ kind: 'schedule', timezone?, everyMinutes }` (`everyMinutes` ≥ 15). Webhook and cron are `validation` 400. Timezone defaults to the host IANA zone.
`GET /routines/:id` → `Routine` · `PATCH /routines/:id` `{ name?, trigger?, instruction?, action?, maxTicketsPerFire?, projectId?, status?: 'active'|'paused' }` — resume (`status: 'active'`) arms the next future slot · `DELETE /routines/:id` → `{ ok: true }`
`GET /routines/:id/usage?window=24h|7d` → `{ tokensIn, tokensOut, tokensCached, runs, costCents, costReportedCents, window }` — weaver-turn spend for that routine's fires plus originated-ticket spend. Session auth; run tokens cannot call these routes.
`GET /routines/:id/fires` → `{ items: [RoutineFire] }` — kept (non-skipped) fires newest first, each `{ wakeId, runId, firedAt, status, summary, sharedTurn }`. `runId` is `COALESCE(wake.run_id, parent.run_id)`. `sharedTurn` is true when that run also claimed work that was not this routine. `GET /routines` items include lifetime `fireCount`. Session auth.

### Artifacts
`GET /artifacts/kit.css` → the AC Artifact Kit's CSS (`ARTIFACT_KIT_CSS`), verbatim, `text/css`. Session-authenticated; used by the ticket Artifact tab's download action to inline the kit into a downloaded artifact that didn't already embed it (VS-269). Per-ticket artifact routes are under Tickets (`GET /tickets/:id/artifacts/:key/raw`).

Weaver artifacts (VS-297, workspace-scoped, no ticket involved): `GET /artifacts` → `[{ key, title, kind, revision, updatedAt }]`, most-recently-updated first, no `body` — the workspace-level sibling of `GET /knowledge/artifacts` above, for artifacts a weaver publishes with `weave_artifact_put` rather than any ticket's tool. `GET /artifacts/:key/revisions` → `[{ revision, authorKind, createdAt }]`, oldest first — the workspace-scoped sibling of `GET /tickets/:id/documents/:key/revisions`. `GET /artifacts/:key/raw?revision=` → that artifact's stored HTML, verbatim, with the identical sandboxing `Content-Security-Policy`, `text/html` content type and `X-Content-Type-Options: nosniff` as `GET /tickets/:id/artifacts/:key/raw` (the CSP string is one shared constant both routes import, so they cannot drift apart) — session-authenticated only, never reachable by a run token. The web app's `/w/:ws/artifacts/:key` page is what renders this through `ArtifactViewer`, and is the URL `weave_artifact_put` itself returns.

### Projects
`GET /projects` · `POST /projects` `{ url, id?, name?, defaultBranch?, landingBranch?, maxWorkers?, setupCommand?, policies? }` (strict: a project carries no runtime or model, and no top-level `autoMerge`; `policies.autoMergeDefault` (VS-153) is the project's auto-merge default, not the ticket-level flag; `landingBranch` (VS-119) is the branch its tickets' work actually lands on when it differs from `defaultBranch` — Fernwood's is `edge`, promoted to `main` separately by a human — and falls back to `defaultBranch` when unset) → **202** `{ project, jobId }` · `GET /projects/:id` · `PATCH /projects/:id` · `DELETE /projects/:id` · `POST /projects/:id/fetch`

`PATCH /projects/:id` also sets, changes or clears a project's display **name** (VS-330): `name` is trimmed and stored; `name: ''` (or whitespace only) clears it, and an omitted `name` leaves the current value alone. `name` is what a person reads and falls back to `slug` when unset; `slug`/`id` stays the stable identifier for the clone path, `workspace.yaml`, routing and knowledge paths.
`PATCH /projects/:id` also declares, changes or clears a project's landing branch after creation (VS-122): a non-empty `landingBranch` is rejected with a `validation` 400 naming the branch when it is not found on the project's remote as of its last fetch; `landingBranch: ''` clears it back to "use `defaultBranch`". Every check that resolves a project's effective landing branch reads the project row fresh, so a change takes effect on the next ticket action — no daemon restart.
`PATCH /projects/:id` also changes the knowledge-repo opt-in (VS-358, VS-359): on a project that already has a clone, turning `knowledgeRepo.enabled` on or off starts a reviewed migration — one pull request moving the project's `knowledge/projects/<id>/**` tree into `.weave/knowledge/` or removing it — and the flag itself changes only when that pull request resolves. The pending switch is reported on `Project.knowledgeSwitch` (`{ direction: 'on' | 'off', branch, prUrl, startedAt } | null`); a second knowledge-repo patch while one is pending is a `conflict`.
`GET /projects/repo-info?url=<git url>` (VS-359) → `{ private: boolean } | null` — whether the repository a not-yet-created project would use is public, read from the forge. `null` whenever the forge cannot say, never an error.
`GET /projects/:id/repo-info` (VS-359) → `{ private: boolean } | null` — the same for an existing project's repository. The web app uses it to warn before committing a project's knowledge to a public repository; the warning is advisory and never blocks the change.
`POST /projects/:id/retry` → **202** `{ project, jobId }` — re-run a failed add against whatever is already on disk; `conflict` unless the project's status is `error` and no job for it is running.

`GET /projects/:id/sync` → `{ syncState: 'in_sync' | 'behind' | 'diverged', behindBy: number | null }` (VS-131) — classifies the primary clone against `origin/<landingBranch>` by fetching and comparing locally; never checks out or merges, so opening this can't itself change the clone. `behindBy` is the commit count only when `behind`, else `null`. `diverged` means the clone holds a commit the remote's current tip no longer recognises (a force-push or rebase upstream) — resolving it is a human's job outside Weave AI, never automatic. `POST /projects/:id/fetch` (above) is the one action that resolves `behind`: the same fetch, followed by `checkout` + `merge --ff-only`; both routes persist `Project.syncState` and emit `project.updated`.

**BREAKING (VS-37):** `POST /projects` used to answer `201` with the finished project after the clone, the OpenSpec adoption and the knowledge seed — minutes of work. It now answers `202` as soon as the row exists, with the project in its `cloning` status and the id of the job doing the rest. Follow `GET /jobs/:id/stream` for progress, or poll `GET /projects/:id` until its status leaves `cloning`.
`GET /projects/:id/merge-queue` → `{ projectId, concurrency, active: [MergeQueueEntry], waiting: [MergeQueueEntry], recent: [MergeQueueOutcome] }` — the per-project merge queue (PLAN §11.4). `MergeQueueEntry` is `{ ticketId, identifier, title, projectId, position, queuedAt, startedAt, workerId, priority, ahead, ciState, ciStateAt }`; `position` is 1-based within `waiting` (ordered by priority, then join time, with bypassed tickets first) and `null` for an `active` entry; `priority` is the ticket's priority and `ahead` is true when a waiting ticket is ordered ahead of one that joined earlier with a lower priority (VS-390); for an `active` entry, `ciState` is the pull request's observed check rollup (`pending` · `success` · `failure` · `none`, or `null` before the first observation) and `ciStateAt` is when that state was first seen, so a client can show whether the merge is waiting on CI or on its worker (VS-391). `concurrency` is the project's `mergeConcurrency` policy (default 1). `MergeQueueOutcome` is `{ ticketId, identifier, title, outcome, at, mergeCommit }` — the last five tickets that left this project's queue, most recent first, `outcome` one of `landed` · `failed` (the merge could not complete) · `withdrawn` (left the queue without either); derived from the activity log, so nothing has to be recorded at merge time.

`GET /projects/:id/pull-requests` → `{ projectId, available, reason, message, stale, capturedAt, windowDays, open: [ProjectPullRequest], recent: [ProjectPullRequest] }` — the project's pull requests, read through the forge and joined on the daemon (VS-97). `open` is every open pull request, `recent` every one merged or closed within `windowDays` (30), each most recently updated first. A `ProjectPullRequest` is the forge's `{ number, title, url, author, state, isDraft, headRefName, baseRefName, createdAt, updatedAt, mergedAt, closedAt, additions, deletions, changedFiles, checks, reviewDecision, mergeCommit }` plus `ticket` (`{ id, identifier, title, status, hasPlan }` or `null` — matched by the ticket's `pull_request` work product, else by the `ac/<identifier>-` branch), `changeName` (the OpenSpec change its ticket implements, or `null`) and `queue` (`{ state: 'landing' | 'waiting', position }` or `null`). `checks` is `pending` · `success` · `failure` · `none`.

Always `200`, never an error status, for a project that has no forge: `available: false` with `reason` one of `no_forge` · `not_authenticated` · `no_clone` · `unsupported` · `unreachable`, `message` set only for `unreachable`. Forge answers are cached per project for three minutes and dropped on that project's `ticket.work_product`, `ticket.merged` and `ticket.status`; `stale: true` means a refresh failed and this is the previous answer. Read-only: there is no write, no merge and no review on this surface.

`GET /projects/:id/pull-requests/:number` → `{ projectId, available, reason, message, stale, pullRequest }` — one pull request as `ProjectPullRequest` plus `body`, `files: [{ path, additions, deletions }]`, `checkRuns: [{ name, state, url }]` and `headSha` (the pull request's current head commit, or `null` when the forge reports none; VS-452). `pullRequest` is `null` with `available: true` when the forge has no such number; a non-integer or non-positive `:number` is a `validation` error.

`GET /projects/:id/pull-requests/:number/diff` → `{ projectId, number, available, reason, message, stale, files: [DiffFileSummary] }` — a pull request's changed-file manifest, from its diff rather than the forge's own file list, so it carries `status` too (VS-107). A `DiffFileSummary` is `{ path, previousPath, status, additions, deletions, binary, tooLarge }`, `status` one of `added` · `modified` · `deleted` · `renamed`. Never carries a hunk: this is the cheap list a file tree renders from. `reason` adds `no_local_branch` to the set `pull-requests` already reports — neither the forge nor the daemon's own clone could produce this pull request's diff.

`GET /projects/:id/pull-requests/:number/diff/file?path=` → `{ projectId, number, available, reason, message, file }` — one file's hunks, sliced from the same diff `diff` already read and cached. `file` is a `DiffFileSummary` plus `hunks: [{ oldStart, oldLines, newStart, newLines, header, lines: [{ kind, oldLine, newLine, text }] }]`, `kind` one of `context` · `add` · `remove`; `hunks` is `[]` when `binary` or `tooLarge`. `file` is `null` with `available: true` when the diff has no such path. `path` is required.

`GET /projects/:id/pull-requests/:number/diff/file/context?path=&start=&end=` → `{ projectId, number, available, reason, lines: [string] }` — content for a collapsed region's expand control, read from the pull request's base revision in the daemon's own clone (base and head agree wherever a diff omitted the lines) — see design.md of `vs-107-the-pr-explorer-shows-the-diff-itself-fi` for why this is always answerable from the base side even when the head branch is not local. `lines` is `[]` when the file has no content there — an added file, or a range past its end. `start`/`end` (1-based, inclusive) must be positive integers.

Diff content comes from `gh pr diff` when the forge can supply it, and otherwise from `git diff` in the daemon's own clone when the pull request's head branch is there — every worker branch always is. The same cache and event-driven invalidation as the rest of `pull-requests`. Read-only throughout: no edit, comment, approve or merge surface here either.

`GET /projects/:id/history` (`cursor?`, `limit?`, default 30, max 200) → `{ refs: [ProjectRef], commits: [HistoryCommit], cursor: string | null }` — the project's commit graph (VS-96): the default branch plus every branch a live worktree or an unfinished ticket holds, read from the project's own clone (never fetched, never mutated — the same clone every worker worktree branches off). A `ProjectRef` is `{ name, sha, isDefault, ticketId, ticketIdentifier, agentId, agentName }`; a recorded branch the repository no longer has is left out. A `HistoryCommit` is `{ sha, parents: [sha], author, authoredAt, subject, refs: [refName] }`, newest first. `cursor` pins the ref tips the first page resolved, so a branch moving mid-page cannot duplicate or drop a commit; `null` when there is no more.

`GET /projects/:id/commits/:sha` → `CommitDetail`: `{ sha, parents: [sha], author, email, authoredAt, committedAt, message, files: [CommitFile], truncatedFiles, forgeUrl }`. A `CommitFile` is `{ path, previousPath, status: 'added'|'modified'|'deleted'|'renamed', additions, deletions }` — a merge's files are reported against its first parent. `forgeUrl` is `null` unless the project's remote is a recognised forge host (github.com, gitlab.com, codeberg.org). `:sha` must be a plain abbreviated or full object name (`validation` error otherwise); an unknown commit is `not_found`.

**Roadmap (VS-397).** A project's roadmap is its future ideas that are not tickets. A `RoadmapItem` is `{ id, workspaceId, projectId, blockId, title, notes, description, kind, priority, roleId, position, status: 'idea'|'planned'|'dropped', ticketId, createdByKind, createdById, createdAt, updatedAt }` — `notes` is markdown (empty when unset), `ticketId` is the ticket the idea became (null until work starts), and `position` is a dense, zero-based order within the project. `:id` may be a project slug or id, as elsewhere under `/projects`.

Since VS-478 an item may be a **pending ticket** in a **block**: `blockId` is the block it belongs to (null = a loose item), `description` is the markdown the created ticket will carry (acceptance criteria included), `kind` is a ticket kind, `priority` a ticket priority, and `roleId` the target role. `POST /projects/:id/roadmap` `{ title, notes?, status?, ticketId? }` creates a loose item; `PATCH /projects/:id/roadmap/:itemId` `{ title?, notes?, status?, position?, ticketId?, description?, kind?, priority?, roleId?, blockId? }` writes any of an item's fields (a `position` renumbers the project's items; `blockId` moves it, null returning it to loose); `DELETE /projects/:id/roadmap/:itemId` → `{ ok: true }`.

`GET /projects/:id/roadmap` → `{ items: [RoadmapItem] }`, ascending by `position`, all of the project's items whether loose or in a block. `POST /projects/:id/roadmap` is **201**.

**Roadmap blocks (VS-478).** A `RoadmapBlock` is `{ id, workspaceId, projectId, title, notes, position, status: 'open'|'started'|'dropped', reportedStatus: 'open'|'started'|'done'|'dropped', startedAt, createdByKind, createdById, createdAt, updatedAt, items: [RoadmapItem] }` — `status` is what is stored, while `reportedStatus` additionally reports `done` for a started block whose every item is linked to a terminal ticket (`done` or `cancelled`); `done` is never stored or settable. `GET /projects/:id/roadmap/blocks` → `{ blocks: [RoadmapBlock] }`, each block in the project's block order with its `items` in the project's item order. `POST /projects/:id/roadmap/blocks` `{ title, notes? }` → **201** `RoadmapBlock`, appended. `PATCH /projects/:id/roadmap/blocks/:blockId` `{ title?, notes?, status?, position? }` → the updated `RoadmapBlock`; `position` renumbers the project's blocks. There is no delete route: a block is set aside with `status: 'dropped'`, and starting a block is a weaver-tool action, not a route.

An unknown project, an `:itemId` or `:blockId` that does not belong to `:id`, an unknown role and a `ticketId` from another project are all `not_found` for the item routes; an empty title, an unknown status, kind or priority is `validation`. Session auth; the weaver reaches the writes through the `weave_roadmap_*` tools rather than these routes.

**Draft plans (VS-398, VS-477).** A project's draft plan is a captain-authored planning session with a read-only `planner` agent, shown in the V2 chat's Plan modal as one tab per `drafting` plan. A `Plan` is `{ id, workspaceId, projectId, threadId, agentId, title, titleSource: 'auto'|'human', status: 'drafting'|'submitted'|'discarded', createdByKind, createdById, submittedAt, discardedAt, createdAt, updatedAt }`. A `PlanSummary` (a tab) is `{ id, projectId, title, titleSource, status, draftCount, createdAt, updatedAt }`.
`GET /projects/:id/plans?status=drafting` → `{ plans: [PlanSummary] }`, newest first; `status=drafting` is the only supported filter (anything else is `validation`). `POST /projects/:id/plans` `{ title? }` → **201** `{ plan, agent: { id, status, runtimeId } }`, a fresh drafting plan with its own thread and planner, alongside any the project already has. `POST /projects/:id/plans/start` `{ title? }` → `{ plan, agent }`, resuming the most recently created drafting plan or creating one. `POST /projects/:id/plans/:planId/activate` → `{ plan, agent }`, focusing a tab: ensures its planner is live and retires the project's other planners that have gone idle. `PATCH /projects/:id/plans/:planId` `{ title }` → the updated `Plan`, captain's rename (`titleSource: 'human'`); an auto title never overwrites it. `GET /projects/:id/plans/:planId` → `{ plan, drafts }` and the draft `PATCH`/`DELETE` routes are unchanged from VS-398 (`drafts` each carry `blockedBy`; VS-517: a draft with a `createdTicketId` also carries `ticketStatus`, and once that ticket is terminal, `report`). `POST /projects/:id/plans/:planId/submit` and `.../discard` are unchanged (submit wakes the weaver with `plan_submitted`; discard leaves the plan and thread as history and creates no tickets). `POST /projects/:id/plans/:planId/drafts/:draftId/dispatch` (VS-517) → the updated `PlanDraft`: captain runs a `scout` draft as a real ticket right now, before the plan is submitted — refused (`validation`) for any other `kind`, a draft already linked to a ticket, or a plan that is not `drafting`. The planner-only `weave_plan_draft_dispatch` tool does the same thing, identically restricted, for the planning agent's own plan — both call the same core `dispatchDraft`. The dispatched ticket's report reaches the planner (a `scout_report` wake), never the weaver, for as long as the plan stays `drafting`; once it is not, the ticket finishes as an ordinary standalone ticket. `:planId` that belongs to another project is `not_found`. Session auth; the planner names its own plan through the planner-only `weave_plan_set_title` tool (≤ 6 words, refused once `titleSource` is `human`).

### Jobs
A job is one long-running workspace-setup operation, watchable while it runs (PLAN §5; `openspec/specs/workspace-setup/setup-jobs`). Kinds: `project_add`.
`GET /jobs?kind=&entity=&limit=` → `[Job]` newest first — `entity` is the id of the thing the job acts on, which is how a client that lost its state finds the job still running for a project · `GET /jobs/:id` → `Job`
`Job` is `{ id, workspaceId, kind, entityType, entityId, state: running|done|failed, steps: [JobStep], log: [JobLogLine], logSeq, requestedBy, startedAt, finishedAt, failedStep, message }`. `JobStep` is `{ id, label, state: pending|running|done|skipped|failed, startedAt, endedAt }` — the whole ordered list exists from the moment the job is created. `JobLogLine` is `{ seq, step, stream: stdout|stderr|daemon, text }`; only the last 200 lines are retained on the record.
`GET /jobs/:id/stream` SSE — replays the job's steps and retained lines, then tails it. Frames are `event: job.step | job.log | job.finished`, `id: <seq>`, `data: JobStreamItem`; resume with `?after=<seq>` or `Last-Event-ID`. The stream closes once the job is terminal. A client attaching more than 200 lines late gets the tail, not the lines it missed.
The workspace outbox carries `job.started` and `job.finished` only — never a line.

### Decisions
`GET /decisions?status=&owner=` · `GET /decisions/:id` · `POST /decisions/:id/answer` `{ key?, text?, remember?, inputs? }` · `POST /decisions/:id/withdraw`

A decision carries `projectId` (the ticket's project, else the one the asker named, else `null` — surfaces label that as `Workspace`) and `inputs`: values the card collects as well as, or instead of, an option. `inputs` on the answer is a map keyed by input key, whose value is a string or, for a `multiselect`, the chosen keys; it is recorded on the decision as `answerInputs` and delivered to the asker in its wake. ### Changelog
`GET /changelog?project=&before=&limit=` → `{ entries: [{ id, at, kind, actor: { kind, id, label }, projectId, ticketId, ticketIdentifier, summary, link }], nextCursor }` — the human-facing record of what happened (PLAN §13.6), newest first. `kind` is one of `filed | plan_approved | pr_opened | landed | cancelled | hired | upgraded`; `link` is `{ kind: 'ticket' | 'url', target }` or null. Without `project` the workspace changelog is served: every project's entries plus the ones belonging to none. `before` is the `nextCursor` of the previous page; `nextCursor` is null when nothing older remains. `limit` defaults to 50 and is capped at 200.

`GET /changelog/heatmap?project=&from=&to=&tz=` → `{ days: [{ date, landed, total, byKind }], timezone, measure: { kind, label, definition } }` — activity per day, dense: every day in the range is present, a quiet day reporting zero. `from`/`to` are `YYYY-MM-DD` and default to the last 371 days; `tz` is an IANA timezone (the daemon's if omitted) and is what decides which day an entry falls on, so the grid and the timeline agree. `measure` is what the grid shades, currently tickets landed.

The changelog is a read-only projection over the `activity` table, not a knowledge file: it has no budget, no curation, and it is never injected into any agent's context. **There is deliberately no write route** — no `POST`, `PUT` or `DELETE`, and no service member behind one — which is what makes it append-only.

### Usage
`GET /usage?scope=workspace|project:<id>|role:<id>|worker:<id>|ticket:<id>|model:<id>&window=&grain=&start=&end=` · `GET /usage/top?by=model|ticket|role|worker|project&...` · `GET /usage/models?...` · `GET /usage/ticket/:id`

The `/usage` series answer carries `billingMix: { subscription, metered, unknown }` — tokens in the queried scope and window per `usage_events.billing_type` — so a client can tell whether any metered spend occurred without a second request. Rows recorded before a runtime had an account snapshot count as `unknown`.

`GET /usage/accounts` → `[{ workspaceId, runtimeId, displayName, billingType (metered_api|subscription_included|unknown), planLabel, limitsAvailable, limits: [{ kind: session|weekly_all|weekly_scoped, label, utilization (0..100), resetsAt, scopeLabel }], note, capturedAt }]` — the current runtime account snapshots (PLAN §16.2), one per runtime, refreshed by the supervisor every 5 minutes. An empty array means nothing has been probed yet. `limits` is empty whenever `limitsAvailable` is false; `note` says why.

`POST /usage/accounts/refresh` `{ runtimeId? }` → `{ accounts: [… as GET /usage/accounts], synced: [runtimeId], throttled: [{ runtimeId, nextSyncAt, retryAfterMs }], failed: [{ runtimeId, message }] }` — probe now (VS-84). Without `runtimeId`, every runtime the workspace spends on, the same set the supervisor poll refreshes. Rate limited to one manual sync per runtime per 30 s: a request inside that window is **not** an error — the runtime appears in `throttled` with when the next sync of it is allowed, and its current snapshot is still in `accounts`, which always carries every runtime the request asked about. Unlike the poll, a probe that threw is reported in `failed` rather than leaving the old snapshot reading as fresh; the previous snapshot does still stand. A probe that ran and could not describe the account counts as `synced` — it replaced the snapshot with `unknown` billing and a `note`, which is what the surfaces show.

`GET /usage/credentials` → `[{ workspaceId, runtimeId, displayName, present, expiresAt, lastVerifiedAt, refreshFailedAt, needsLogin, detail, updatedAt }]` — the credential state per runtime (VS-75). There is one credential per runtime per host, shared with the machine owner's own CLI; `present` and `expiresAt` are read from that file on every request, never cached. `needsLogin: true` is the gate: no turn is started for any agent on that runtime until a probe clears it, and one decision (correlation key `runtime-login:<runtimeId>`) is open for the human. **No field carries the token or any part of it**, and none may be added that does.

### Threads (chat)
`GET /threads?channel=web` · `POST /threads` `{ channel: 'web', label? }` · `GET /threads/:id/messages?before=&limit=` · `POST /threads/:id/messages` `{ body, projectId?, blockId?, replyToMessageId?, idempotencyKey? }` (inbound from human; wakes the agent. `projectId` is the project the message was sent about — an id or a slug, stored on the message and carried in the wake payload; unknown ids are rejected with `not_found`. `blockId` is a roadmap block of that project (VS-491) — stored on the message and carried in the wake payload as `blockId` and `blockTitle`; a block with no `projectId` is rejected with `validation`, and one that does not exist or belongs to another project with `not_found`. `replyToMessageId` is the message this one answers — it must name a message of the same thread, and one that does not is rejected with `not_found`; it is stored on the message and carried in the wake payload alongside `replyToExcerpt`, a bounded excerpt of that message's body. The weaver's `weave_human_send` default for it links a reply to every human message that woke its turn and that no earlier reply in the turn has already linked, so several messages that arrived batched are all recorded (VS-449). `idempotencyKey` is an optional client-generated key: a second request carrying a key already stored on that thread returns the existing message and does not wake the agent again (VS-148). Reads return `replyToMessageId`, `replyToExcerpt` and `replyToMessageIds` on every message: `replyToMessageIds` is every message the reply answers, oldest-first (`replyToMessageId` is the newest of them and the one `replyToExcerpt` quotes — VS-449), and the excerpt is resolved from the referenced row so it is available even when that message is outside the requested page. The `human_message` wake payload's `body` is bounded to 8,000 characters (VS-242): a message under that carries the full body with no extra fields; a longer one is cut to the bound with `truncated: true` and `bodyLength` set to the message's real length — the full body stays readable via `weave_thread_message_get` (see MCP § below)) · `POST /threads/:id/bind` `{ ticketId | null }`

**Search and jump-to-message (VS-320).** `GET /threads/:id/search?q=&limit=` → `[{ messageId, authorKind, authorId, createdAt, snippet }]`, newest first, over every message stored in the thread (not only a loaded page) — full-text via a dedicated `thread_message_search` FTS5 index kept current on every `inbound`/`outbound` write. `q` is always plain text: quotes, `*`, `-`, `:` and parentheses are stripped, never interpreted as FTS5 operator syntax, and never raise an error. `snippet` marks the matched text with `` / `` (STX/ETX — never raw HTML, and never `[` / `]`, which collide with this chat's own markdown links, checkboxes and `[Risk]`-style labels). Scoped exactly like `GET /threads/:id/messages` — a `:id` outside the caller's workspace is `not_found`. `GET /threads/:id/messages` also accepts `?around=<messageId>` as an alternative to `?before=` (the two are mutually exclusive; combining them is `validation`): a bounded window of messages centered on `messageId` (itself included), oldest-first, for jumping to a search result — or any known message id — that is far outside the currently loaded page. `around` naming a message outside the thread is `not_found`, the same as `weave_thread_message_get`.

**Attachments (VS-133).** `POST /threads/:id/messages` also accepts `multipart/form-data` — a `body` text field plus up to 4 `files` parts (and the same optional `projectId`, `blockId`, `replyToMessageId`, `idempotencyKey` fields as JSON) — as an alternative to the JSON shape above; the two are distinguished by `Content-Type`. Accepted types: images (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, ≤5MB each, verified against the file's own leading bytes, not just the declared type) and plain text (`text/plain`, `text/markdown`, ≤256KB each, inlined verbatim wherever the weaver reads it). Anything else, an oversized file, or more than 4 files is rejected with `validation` before anything is stored; a request whose `Content-Length` already exceeds what any accepted combination could need is rejected before the body is even read. Attachments are rejected outright on a thread bound to a ticket (out of scope — no wake payload exists on that path to carry one). A stored attachment appears as an `{ type: 'attachment', id, filename, mediaType, byteSize }` entry in the message's `parts`. Bytes are served back at `GET /threads/:threadId/attachments/:attachmentId` (same `/api` auth as everything else; `not_found` unless the attachment's own `thread_id` matches the URL — which also makes a cross-workspace fetch impossible, since each workspace is its own database). The response carries the stored `content-type`, a `content-length` taken from the bytes actually served rather than the stored size, and a `content-disposition` — `inline` for an image, otherwise `attachment` naming the display filename (VS-528). An attachment lives exactly as long as the message that carries it: no separate expiry, not counted toward usage. The weaver receives an image's actual bytes as a real MCP `image` content block on the `weave_inbox` tool result (not a filename it would have to fetch separately) — see MCP § below.

### Web push
`GET /push/config` → `{ configured, vapidPublicKey }` — what the browser needs before it can subscribe at all; the daemon generates its own VAPID key pair the first time one is needed (VS-295, `packages/server/src/vapid.ts`), so `configured` is false (and the key null) only until that generation has happened or has failed, never because an operator has to supply one · `GET /push/subscriptions` → `[{ id, endpoint, categories, createdAt }]` · `POST /push/subscriptions` `{ endpoint, keys, categories? }` → `{ id }` (201; re-registering the same endpoint replaces the row and is also how a device updates its stored `categories` without unsubscribing — `categories` is any of `decisions`/`landed`/`everything`, defaulting to `['decisions', 'landed']` when omitted) · `DELETE /push/subscriptions/:id`.

Delivery is real: creating a decision with `owner: 'human'` fires a push (`PushDispatcher`, one per workspace) to every subscription whose stored `categories` include `decisions` — the only category with an event source today. A subscription the push service rejects as permanently invalid (404/410) is deleted rather than retried forever. With no VAPID key pair configured, `sendPush` is a no-op reporting everyone `skipped`, exactly as before this existed.

### MCP
`POST/GET /mcp/runs/:runId` — Streamable HTTP MCP server named `weave-ai` exposing the `weave_*` tools scoped to that run's agent (PLAN §9.2). Weaver-only `weave_run_inspect` / `weave_run_list` read a run's phase, elapsed time and transcript over this surface — the same events `GET /runs/:id/events` serves to a session, which a run token may not reach. Weaver-only `weave_decision_review` (`{ decisionId, status: 'looked'|'concerns', note, waitingOn? }` — the note is required for both marks, VS-234; the optional ≤120-char `waitingOn` names what the card is waiting on, VS-481) marks that the weaver has reviewed a plan, merge or action approval; workers receive the existing weaver-only 403. Weaver-only `weave_role_update` (VS-335) `{ id, patch, reason, applyToRunning? }` edits a role's spec fields — the short description, scope, responsibilities, capabilities, exclusions, rules, session policy, permission, notes, name, title and icon; `id` and `project` are immutable and `secrets`/`maxWorkers` are refused here in favour of `weave_role_set_secrets`/`weave_role_set_max_workers`; a `permission` change follows the hire policy and is raised for approval, and `applyToRunning` re-briefs the role's live workers. The result reports the revision's `changedKeys`, whether a spec-rendered `CHARTER.md` was rewritten, and how many workers were re-briefed — a charter written by hand is left alone and the caller updates it with `weave_role_update_charter`. Weaver-only `weave_incident_list` / `weave_incident_get` (VS-222; global across workspaces, VS-499) read the system incidents agents filed — from every workspace plus workspace-less daemon-global rows by default, bounded by `since`; `weave_incident_list` takes an optional `workspaceId` to narrow to exactly one workspace, and each returned incident carries the originating workspace's `workspaceName` alongside its `workspaceId`. The human's daemon-wide view stays on the session routes above. `weave_incident_list`'s `status` filter (`open` | `resolved` | `all`, VS-271) defaults to `open`. Weaver-only `weave_incident_resolve` (`{ id, resolution, ticketId? }`, VS-271) marks an incident resolved — its own workspace's or another's (VS-499) — with a required reason and an optional, unvalidated ticket reference; it records `resolvedByWorkspaceId` from the calling run, an unknown id is `not_found`, resolving an already-resolved incident is `wrong_status` and never overwrites it, and resolution is never inferred from other activity. Weaver-only `weave_thread_message_get` (VS-242) `{ threadId, messageId }` → the named message's full stored body, scoped to its thread the same way `GET /threads/:threadId/attachments/:attachmentId` is — a `messageId` from a different thread is `not_found`, identically to an unknown one. It is the read path for a `human_message` wake payload whose `body` was truncated. A tool result's `content` is normally one `text` block (the JSON `ToolResult`); `weave_inbox` (VS-133) may append `image` blocks after it — one per image attachment on a bundled `human_message` wake, base64 bytes and the stored `mediaType` — so the weaver receives the actual picture as real vision input, not a filename. A text-document attachment is inlined as text inside the JSON instead, in that message's `attachments` array. `weave_ticket_list` (VS-161) returns a lean projection (no `description`) unless `includeDescription` is set; list-tool JSON is capped at 64 KiB with `truncated: true`. Get-by-id tools (`weave_ticket_get`, document/knowledge gets) are not capped. Session `GET /tickets` still returns full rows. Worker-only `weave_schedule_wakeup` (VS-317) `{ reason, delayMinutes? | at? }` queues a wake for the calling worker's own next turn with `notBefore` set; a delay is bounded (1 minute to 24 hours), exactly one of `delayMinutes`/`at` is required, and a second call replaces the worker's pending self-wake rather than stacking one. The weaver receives the existing 403. The pending self-wake appears as `scheduledWake: { at, reason } | null` on `weave_worker_list`, `weave_worker_get` and `weave_run_inspect`'s worker view.

## Events (SSE `type`)
See `EVENT_TYPES` in `@weave-ai/shared`. Payloads carry the entity snapshot where cheap (ticket, decision, worker, thread message) or `{ id }` otherwise. The daemon-wide `GET /api/events` stream multiplexes all loaded workspaces over one connection; its `id:` is an opaque base64url cursor map, with independent durable positions per workspace. Two frame types are live-only (`EPHEMERAL_EVENT_TYPES`): they arrive on both SSE routes but are never written to the outbox, never replayed, and sent without an `id:` so they do not move the client's cursor — the reader recovers by re-reading what is behind them. `worker.activity` (VS-328) is the per-worker activity line and last test tally (`{ agentId, ticketId, activity, tests }`). `run.event` (VS-417) is one run's `RunEvent`, whose `runId` the client filters on, so a page can show many live runs over the one workspace stream instead of an `EventSource` per run.
