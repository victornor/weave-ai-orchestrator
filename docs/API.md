# AgentConductor HTTP API (v1)

Base: `/api`. Workspace-scoped routes: `/api/w/:ws/...` where `:ws` is the workspace id (slug). JSON in/out. Errors: `{ error: { code, message, details?, retryable } }` with the status from `OcError.status(code)`.

Auth: `Authorization: Bearer <token>` (CLI/presenter) or the `ac_session` httpOnly cookie (web). Loopback listener accepts run tokens (`Bearer rt_...`) for `/mcp/runs/:runId` and `/api/w/:ws/agent/*` only.

## Daemon-level
- `GET /api/health` → `{ ok, version, release: { version, path, sha }, workspaces: [{id, name, status}], operatorConfigured, tlsMode, publicUrl, transcription: { configured, backend: 'chrome'|'voxtype' }, host: { platform, hostname, tools: { git|gh|openspec|wt: { available, version, need, purpose } } } }` — `version` (and `release.version`) is the short git sha of the release this process is executing, or `unknown` when it cannot be determined — never a hardcoded package version. `transcription.backend` is the web composer's dictation backend (`chrome` default); `configured` is true only when host transcription will actually run (Voxtype selected and installed, or a yaml `command` provider). `host.tools` is the daemon host's tool detection (cached 60 s), which is what a remote `conductor doctor` reports. `release` is the release directory **this process is executing** (never what `current` points at, which an upgrade swings before the restart); `release.sha` is `null` when it could not be determined.
- `POST /api/auth/setup` `{ username, password }` (only when no operator) · `POST /api/auth/login` `{ username, password, totp?, deviceName?, kind }` → `{ token, sessionId, expiresAt }` or `{ totpRequired: true }` (401 `auth_totp_required`) · `POST /api/auth/logout` · `GET /api/auth/me` → `{ operator, session, totpEnabled }`
- `GET /api/auth/sessions` · `DELETE /api/auth/sessions/:id` · `DELETE /api/auth/sessions` (all others)
- `POST /api/auth/totp/setup` → `{ secret, otpauthUrl, recoveryCodes }` · `POST /api/auth/totp/enable` `{ code }` · `POST /api/auth/totp/disable` `{ password }` · `POST /api/auth/password` `{ current, next }`
- `GET /api/workspaces` → `[{ id, name, ticketPrefix, root, projects, needsYou }]` — `needsYou` is that workspace's count of open decisions owned by the human, so the web app's sidebar can badge every workspace from one request instead of one per workspace · `POST /api/workspaces` `{ path }` (register existing) · `POST /api/workspaces/init` `{ path, id, name, ticketPrefix }` · `POST /api/workspaces/import` `{ path, target }` (stage an export into `target`, register it, import its tickets as `backlog`) → `{ id, path, created, roles, knowledgeFiles, tickets, skipped }`
- `GET /api/incidents[?reporter=conductor|worker][&limit=]` → `{ items: [Incident], total }` — system incidents agents filed through `ac_incident` (VS-174), newest first. `Incident` is `{ id, reporterKind: 'conductor'|'worker', title, whatFailed, tryingToDo, evidence, workspaceId, projectId, ticketId, agentId, runId, roleId, createdAt }`. `limit` default 100, max 200. Run tokens cannot list. · `GET /api/incidents/:id` → one `Incident` (`not_found` if unknown).
- `GET /api/runtimes` → `[{ id, displayName, detection, capabilities, models }]` · `GET /api/runtimes/:id/models`
- `GET /api/daemon/update[?refresh=1]` → `{ configured, running: { version, path, sha }, source, ref, targetSha, updateAvailable, checkedAt, error }` — resolves `upgrade.source` at `upgrade.ref` with `git ls-remote` (no clone) and compares it with the running release. `configured: false` when no `upgrade.source` is set: not an update and not an error. Cached for `upgrade.updateCheckIntervalSec` (default 900); `?refresh=1` resolves again. A check that fails sets `error` and leaves `updateAvailable` false.
- `GET /api/daemon/upgrade` → `{ upgrade, waitingFor: [{ workspace, running, runIds }] }` — the latest upgrade record, and (only while it is still cancellable) the work holding it. `upgrade.state` is one of `queued|waiting|building|switching|restarting|completed|failed|cancelled`; `upgrade.log` is a bounded tail (200 lines) of the build output; `upgrade.reason` is one of `build_failed|backup_failed|switch_failed|restart_unverified|restart_failed|abandoned`; `upgrade.drainedRuns`/`upgrade.interruptedRuns` are how many runs were still executing when dispatch was held, and how many of those were still executing when the bound to wait for them expired (the upgrade proceeds either way — see `docs/OPERATIONS.md`).
- `POST /api/daemon/upgrade` `{ ref?, source?, test? }` → 202 with the record — queue a deferred upgrade: dispatch is held at once, in-flight turns finish, and only then does the daemon build, back up, switch `current` and hand the restart to a detached runner. 409 `conflict` while one is already in flight, 400 `validation` when no source is configured.
- `POST /api/daemon/upgrade/cancel` → the cancelled record — only from `queued` or `waiting` (409 `conflict` from `building` on, 404 when nothing is in flight). Resumes dispatch on every workspace that is not itself paused.
- `POST /api/daemon/drain` `{ timeoutSec? }` → `{ drained, running: [{workspace, runId}], workspaces }` (stop dispatching everywhere, wait for in-flight turns up to the timeout; used by `conductor daemon upgrade` before a restart) · `POST /api/daemon/undrain` → `{ resumed }` (start dispatching again on workspaces that are not paused)
- `POST /api/transcribe` (multipart audio, 16 kHz mono WAV when using Voxtype) → `{ text }` or 501 when no host backend will run
- `GET /api/daemon/transcription` → `{ backend: 'chrome'|'voxtype', model, voxtype: { installed, models: [{ id, engine, installed }], error? } }` — daemon dictation setting plus the host Voxtype probe. Session auth.
- `PUT /api/daemon/transcription` `{ backend, model? }` → same shape as GET. Persists to `daemon.yaml` and takes effect without a restart. `voxtype` backend requires the binary; `model` must be an installed id. 400 `validation` otherwise.
- `GET /api/daemon/models` → `{ conductor: ModelSetting | null, workers: ModelSetting | null, workerOptions: WorkerModelOption[] | null }` — optional overlays (VS-185, ADR 0013). Null (and an empty catalog) means no overlay for that control. Session auth.
- `PUT /api/daemon/models` `{ conductor?, workers?, workerOptions? }` — omitted key leaves that overlay; `null` or `workerOptions: []` clears; a value sets. Persists to `daemon.yaml` and takes effect without a restart. Duplicate option ids are `validation` 400.
- `GET /llms/api.txt` (agent-readable summary) · `GET /api/openapi.json`

## Workspace
- `GET /api/w/:ws` → workspace + config summary · `PATCH /api/w/:ws/config` (partial `workspace.yaml`) · `POST /api/w/:ws/pause` · `POST /api/w/:ws/resume`
- `GET /api/w/:ws/events?after=<seq>` SSE stream (`event: <type>`, `id: <seq>`, `data: WorkspaceEvent`); heartbeat comment every 15 s
- `POST /api/w/:ws/export` `{ out? }` → `{ path, workspace, roles, knowledgeFiles, tickets }` (portable package: `workspace.yaml`, `roles/**`, `knowledge/**`, `tickets/*.md`; no db, no runs, no secrets)
- `GET /api/w/:ws/briefing`

### Models
`GET /models` → `{ conductor: { runtime, model, effort? }, workers: { runtime, model, effort? }, workerOptions: [{ id, description, runtime, model, effort? }], locked: { conductor, workers, workerOptions } }` — effective values after a daemon overlay (VS-185, ADR 0013), plus which controls are locked. The conductor runs on the first; a worker runs on the option its ticket names, or on `workers` when it names none. Roles, projects and agent rows still cannot choose a runtime or a model.
`PUT /models` takes the two settings whole. `workerOptions` omitted keeps the existing catalog; an explicit array (including `[]`) replaces it. Locked controls are not written to workspace yaml. `model: null` means the runtime chooses; `effort` is optional and is the only place it can be set. An empty `runtime` is a `validation` 400. Changing a runtime retires that agent's session, so its next turn starts a new one. Duplicate option ids and more than 16 options are a `validation` 400.

### Channels
`GET /channels/telegram/token` → `{ configured, source: 'secret' | 'env' | null, botUsername: string | null }` — never a token value. `source` is which precedence branch is in effect (VS-125): `secret` when the workspace secret store holds it (set from Settings), `env` when it comes from an `${ENV_VAR}` reference already resolved in `workspace.yaml`, `null` when nothing resolves.
`POST /channels/telegram/token` `{ token }` → `{ ok: true, botUsername }` — calls Telegram's `getMe` before accepting the token; on success registers it in the workspace secret store (never `workspace.yaml`, never the database) and restarts the Telegram channel with it, no daemon restart. On failure (`validation` 400, Telegram's own message) nothing is written and any previously-working token is untouched.
`DELETE /channels/telegram/token` → `{ ok: true }` — clears the stored token and stops the Telegram channel if it was running from it.
`GET /channels/telegram/pending` → `{ pending: Array<{ externalUserId, username: string | null, displayName: string | null, firstSeenAt, lastSeenAt, attemptCount }> }` (VS-135) — everyone who has messaged the bot while not on the allowlist, identity only; never the message text. Capped at 50 entries per workspace and expired 7 days after their last attempt.
`POST /channels/telegram/pending/:externalUserId/approve` → `{ allowedUserIds: number[] }` — adds the id to the allowlist, clears its pending row, and restarts the Telegram channel so their next message is accepted, no daemon restart. Approving an id already on the allowlist is a no-op that still returns the current list.
`POST /channels/telegram/allow-all/disable` → `{ ok: true }` — turns off a workspace's `allowAll` grandfathering (VS-125) in favour of the allowlist, and restarts the channel. There is no route that turns `allowAll` on; it can only ever be true for a workspace that already had it set before VS-135.

### Scheduled tasks (routines)
Human-facing name is **Scheduled tasks**; HTTP/CLI/MCP identifiers stay `routines` / `routine` (VS-220). Recurring alarms that wake the conductor with an instruction via the existing wake queue. Default action is `report` (look, then reply); `file_work` is the only filing licence. Cap `maxTicketsPerFire` ≤ 8 (defaults 0 / 3).

`GET /routines` → `{ items: [Routine] }` · `POST /routines` `{ name, trigger, instruction, action?, maxTicketsPerFire?, projectId? }` → **201** `Routine`. `trigger` is `{ kind: 'schedule', timezone?, daily: { hour, minute } }` or `{ kind: 'schedule', timezone?, everyMinutes }` (`everyMinutes` ≥ 15). Webhook and cron are `validation` 400. Timezone defaults to the host IANA zone.
`GET /routines/:id` → `Routine` · `PATCH /routines/:id` `{ name?, trigger?, instruction?, action?, maxTicketsPerFire?, projectId?, status?: 'active'|'paused' }` — resume (`status: 'active'`) arms the next future slot · `DELETE /routines/:id` → `{ ok: true }`
`GET /routines/:id/usage?window=24h|7d` → `{ tokensIn, tokensOut, tokensCached, runs, costCents, costReportedCents, window }` — conductor-turn spend for that routine's fires plus originated-ticket spend. Session auth; run tokens cannot call these routes.

### Projects
`GET /projects` · `POST /projects` `{ url, id?, defaultBranch?, landingBranch?, maxWorkers?, setupCommand?, policies? }` (strict: a project carries no runtime or model, and no top-level `autoMerge`; `policies.autoMergeDefault` (VS-153) is the project's auto-merge default, not the ticket-level flag; `landingBranch` (VS-119) is the branch its tickets' work actually lands on when it differs from `defaultBranch` — Fernwood's is `edge`, promoted to `main` separately by a human — and falls back to `defaultBranch` when unset) → **202** `{ project, jobId }` · `GET /projects/:id` · `PATCH /projects/:id` · `DELETE /projects/:id` · `POST /projects/:id/fetch`

`PATCH /projects/:id` also declares, changes or clears a project's landing branch after creation (VS-122): a non-empty `landingBranch` is rejected with a `validation` 400 naming the branch when it is not found on the project's remote as of its last fetch; `landingBranch: ''` clears it back to "use `defaultBranch`". Every check that resolves a project's effective landing branch reads the project row fresh, so a change takes effect on the next ticket action — no daemon restart.
`POST /projects/:id/retry` → **202** `{ project, jobId }` — re-run a failed add against whatever is already on disk; `conflict` unless the project's status is `error` and no job for it is running.

`GET /projects/:id/sync` → `{ syncState: 'in_sync' | 'behind' | 'diverged', behindBy: number | null }` (VS-131) — classifies the primary clone against `origin/<landingBranch>` by fetching and comparing locally; never checks out or merges, so opening this can't itself change the clone. `behindBy` is the commit count only when `behind`, else `null`. `diverged` means the clone holds a commit the remote's current tip no longer recognises (a force-push or rebase upstream) — resolving it is a human's job outside AgentConductor, never automatic. `POST /projects/:id/fetch` (above) is the one action that resolves `behind`: the same fetch, followed by `checkout` + `merge --ff-only`; both routes persist `Project.syncState` and emit `project.updated`.

**BREAKING (VS-37):** `POST /projects` used to answer `201` with the finished project after the clone, the OpenSpec adoption and the knowledge seed — minutes of work. It now answers `202` as soon as the row exists, with the project in its `cloning` status and the id of the job doing the rest. Follow `GET /jobs/:id/stream` for progress, or poll `GET /projects/:id` until its status leaves `cloning`.
`GET /projects/:id/merge-queue` → `{ projectId, concurrency, active: [MergeQueueEntry], waiting: [MergeQueueEntry], recent: [MergeQueueOutcome] }` — the per-project merge queue (PLAN §11.4). `MergeQueueEntry` is `{ ticketId, identifier, title, projectId, position, queuedAt, startedAt, workerId }`; `position` is 1-based within `waiting` and `null` for an `active` entry. `concurrency` is the project's `mergeConcurrency` policy (default 1). `MergeQueueOutcome` is `{ ticketId, identifier, title, outcome, at, mergeCommit }` — the last five tickets that left this project's queue, most recent first, `outcome` one of `landed` · `failed` (the merge could not complete) · `withdrawn` (left the queue without either); derived from the activity log, so nothing has to be recorded at merge time.

`GET /projects/:id/pull-requests` → `{ projectId, available, reason, message, stale, capturedAt, windowDays, open: [ProjectPullRequest], recent: [ProjectPullRequest] }` — the project's pull requests, read through the forge and joined on the daemon (VS-97). `open` is every open pull request, `recent` every one merged or closed within `windowDays` (30), each most recently updated first. A `ProjectPullRequest` is the forge's `{ number, title, url, author, state, isDraft, headRefName, baseRefName, createdAt, updatedAt, mergedAt, closedAt, additions, deletions, changedFiles, checks, reviewDecision, mergeCommit }` plus `ticket` (`{ id, identifier, title, status, hasPlan }` or `null` — matched by the ticket's `pull_request` work product, else by the `ac/<identifier>-` branch), `changeName` (the OpenSpec change its ticket implements, or `null`) and `queue` (`{ state: 'landing' | 'waiting', position }` or `null`). `checks` is `pending` · `success` · `failure` · `none`.

Always `200`, never an error status, for a project that has no forge: `available: false` with `reason` one of `no_forge` · `not_authenticated` · `no_clone` · `unsupported` · `unreachable`, `message` set only for `unreachable`. Forge answers are cached per project for three minutes and dropped on that project's `ticket.work_product`, `ticket.merged` and `ticket.status`; `stale: true` means a refresh failed and this is the previous answer. Read-only: there is no write, no merge and no review on this surface.

`GET /projects/:id/pull-requests/:number` → `{ projectId, available, reason, message, stale, pullRequest }` — one pull request as `ProjectPullRequest` plus `body`, `files: [{ path, additions, deletions }]` and `checkRuns: [{ name, state, url }]`. `pullRequest` is `null` with `available: true` when the forge has no such number; a non-integer or non-positive `:number` is a `validation` error.

`GET /projects/:id/pull-requests/:number/diff` → `{ projectId, number, available, reason, message, stale, files: [DiffFileSummary] }` — a pull request's changed-file manifest, from its diff rather than the forge's own file list, so it carries `status` too (VS-107). A `DiffFileSummary` is `{ path, previousPath, status, additions, deletions, binary, tooLarge }`, `status` one of `added` · `modified` · `deleted` · `renamed`. Never carries a hunk: this is the cheap list a file tree renders from. `reason` adds `no_local_branch` to the set `pull-requests` already reports — neither the forge nor the daemon's own clone could produce this pull request's diff.

`GET /projects/:id/pull-requests/:number/diff/file?path=` → `{ projectId, number, available, reason, message, file }` — one file's hunks, sliced from the same diff `diff` already read and cached. `file` is a `DiffFileSummary` plus `hunks: [{ oldStart, oldLines, newStart, newLines, header, lines: [{ kind, oldLine, newLine, text }] }]`, `kind` one of `context` · `add` · `remove`; `hunks` is `[]` when `binary` or `tooLarge`. `file` is `null` with `available: true` when the diff has no such path. `path` is required.

`GET /projects/:id/pull-requests/:number/diff/file/context?path=&start=&end=` → `{ projectId, number, available, reason, lines: [string] }` — content for a collapsed region's expand control, read from the pull request's base revision in the daemon's own clone (base and head agree wherever a diff omitted the lines) — see design.md of `vs-107-the-pr-explorer-shows-the-diff-itself-fi` for why this is always answerable from the base side even when the head branch is not local. `lines` is `[]` when the file has no content there — an added file, or a range past its end. `start`/`end` (1-based, inclusive) must be positive integers.

Diff content comes from `gh pr diff` when the forge can supply it, and otherwise from `git diff` in the daemon's own clone when the pull request's head branch is there — every worker branch always is. The same cache and event-driven invalidation as the rest of `pull-requests`. Read-only throughout: no edit, comment, approve or merge surface here either.

`GET /projects/:id/history` (`cursor?`, `limit?`, default 30, max 200) → `{ refs: [ProjectRef], commits: [HistoryCommit], cursor: string | null }` — the project's commit graph (VS-96): the default branch plus every branch a live worktree or an unfinished ticket holds, read from the project's own clone (never fetched, never mutated — the same clone every worker worktree branches off). A `ProjectRef` is `{ name, sha, isDefault, ticketId, ticketIdentifier, agentId, agentName }`; a recorded branch the repository no longer has is left out. A `HistoryCommit` is `{ sha, parents: [sha], author, authoredAt, subject, refs: [refName] }`, newest first. `cursor` pins the ref tips the first page resolved, so a branch moving mid-page cannot duplicate or drop a commit; `null` when there is no more.

`GET /projects/:id/commits/:sha` → `CommitDetail`: `{ sha, parents: [sha], author, email, authoredAt, committedAt, message, files: [CommitFile], truncatedFiles, forgeUrl }`. A `CommitFile` is `{ path, previousPath, status: 'added'|'modified'|'deleted'|'renamed', additions, deletions }` — a merge's files are reported against its first parent. `forgeUrl` is `null` unless the project's remote is a recognised forge host (github.com, gitlab.com, codeberg.org). `:sha` must be a plain abbreviated or full object name (`validation` error otherwise); an unknown commit is `not_found`.

### Jobs
A job is one long-running workspace-setup operation, watchable while it runs (PLAN §5; `openspec/specs/workspace-setup/setup-jobs`). Kinds: `project_add`.
`GET /jobs?kind=&entity=&limit=` → `[Job]` newest first — `entity` is the id of the thing the job acts on, which is how a client that lost its state finds the job still running for a project · `GET /jobs/:id` → `Job`
`Job` is `{ id, workspaceId, kind, entityType, entityId, state: running|done|failed, steps: [JobStep], log: [JobLogLine], logSeq, requestedBy, startedAt, finishedAt, failedStep, message }`. `JobStep` is `{ id, label, state: pending|running|done|skipped|failed, startedAt, endedAt }` — the whole ordered list exists from the moment the job is created. `JobLogLine` is `{ seq, step, stream: stdout|stderr|daemon, text }`; only the last 200 lines are retained on the record.
`GET /jobs/:id/stream` SSE — replays the job's steps and retained lines, then tails it. Frames are `event: job.step | job.log | job.finished`, `id: <seq>`, `data: JobStreamItem`; resume with `?after=<seq>` or `Last-Event-ID`. The stream closes once the job is terminal. A client attaching more than 200 lines late gets the tail, not the lines it missed.
The workspace outbox carries `job.started` and `job.finished` only — never a line.

### Workers (agents)
`GET /workers?status=&project=&role=&includeRetired=` (each worker carries `interactiveSession: boolean`, joined from its ticket — VS-101) · `GET /workers/:id` (agent + session + ticket + last run + usage + `input: { midTurn, reason? }` — whether a message sent right now would reach a running turn, VS-99 — + `sessionResumable: boolean` — whether the worker's *next* turn would resume its existing session rather than start fresh, VS-106; `ticket.interactiveSession` marks a session) · `GET /workers/:id/brief` · `POST /workers/:id/message` `{ body, live? }` → `{ delivery: 'mid_turn' | 'queued', runId, wakeId }` (`live` asks for mid-turn delivery when the runtime and an executing turn allow it; the human's words are always recorded on the ticket first, and delivery is never both mid-turn and queued; refused when the caller is the conductor and the ticket is an interactive session, VS-101; refused with `wrong_status` against a retired worker rather than recording a comment and queuing a wake nobody will read, VS-106) · `POST /workers/:id/relaunch` `{ note }` · `POST /workers/:id/cancel` `{ reason }` · `POST /workers/:id/pause|resume` · `POST /workers/start-session` `{ ticketId }` or `{ projectId, roleId, kind, title, description? }` → the started/resolved worker (VS-101: an interactive session always has a ticket — an existing one, or one created in this same call — and its agent is that ticket's worker, provisioned exactly as `spawn` provisions any worker's; ending one is the ordinary `POST /workers/:id/cancel` plus, if unlanded work should go, the ordinary `POST /worktrees/:id/discard`) · `GET /conductor` (same envelope as `GET /workers/:id`: `{ worker, ticket, lastRun, usage }` — `lastRun` is how a chat surface finds the turn to stream) · `POST /conductor/reset-session`

### Tickets
`GET /tickets?project=&status=&kind=&role=&search=&limit=&offset=&includeTerminal=&sort=` (`includeTerminal=true` keeps done/cancelled in an unfiltered list; `sort=finished` orders by when a ticket reached done or cancelled instead of by number; each ticket carries `interactiveSession: boolean`, VS-101, `summary: string | null`, VS-146, and `workerModelId: string | null`, VS-162) · `POST /tickets` (TicketCreateInput, which now accepts `interactiveSession?: boolean` — prefer `POST /workers/start-session` to create one and start its worker in the same call — `landingBranch?: string` (VS-119): set only at creation, overrides the project's own landing branch for this ticket alone, never inferred from a PR base — `summary?: string` (VS-146, max 200): a one-line why shown on plan-approval cards in conductor chat — and `workerModelId?: string` (VS-162): a catalog option id from `GET /models`; omit for `models.workers`; unknown id is `validation`) · `GET /tickets/:id` (id or identifier; includes blockers, children, worker, openspecState, workProducts, documents list, and `mergeQueue: { position, concurrency }` — `position` is the ticket's place among its project's waiting tickets, `null` unless it is waiting; `worker` names the ticket's current worker, falling back to the last worker that held it once it has retired, so a landed ticket still says who built it) · `PATCH /tickets/:id` `{ title?, description?, summary?, priority?, autoMerge? }` (`summary` nullish so it can be cleared) · `POST /tickets/:id/assign` `{ roleId, workerModelId? }` (`workerModelId` only while the ticket has no worker) · `POST /tickets/:id/transition` `{ to, note?, unblock?, blockedBy? }` · `POST /tickets/:id/retry` `{ note? }` (relaunch the parked worker or spawn one; blocked → back to work) · `POST /tickets/:id/cancel` `{ reason }` · `PUT /tickets/:id/blockers` `{ blockedBy: [] }`
`GET /tickets/:id/comments?after=` · `POST /tickets/:id/comments` `{ body }` (human; wakes worker) · `GET /tickets/:id/documents/:key?revision=` · `PUT /tickets/:id/documents/:key` `{ body }` · `GET /tickets/:id/documents/:key/revisions` · `GET /tickets/:id/work-products` · `GET /tickets/:id/runs` · `GET /tickets/:id/usage` · `GET /tickets/:id/knowledge-usage` (VS-110; see Knowledge & specs) · `POST /tickets/:id/discard` `{ force: true }` (creates discard_approval unless already approved)

### Decisions
`GET /decisions?status=&owner=` · `GET /decisions/:id` · `POST /decisions/:id/answer` `{ key?, text?, remember?, inputs? }` · `POST /decisions/:id/withdraw`

A decision carries `projectId` (the ticket's project, else the one the asker named, else `null` — surfaces label that as `Workspace`) and `inputs`: values the card collects as well as, or instead of, an option. `inputs` on the answer is a map keyed by input key, whose value is a string or, for a `multiselect`, the chosen keys; it is recorded on the decision as `answerInputs` and delivered to the asker in its wake. A `secret` input is the exception: its value is registered as a workspace secret under the input's `secretName` and **only that name** is recorded, so the value never reaches the decision, the chat, a ticket, a log, a transcript or an export. Clients must not put an answer carrying a secret input into any client-side retry queue.

`plan_approval`, `merge_approval` and `action_approval` also carry `conductorReviewStatus` (`unseen` | `looked` | `concerns`), `conductorReviewedAt`, `conductorReviewNote` and `conductorReviewedByAgentId` (VS-223). GET already serialises them. There is no human HTTP write for the mark; the conductor writes it through MCP `ac_decision_review`. The card always shows the state; `answer` does not read these fields.

### Runs

### Knowledge & specs
`GET /knowledge` (lint) · `GET /knowledge/:scope?project=` · `PUT /knowledge/:scope?project=` `{ body }` (human replace) · `POST /knowledge/:scope/note?project=` `{ section, text, doc? }` (`doc` appends into that linked document's section instead of the hub; the document must already exist — VS-109) · `GET /knowledge/:scope/revisions?project=` → each revision also carries `ticketId, ticketIdentifier` (nullable; VS-102) · `POST /knowledge/:scope/revert?project=` `{ revision }` · `POST /knowledge/:scope/curate?project=` · `GET /search?q=&project=` (knowledge + specs)

`GET /knowledge/health?project=` (VS-102) → `{ hubs: [{ path, scope, projectId, projectSlug, tokenEstimate, budgetTokens, pct, nearBudget, curationPending, lastCuratedAt }], orphans: [KnowledgeDocSummary], stale: [KnowledgeDocSummary], unresolvedLinks: [{ fromPath, fromTitle, toSlug }] }`. Derived on read, no new table; omitting `project` reports the whole workspace (every hub, every project's documents), a project scopes to that project's hub plus `shared`. `orphans` is every listed document with no backlink; `stale` is every listed document not written to in 90 days.

Linked documents: `GET /knowledge/docs?scope=&project=` → `[{ path, scope, projectId, projectSlug, slug, title, summary, tokenEstimate, budgetTokens, links, backlinks, updatedAt }]` · `GET /knowledge/docs/:scope/:slug?project=` → the document plus `body, revision, linksTo: [{slug, path, title}], linkedFrom: [{path, slug, title}]` · `PUT /knowledge/docs/:scope/:slug` `{ body }` → `{ path, revision, tokenEstimate, budgetTokens, unresolvedLinks, backlinks, orphan }` · `DELETE /knowledge/docs/:scope/:slug` (archived first) · `GET /knowledge/graph?project=` → `{ nodes: [{ id (path), kind: hub|doc, scope, projectId, projectSlug, slug, title, tokens, updatedAt }], edges: [{ from, to }] }`. Stub workspace hubs (SHARED.md, decisions.md, WORKSPACE.md with no section entries and no resolved wiki-links) are omitted; the unscoped graph adds workspace → shared and workspace → decisions edges when both ends are present (VS-180). A project scopes to that project's hub and documents only. Documents are `[[slug]]`-linked markdown pages under `knowledge/projects/<id>/docs/`, `knowledge/workspace/shared/` and `knowledge/workspace/docs/`, each held to `defaults.knowledgeBudgetTokens.document` (10000 by default); `GET /knowledge` (lint) rows carry `kind: hub|doc`, `title` and `projectSlug`.
`GET /specs/:project` (capabilities) · `GET /specs/:project/capabilities/:capability` · `GET /specs/:project/changes?state=` · `GET /specs/:project/changes/:name` · `GET /specs/:project/graph` · `POST /specs/:project/reindex`. Capability ids are OpenSpec paths and are often nested (`conductor-chat/dispatch-labels`); `:capability` accepts the slash either raw or percent-encoded. The capability detail is flat: `{ id, capability, title, body, requirements: [{ name, text, scenarios }], pending: [{ changeName, ticketId, ticketIdentifier, deltaKind }], history: [{ changeName, ticketId, ticketIdentifier, state, archivedAs, archivedAt }] }`.

**Knowledge context (VS-110)** — what a run actually consumed, not a file's stored estimate; separate from `/usage` below, which is billed model tokens. `GET /tickets/:id/knowledge-usage` → `{ hubTokens, documentTokens, totalTokens, documents: [{ scope, projectId, slug, tokens }] }`, summed over the ticket's own runs and its subtree. `GET /knowledge/usage/summary?project=&window=` → `{ averageTokensPerRun, runs }` · `GET /knowledge/usage/top?project=&window=` → `[{ scope, projectId, slug, title, reads, tokens }]`, most-read first · `GET /knowledge/usage/never-read?project=&window=` → `[{ scope, projectId, slug, title, tokenEstimate }]`, documents in the catalogue no run read in the window. `window` is the same vocabulary as `/usage` (`24h|today|yesterday|week|7d|month|all|custom`), defaulting to `all`. Registered before `/knowledge/:scope` so `usage` is never read as a knowledge scope.

### Changelog
`GET /changelog?project=&before=&limit=` → `{ entries: [{ id, at, kind, actor: { kind, id, label }, projectId, ticketId, ticketIdentifier, summary, link }], nextCursor }` — the human-facing record of what happened (PLAN §13.6), newest first. `kind` is one of `filed | plan_approved | pr_opened | landed | cancelled | hired | upgraded`; `link` is `{ kind: 'ticket' | 'url', target }` or null. Without `project` the workspace changelog is served: every project's entries plus the ones belonging to none. `before` is the `nextCursor` of the previous page; `nextCursor` is null when nothing older remains. `limit` defaults to 50 and is capped at 200.

`GET /changelog/heatmap?project=&from=&to=&tz=` → `{ days: [{ date, landed, total, byKind }], timezone, measure: { kind, label, definition } }` — activity per day, dense: every day in the range is present, a quiet day reporting zero. `from`/`to` are `YYYY-MM-DD` and default to the last 371 days; `tz` is an IANA timezone (the daemon's if omitted) and is what decides which day an entry falls on, so the grid and the timeline agree. `measure` is what the grid shades, currently tickets landed.

The changelog is a read-only projection over the `activity` table, not a knowledge file: it has no budget, no curation, and it is never injected into any agent's context. **There is deliberately no write route** — no `POST`, `PUT` or `DELETE`, and no service member behind one — which is what makes it append-only.

### Usage
`GET /usage?scope=workspace|project:<id>|role:<id>|worker:<id>|ticket:<id>|model:<id>&window=&grain=&start=&end=` · `GET /usage/top?by=model|ticket|role|worker|project&...` · `GET /usage/models?...` · `GET /usage/ticket/:id`

The `/usage` series answer carries `billingMix: { subscription, metered, unknown }` — tokens in the queried scope and window per `usage_events.billing_type` — so a client can tell whether any metered spend occurred without a second request. Rows recorded before a runtime had an account snapshot count as `unknown`.

`GET /usage/accounts` → `[{ workspaceId, runtimeId, displayName, billingType (metered_api|subscription_included|unknown), planLabel, limitsAvailable, limits: [{ kind: session|weekly_all|weekly_scoped, label, utilization (0..100), resetsAt, scopeLabel }], note, capturedAt }]` — the current runtime account snapshots (PLAN §16.2), one per runtime, refreshed by the supervisor every 5 minutes. An empty array means nothing has been probed yet. `limits` is empty whenever `limitsAvailable` is false; `note` says why.

`POST /usage/accounts/refresh` `{ runtimeId? }` → `{ accounts: [… as GET /usage/accounts], synced: [runtimeId], throttled: [{ runtimeId, nextSyncAt, retryAfterMs }], failed: [{ runtimeId, message }] }` — probe now (VS-84). Without `runtimeId`, every runtime the workspace spends on, the same set the supervisor poll refreshes. Rate limited to one manual sync per runtime per 30 s: a request inside that window is **not** an error — the runtime appears in `throttled` with when the next sync of it is allowed, and its current snapshot is still in `accounts`, which always carries every runtime the request asked about. Unlike the poll, a probe that threw is reported in `failed` rather than leaving the old snapshot reading as fresh; the previous snapshot does still stand. A probe that ran and could not describe the account counts as `synced` — it replaced the snapshot with `unknown` billing and a `note`, which is what the surfaces show.

`GET /usage/credentials` → `[{ workspaceId, runtimeId, displayName, present, expiresAt, lastVerifiedAt, refreshFailedAt, needsLogin, detail, updatedAt }]` — the credential state per runtime (VS-75). There is one credential per runtime per host, shared with the machine owner's own CLI; `present` and `expiresAt` are read from that file on every request, never cached. `needsLogin: true` is the gate: no turn is started for any agent on that runtime until a probe clears it, and one decision (correlation key `runtime-login:<runtimeId>`) is open for the human. **No field carries the token or any part of it**, and none may be added that does.

### Threads (chat)
`GET /threads?channel=web` · `POST /threads` `{ channel: 'web', label? }` · `GET /threads/:id/messages?before=&limit=` · `POST /threads/:id/messages` `{ body, projectId?, replyToMessageId?, idempotencyKey? }` (inbound from human; wakes the agent. `projectId` is the project the message was sent about — an id or a slug, stored on the message and carried in the wake payload; unknown ids are rejected with `not_found`. `replyToMessageId` is the message this one answers — it must name a message of the same thread, and one that does not is rejected with `not_found`; it is stored on the message and carried in the wake payload alongside `replyToExcerpt`, a bounded excerpt of that message's body. `idempotencyKey` is an optional client-generated key: a second request carrying a key already stored on that thread returns the existing message and does not wake the agent again (VS-148). Reads return both `replyToMessageId` and `replyToExcerpt` on every message, the excerpt resolved from the referenced row so it is available even when that message is outside the requested page) · `POST /threads/:id/bind` `{ ticketId | null }`

**Attachments (VS-133).** `POST /threads/:id/messages` also accepts `multipart/form-data` — a `body` text field plus up to 4 `files` parts (and the same optional `projectId`, `replyToMessageId`, `idempotencyKey` fields as JSON) — as an alternative to the JSON shape above; the two are distinguished by `Content-Type`. Accepted types: images (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, ≤5MB each, verified against the file's own leading bytes, not just the declared type) and plain text (`text/plain`, `text/markdown`, ≤256KB each, inlined verbatim wherever the conductor reads it). Anything else, an oversized file, or more than 4 files is rejected with `validation` before anything is stored; a request whose `Content-Length` already exceeds what any accepted combination could need is rejected before the body is even read. Attachments are rejected outright on a thread bound to a ticket (out of scope — no wake payload exists on that path to carry one). A stored attachment appears as an `{ type: 'attachment', id, filename, mediaType, byteSize }` entry in the message's `parts`. Bytes are served back at `GET /threads/:threadId/attachments/:attachmentId` (same `/api` auth as everything else; `not_found` unless the attachment's own `thread_id` matches the URL — which also makes a cross-workspace fetch impossible, since each workspace is its own database). An attachment lives exactly as long as the message that carries it: no separate expiry, not counted toward usage. The conductor receives an image's actual bytes as a real MCP `image` content block on the `ac_inbox` tool result (not a filename it would have to fetch separately) — see MCP § below.

### MCP
`POST/GET /mcp/runs/:runId` — Streamable HTTP MCP server named `agent-conductor` exposing the `ac_*` tools scoped to that run's agent (PLAN §9.2). Conductor-only `ac_run_inspect` / `ac_run_list` read a run's phase, elapsed time and transcript over this surface — the same events `GET /runs/:id/events` serves to a session, which a run token may not reach. Conductor-only `ac_decision_review` (`{ decisionId, status: 'looked'|'concerns', note? }`) marks that the conductor has read a plan, merge or action approval; workers receive the existing conductor-only 403. Conductor-only `ac_incident_list` / `ac_incident_get` (VS-222) read the system incidents agents filed, scoped to the caller's workspace plus workspace-less daemon-global rows and bounded by `since`; the human's daemon-wide view stays on the session routes above. A tool result's `content` is normally one `text` block (the JSON `ToolResult`); `ac_inbox` (VS-133) may append `image` blocks after it — one per image attachment on a bundled `human_message` wake, base64 bytes and the stored `mediaType` — so the conductor receives the actual picture as real vision input, not a filename. A text-document attachment is inlined as text inside the JSON instead, in that message's `attachments` array. `ac_ticket_list` (VS-161) returns a lean projection (no `description`) unless `includeDescription` is set; list-tool JSON is capped at 64 KiB with `truncated: true`. Get-by-id tools (`ac_ticket_get`, document/knowledge gets) are not capped. Session `GET /tickets` still returns full rows.
