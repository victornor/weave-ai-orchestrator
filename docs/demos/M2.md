# M2 — Roles, workers, worktrees, the OpenSpec flow, worker-performed merge

Demonstrates PLAN §22 M2: `oc project add`, hiring a role and approving the hire, worker spawn with
a generated brief and a provider-created worktree, the full `change` ticket flow
(`proposing → proposed → approved → in_progress → in_review → merging → done`) driven by **one
worker on one session**, the worker rebasing and resolving a conflict itself, OpenSpec archive on the
default branch, the landed-work removal test, worker retirement, concurrency limits, stuck-worker
relaunch, and the discard guard.

**Takes:** 45–90 minutes depending on the repo. **Needs:** M1 done, a git repo you can push to,
`gh auth login` on the daemon host (or `deliveryMode: local-branch`), `openspec` and `wt` installed
(the demo is run twice, once per worktree provider).

---

## 1. Add a project

```bash
oc project add git@github.com:acme/api.git --runtime claude --setup "pnpm install"
oc project show api
oc ticket list -p api
```

Expected:

- `projects/api/` is a clone kept on the default branch — nothing ever works in it.
- `openspec init` ran in the clone if the repo had no `openspec/` (best effort; a failure is logged,
  not fatal).
- `knowledge/projects/api/PROJECT.md` exists, seeded from the template with empty sections.
- A `scout` ticket **ACME-1 "Describe project api"** exists in `backlog` — no role, so nothing runs.
- The generated `wt.toml` names the project: `cat ~/work/acme/.openconductor/wt.toml`.

## 2. Hire a role

There is no `oc role hire` — hiring is the conductor's job (it uses the `oc_role_hire` tool), and you
confirm it. Ask for it:

```bash
oc say "hire a backend engineer for api, on claude"
oc decision list
```

Expected: one open decision of kind `hire_approval`, titled `Hire <name> for api?`, with options
`approve`, `runtime:<other runtime>` (one per other registered runtime) and `reject`.

```bash
oc decision show <id>            # the charter summary, scope, runtime, model, max workers
oc decision answer <id> approve  # or: oc decision answer <id> 1
oc role list
```

Expected: the role goes `pending_activation → active`. Answering `runtime:opencode` instead approves
the hire *and* switches the runtime before the first run. `roles/<id>/role.yaml` and `CHARTER.md`
exist on disk; `oc role charter show <id>` prints the charter.

The scout ticket now has a home. Within a tick the supervisor spawns a worker for it:

```bash
oc worker list
oc ticket show ACME-1
```

When it finishes, `PROJECT.md` is seeded from its report:

```bash
oc knowledge show project -p api
oc knowledge lint
```

## 3. Ask for a change

```bash
oc say "in api, add a /healthz endpoint that returns build info. Plan it first."
oc ticket list -p api
```

Expected: the conductor creates a `change` ticket (say **ACME-2**) with a description carrying
context, the request and acceptance criteria, assigns it to the Backend Engineer role, and tells you
a worker is drafting the plan.

Watch the worker come up:

```bash
oc worker list
oc worker show <workerId>          # home, worktree, ticket, session, runtime, spend
oc worker brief <workerId>         # exactly what it was told
oc attach <workerId>               # live transcript; q to leave
```

Expected on disk: `workers/<id>/AGENTS.md` (charter + brief), `brief.md`, `.claude/skills/…`, and
`work/` — a worktree of `projects/api` on branch `oc/acme-2-...`, created by `wt` and warmed with the
setup command.

## 4. Approve the plan

```bash
oc ticket show ACME-2
oc decision list
```

Expected: ticket in `proposed`; one open `plan_approval` decision, options `approve` / `revise` /
`reject`, free text allowed. The plan itself is a revisioned ticket document, and the OpenSpec change
validated before the decision was created.

Try a revision first, to prove the loop:

```bash
oc decision answer <id> revise --text "also cover the version endpoint, and no new dependencies"
oc ticket show ACME-2
```

Expected: the ticket goes back to `proposing`, the same worker is woken with a `ticket_comment`
wake, and a new `plan_approval` decision supersedes nothing — the old one is answered, the new one
appears when the worker re-proposes.

Then approve:

```bash
oc decision answer <id> approve
oc ticket show ACME-2
```

Expected: status `approved`, the *same* worker woken (same session — it remembers its own proposal),
then `in_progress` as it starts ticking `tasks.md`.

## 5. Delivery

Watch it work:

```bash
oc attach <workerId>
oc ticket comments ACME-2
oc ticket comment ACME-2 "use the existing config loader, don't add a new one"
```

Expected: the comment is stored as a human comment, wakes the worker, and the worker answers with a
comment of its own. Everything you said to each other stays on the ticket.

When all tasks are done the worker pushes, opens a PR with `gh`, records a work product, and
transitions `in_review`:

```bash
oc ticket show ACME-2
oc ticket open ACME-2 --pr --print
```

For `deliveryMode: local-branch` (no `gh`), set it on the project and the worker delivers a branch
work product instead of a PR — everything else in this demo is identical:

```yaml
projects:
  - id: api
    policies: { deliveryMode: local-branch, requireCi: false }
```

## 6. Merge, with a real conflict

Before approving the merge, land a conflicting change on `main` yourself so the worker has to rebase:

```bash
# in a normal clone of api, on main
$EDITOR <a file the ticket also touches> && git commit -am "conflicting change" && git push
```

Then:

```bash
oc decision list                 # merge_approval: approve | changes
oc decision answer <id> approve
oc attach <workerId>
```

Expected, in one turn of the same session: ticket `merging`; the worker rebases onto `main`, resolves
the conflict itself, re-runs tests and lint, pushes with `--force-with-lease`, waits for CI,
`gh pr merge --squash`, and reports done. The daemon then verifies the merge on the forge,
fast-forwards `projects/api`, runs `openspec archive` on the default branch and pushes the archive
commit, runs the **landed-work test**, removes the worktree, retires the worker, and sets the ticket
`done`.

```bash
oc ticket show ACME-2
oc worktree list -p api          # the ticket's worktree is gone
oc worker list --all             # the worker is retired
ls ~/work/acme/archive/workers/  # its brief, notes and final report
oc specs changes -p api --state archived
oc usage --scope ticket:ACME-2 --by model
oc knowledge show project -p api # one new dated learning
```

## 7. Concurrency and the role slot limit

Set the role's limit low, then queue four tickets:

```bash
oc role show <roleId>            # note maxWorkers
for i in 1 2 3 4; do
  oc ticket create "concurrency probe $i" -p api -k task --assign <roleId>
done
oc worker list
oc top
```

Expected: workers spawn up to `role.maxWorkers` (and no further than the project's `maxWorkers`
across all roles). The fourth ticket stays `todo` with no worker; asking the conductor about it gets
a plain-language answer about the slot rather than silence. Each running worker has its own worktree:

```bash
oc worktree list -p api
```

## 8. Kill a worker mid-turn

```bash
oc runs list -s running                       # note the run id and its worker
oc runs show <runId> --json | jq '.pid, .pgid'   # the daemon records both
kill -9 <pid>
```

Expected: within a supervisor tick (15 s) the run is marked failed, and the worker is **relaunched
into the same home and the same worktree** with a progress note (last status, tasks ticked, dirty
files, last commit) and finishes the ticket. Nothing is reset. `oc worker relaunch <id> --note "…"`
does the same by hand.

## 9. Discard is guarded

```bash
oc ticket discard ACME-3
# Type ACME-3 to discard its worktree and any uncommitted work:
```

Expected: without typing the identifier, nothing happens. With `--force` (or after typing it), the
call still does not destroy anything — it creates a `discard_approval` decision and prints
`needs approval — answer decision <id>`. Only after `oc decision answer <id> approve` is the
unlanded worktree removed. `oc worktree verify <id>` shows the verdict (`dirty` / `landed` /
ahead-behind) that the guard is based on.

## 10. Run it again with the `git` provider

```yaml
# workspace.yaml
projects:
  - id: api
    worktrees: git
    warmPaths: [node_modules]
    setupCommand: pnpm install
```

Restart the daemon (or `PATCH /api/w/acme/config`) and repeat steps 3–6. The demo must pass
identically; only `oc worktree list` shows the provider changed.

## Acceptance checklist

- [ ] `oc project add` clones, initialises OpenSpec, seeds `PROJECT.md`, and creates the scout ticket.
- [ ] The conductor hires; the human approves the hire; the approval card can switch the runtime.
- [ ] A worker spawns with its own home, generated brief and worktree, and proposes in the worktree.
- [ ] `revise` sends the plan back to the same worker; `approve` moves it to `approved` on the same session.
- [ ] The worker implements, ticks tasks, delivers a PR (or a branch), and transitions `in_review`.
- [ ] The human approves the merge; the same worker rebases onto a conflicting `main`, resolves, merges.
- [ ] The daemon archives the change on the default branch, removes the worktree, retires the worker, ticket `done`.
- [ ] Three tickets on one role run as three concurrent workers; a fourth waits and the conductor says so.
- [ ] Killing a worker mid-turn relaunches it with a progress note into the same worktree; it finishes.
- [ ] `oc ticket discard` refuses without confirmation and still requires an approved `discard_approval`.
- [ ] Both worktree providers pass.

## Not yet automated

- Hiring has no CLI verb. It happens through the conductor (`oc say "hire …"`) or the web app;
  `oc role activate <id>` only activates a role that already exists.
- There is no CLI for editing a role's charter text — `oc role charter show|rollback` reads and
  reverts; new charter text goes through the conductor or `PUT /api/w/<ws>/roles/:id/charter`.
- Hourly reconciliation of PR state against the forge (PLAN §7.5) is not in the supervisor loop yet;
  `oc project fetch` refreshes the clone and reindexes specs on demand.
