# M3 — Telegram, presentation surfaces, TOTP

Demonstrates PLAN §22 M3: the Telegram channel with decision cards as inline buttons, TOTP and
device management, and the client-side presenter putting every live worker into its own tmux window,
Hyprland window or herdr pane — switchable at runtime without restarting a single run.

**Takes:** 30–45 minutes. **Needs:** M2 done and at least one ticket you can push through it again, a
Telegram bot token from `@BotFather`, and (for the surface half) a machine running Hyprland and/or
herdr and/or tmux.

---

## Part 1 — TOTP and devices

TOTP enrolment is web-only; there is no `conductor` command for it.

1. Open the web app, **Settings → Security**, and start TOTP setup. The server returns a secret, an
   `otpauth://` URL rendered as a QR code, and a list of **recovery codes** — write those down, they
   are the only way back in if you lose the authenticator.
2. Enter the six-digit code to enable it. `GET /api/auth/me` now reports `totpEnabled: true`.
3. From the CLI:

```bash
conductor logout --forget
conductor login https://conductor.example.com --pin --device laptop
# Password for operator@conductor.example.com:
# Six-digit code:
```

Expected: the first login attempt comes back `401 auth_totp_required`, the CLI prompts for the code,
and the second attempt succeeds. A recovery code is accepted at the same prompt.

4. Prove the lockout and the device list:

```bash
conductor devices list                       # kind, device name, ip, last seen, expires
conductor devices revoke <sessionId>
conductor devices revoke --all               # everything except the session you are using
```

Five failed logins within `auth.lockoutMinutes` return `429 auth_locked`
(`too many failed attempts; try again in 15 minutes`). Recovery is in
[`../OPERATIONS.md`](../OPERATIONS.md#locked-out--auth_locked-http-429).

## Part 2 — Telegram

Configure the channel in `workspace.yaml`. The token is **always** an `${ENV_VAR}` reference; a
literal is rejected by the schema.

```yaml
conductor:
  channels: [web, cli, telegram]
channels:
  telegram:
    botToken: ${TELEGRAM_BOT_TOKEN}
    allowedUserIds: [12345678]     # your numeric Telegram user id; empty = allow everyone
```

Put the variable where the daemon will see it. Under systemd that means the unit, not your shell:

```bash
printf 'TELEGRAM_BOT_TOKEN=123456:AA...\n' > ~/.config/agent-conductor/env
chmod 600 ~/.config/agent-conductor/env
# add to ~/.config/systemd/user/agent-conductor.service, under [Service]:
#   EnvironmentFile=%h/.config/agent-conductor/env
systemctl --user daemon-reload && systemctl --user restart agent-conductor.service
journalctl --user -u agent-conductor -n 50 | grep telegram
```

Expected: `telegram channel started` with `allowedUsers: 1`. If the variable is missing you get
`invalid telegram config: botToken: unresolved ${ENV_VAR} reference (set the environment variable on
the daemon host)` and the channel does not start — the rest of the daemon is unaffected.

Now, from your phone:

1. Message the bot: *"in api, add a `/version` endpoint and merge it when it's done."*
   Expected: the conductor replies in the same chat, creates the ticket with **auto-merge on**
   (because you said so), and assigns it.
2. Wait for the plan. Expected: a **decision card** as a Telegram message with inline buttons
   (`Approve`, `Revise`, `Reject`). Tap `Approve`.
   Expected: the button is acknowledged, the ticket moves to `approved`, and the worker continues on
   the same session. On the laptop, `conductor decision list` now shows nothing open — same state,
   different surface.
3. Because auto-merge is on, no merge card appears. Expected final message: something like
   *"`/version` landed in api (PR #88 merged)."*

Sanity checks from any client:

```bash
conductor ticket show ACME-<n>          # autoMerge: true, status done
conductor decision list -s answered
```

A message from a user id that is not in `allowedUserIds` is ignored, logged once, and any button
press answers `Not authorised.`

## Part 3 — Presentation surfaces

Surfaces never change execution. The daemon stores the desired configuration; `conductor presenter`, running
on **the machine whose screen you are looking at**, reconciles windows locally and each window runs
`conductor attach <worker>` against the daemon.

Start with the reference surface, tmux, because it works over SSH:

```bash
conductor presentation set workers.surface tmux
conductor presentation set workers.session ac-acme
conductor presentation status

conductor presenter &                   # on the machine you are looking at
conductor presentation open             # attaches this terminal to the tmux session
```

Expected: a tmux session `ac-acme`, one window per live worker running `conductor attach <id>`, window names
carrying role, ticket and status glyph, appearing and disappearing as tickets start and finish.

Now Hyprland:

```bash
conductor presentation set workers.surface hyprland
conductor presentation set workers.workspace 5
conductor presentation set workers.layout grid
conductor presentation set conductor.surface terminal

pkill -f 'conductor presenter'; conductor presenter --surface hyprland &
```

Expected: each live worker gets its own terminal window on Hyprland workspace 5, tiled as a grid,
titled `<role> #<n> · <ticket> · <status>`; the conductor opens in a terminal on your current
workspace running `conductor chat`. Windows close (after a short grace) when a worker retires.
The adapter never writes to a Hyprland config file — everything is `hyprctl keyword windowrule`,
`hyprctl dispatch exec`, `hyprctl clients -j` at runtime, re-applied on every reconcile. The terminal
is `$TERMINAL`, else `xdg-terminal-exec`, else set `workers.terminal` explicitly:

```bash
conductor presentation set workers.terminal foot
```

Then herdr, live, **without restarting any run**:

```bash
conductor presentation set workers.surface herdr
conductor presentation set workers.workspace acme
conductor presentation set workers.tabPerProject true
conductor presentation reconcile
```

Expected: the Hyprland windows close and the same workers reappear in one herdr workspace with a tab
per project and a pane per worker. `conductor runs list -s running` shows the same run ids throughout — the
processes never stopped.

Useful checks:

```bash
conductor presentation status           # desired config + what the presenters report
conductor top                           # the same picture in one terminal screen
conductor presentation set workers.surface headless   # back to nothing on screen
```

Two presenters can run at once (laptop and desktop) with different surfaces each; pass `--surface`
to override the workspace setting for one of them, and `--once` to reconcile and exit.

## Acceptance checklist

- [ ] TOTP can be enabled in the web app and `conductor login` prompts for the code (and accepts a recovery code).
- [ ] `conductor devices list|revoke` works; five bad logins lock the account for the configured window.
- [ ] Telegram: a message creates a ticket; a plan arrives as a card with inline buttons; tapping Approve advances the ticket.
- [ ] Auto-merge on a ticket suppresses the merge card and the work still lands.
- [ ] A non-allowlisted Telegram user is ignored.
- [ ] `conductor presenter` on tmux puts one window per live worker into `ac-<workspace>` and `conductor presentation open` attaches.
- [ ] Hyprland: one titled window per live worker on the configured workspace; windows appear and disappear with tickets.
- [ ] Switching `workers.surface` to herdr moves the same workers without restarting any run.

## Not yet automated

- **Telegram has no slash commands.** `/talk <ticket>` from PLAN §11.7 is not implemented; to talk to
  a specific worker use the web ticket page, `conductor chat <ticketId>`, `conductor attach <worker>` or
  `conductor ticket comment <id> "..."`.
- **PWA push notifications are not delivered.** Subscriptions are stored
  (`POST /api/w/<ws>/push/subscriptions`) but the sender is a stub that logs and reports `skipped` —
  VAPID keys and delivery are outstanding. Decision cards still arrive on Telegram and in the web app.
- **Voice dictation off-device needs a provider.** `transcription.provider` defaults to `none`, and
  `POST /api/w/<ws>/transcribe` then returns 501 with a clear message. Set
  `transcription: { provider: command, command: "<cmd reading audio on stdin>" }` in `daemon.yaml` to
  enable it. The browser's own Web Speech API works without any of this where the browser supports it.
- **ACME TLS is not implemented** (`http.tls.mode: acme` throws). Use `self-signed` with
  `conductor login --pin`, `files` with certbot, or a reverse proxy.
- `conductor daemon install-service` writes a **systemd user unit** only; there is no launchd plist and no
  Docker image in the repo yet.
