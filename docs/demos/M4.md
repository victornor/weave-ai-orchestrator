# M4 — Usage analytics and the Spec Explorer

Demonstrates PLAN §22 M4: the usage API with its shared windows and grains, per-ticket cost with the
subtree rolled up, model mix over time, the spec index and Spec Explorer (capabilities, changes,
search, graph), and the CLI and web views agreeing to the token.

**Takes:** 20 minutes. **Needs:** M2 done — you need at least one merged `change` ticket with real
turns behind it, and `openspec` installed so the index has something to show.

---

## 1. Usage in the terminal

```bash
oc usage                                        # workspace, last 24h, totals
oc usage --window 7d --grain day --series       # every bucket, not just the totals
oc usage --scope project:api --window month
oc usage --by model --window 7d                 # the model mix
oc usage --by ticket --window month             # the most expensive tickets
oc usage --by role
oc usage --scope ticket:ACME-2                  # one ticket, subtree rolled up
oc usage --scope worker:<workerId>
oc usage --window custom --start 2026-09-01T00:00:00Z --end 2026-09-04T00:00:00Z
```

Windows: `24h`, `today`, `yesterday`, `week`, `7d`, `month`, `all`, `custom`.
Grains: `hour`, `day`, `week`.
Scopes: `workspace`, `project:<id>`, `role:<id>`, `worker:<id>`, `ticket:<id>`, `model:<id>`.

Expected in every view: tokens (in, out, cached) as the headline number, cost beside it, and cost
always labelled **reported** or **estimated** — reported when the runtime told us, estimated when the
daemon priced the tokens itself. Nothing here ever blocks work: there are no budgets in v1.

## 2. Usage in the web app

Open **Usage** in the web app and set it to the same scope and window.

Expected: the totals match `oc usage` exactly. The view carries the workspace and per-project totals,
the share each project takes, a series at the selected grain, the model mix over time, per-role and
per-worker breakdowns, and run counts with successes.

Cross-check to the token:

```bash
oc usage --scope ticket:ACME-2 --json | jq '{tokens, cost}'
```

Then open the ticket page in the web app and compare its cost panel and per-turn breakdown. They read
from the same endpoint (`GET /api/w/<ws>/usage`), so any difference is a bug worth filing.

## 3. Per-turn attribution

```bash
oc ticket show ACME-2
oc runs list -t ACME-2
oc runs show <runId>                 # transcript + phase timings + usage + cost for one turn
```

Expected: every run on the ticket is attributed to the workspace, project, role, worker, ticket and
model, and the sum of the runs equals `oc usage --scope ticket:ACME-2`. A ticket with children shows
the subtree rolled up.

## 4. The spec index

```bash
oc specs list -p api                       # capabilities on main
oc specs show <capability> -p api          # requirements, scenarios, pending deltas
oc specs changes -p api                    # every change; --state active|archived to filter
oc specs changes -p api --state archived   # what has landed
oc specs changes <change-name> -p api      # one change: proposal, design, tasks, deltas
oc specs search "health" -p api            # knowledge + specs in one query
oc specs explore api                       # the TUI explorer
```

Expected: the capability your M2 ticket touched exists; the requirement it added is attributed to
**ACME-2** and its PR; a change that is still in flight shows as a pending delta linked to its
ticket. Everything is read-only — specs change only through tickets.

If the index looks stale (someone pushed to `main` outside OpenConductor):

```bash
oc project fetch api          # fast-forwards the clone and reindexes
# or: curl -X POST .../api/w/acme/specs/api/reindex
```

## 5. The Spec Explorer and Knowledge, in the web app

Open **Knowledge & Specs**. One section, one search box.

Expected:

- **Knowledge**: the workspace KB, `SHARED.md`, `decisions.md` and each project's `PROJECT.md`, each
  with a size/budget meter, last-curated date, revision history, revert, and a "curate now" action.
  The same numbers as `oc knowledge lint`.
- **Specs**: per project a capability list; capability pages with requirements and scenarios, pending
  deltas linked to their tickets, and change history back to tickets and PRs; change pages with
  proposal, design, tasks (with progress) and delta specs; and a **Graph** toggle where capabilities,
  changes and tickets are nodes.
- **Search** finds text across specs and knowledge in one box; `⌘K` opens the command palette from
  anywhere.

```bash
oc knowledge lint            # compare against the meters in the UI
```

## 6. Doctor

```bash
oc doctor
oc doctor --json | jq '.checks[] | select(.ok != true)'
```

Expected: a line per check — context, local daemon process, node ≥ 22, git, gh, daemon API, operator
password, workspaces, and one line per runtime with its detected version — each failing line followed
by the exact command that fixes it, and a non-zero exit code when something failed.

## Acceptance checklist

- [ ] `oc usage` supports every scope, window and grain, and `--by` breaks down by model, ticket, role, worker and project.
- [ ] The Usage view in the web app matches `oc usage --scope ticket:ACME-2` to the token.
- [ ] Cost is always labelled reported or estimated; tokens are the headline.
- [ ] The ticket page shows per-turn cost and the subtree rollup.
- [ ] `oc specs list|show|changes|search` return the capability that the M2 ticket changed, attributed to that ticket.
- [ ] The Spec Explorer shows capability pages, change pages and the graph, all read-only.
- [ ] `oc knowledge lint` and the KB meters in the UI agree.
- [ ] `oc doctor` is green, or names the fix for every failure.

## Not yet automated

- **`oc workspace export|import` does not exist yet.** PLAN §20 specifies it; the CLI currently has
  `oc workspace list|use|register|unregister`. Move a workspace by copying its directory and
  registering it (`oc workspace register <path>`).
- **OTLP export is not wired.** `otlpEndpoint` is accepted by `daemon.yaml`'s schema but nothing reads
  it; telemetry stays in the run log and the database. There is no phone-home either way.
- **Usage is computed on read**, not from precomputed daily rollups. That is fine at demo scale;
  large windows over long histories will be slower than the plan's rollup design.
- **Nothing prunes the run logs yet.** `defaults.runLogRetentionDays` and `defaults.workerArchiveDays`
  are read from `workspace.yaml` but no code enforces them, so `<workspace>/.openconductor/runs/` and
  `<workspace>/archive/workers/` grow without bound. Delete old run directories by hand for now.
