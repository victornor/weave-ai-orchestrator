# M5 — More runtimes, and the plugin API

Demonstrates PLAN §22 M5: the Codex, OpenCode and Gemini adapters (args, event parsers, session
resume, `cwd = home` instruction discovery, per-workspace config homes, `listModels`,
`oc runtime login`), the model dropdown per runtime, and the plugin surface (`plugin-sdk`, OpenAPI,
`llms/api.txt`).

The demo is: **run M2 again with the role on a different runtime, and get the same result.**

**Takes:** 30 minutes per runtime. **Needs:** M2 passing on `claude`, and the target CLI installed
and authenticated on the daemon host.

> **Live status.** `claude` and `opencode` have been driven end to end against real accounts.
> `codex` and `gemini` are implemented and fixture-tested but **have not been verified live** — the
> point of running this demo on them is to find out what breaks.

---

## 1. Detection and models

```bash
oc runtime list
oc runtime detect
oc runtime models opencode
oc runtime models codex
```

Expected: one row per registered runtime with `available`/`missing`, a version, a path and a model
count. A missing CLI is never fatal — the runtime is simply not usable. Model sources differ:
OpenCode reports models it detects (`source: detected`); Claude, Codex and Gemini offer a static list
plus whatever you configure.

## 2. Log the runtime in, in the workspace's own config home

Runs never touch your personal CLI config. Each runtime gets a config home at
`<workspace>/.openconductor/runtimes/<runtime>/`, seeded once from your host credentials when the
workspace is first loaded, and otherwise filled by:

```bash
oc runtime login opencode --print     # shows the env and command it would run
oc runtime login opencode             # actually runs it, with the env pointed at the config home
```

| Runtime | env pointed at the config home | command it runs |
|---|---|---|
| claude | `CLAUDE_CONFIG_DIR` | `claude setup-token` |
| codex | `CODEX_HOME` | `codex login` |
| opencode | `XDG_CONFIG_HOME` | `opencode auth login` |
| gemini | `GEMINI_CLI_HOME` | `gemini` (prompts on first run) |

```bash
ls ~/work/acme/.openconductor/runtimes/opencode/
```

Expected: credentials there, mode 0600, and nothing new in `~/.config` or `~/.local/share` for that
CLI.

## 3. Switch a role to the new runtime

The role is what workers inherit from, so this is the switch that matters:

```bash
oc role show <roleId>
oc role set-runtime <roleId> opencode --reason "M5 demo"
oc role set-model <roleId> <model-id>        # or: default
oc role show <roleId>
```

Expected: the change is recorded as a role revision with your reason (`oc role show` lists
revisions), and it takes effect on the **next worker spawned from the role** — workers already
running finish on the runtime they started with.

To change what *new* roles in a project default to, edit the project. There is no
`oc project set-runtime`; use the API, the web app's Settings → Projects, or `workspace.yaml`:

```bash
curl -X PATCH -H 'content-type: application/json' -H "authorization: Bearer $OC_TOKEN" \
  -d '{"runtime":"opencode"}' https://oc.example.com/api/w/acme/projects/api
```

```yaml
# or in workspace.yaml, then restart the daemon
projects:
  - id: api
    runtime: opencode
```

The conductor is switched separately, and can live on a different runtime from every worker:

```bash
oc conductor set-runtime opencode
oc conductor set-model default
oc conductor reset-session       # a runtime switch is cleanest on a fresh session
```

## 4. Re-run the M2 demo

Run [`M2.md`](M2.md) steps 3–6 unchanged with the role on the new runtime. The whole flow must
behave identically:

```bash
oc say "in api, add a /ready endpoint. Plan it first."
oc worker list                   # runtime column shows the new runtime
oc attach <workerId>
oc decision answer <id> approve  # plan
oc decision answer <id> approve  # merge
oc ticket show ACME-<n>
```

What to watch for, because this is where runtime differences bite:

| Check | Why it can differ |
|---|---|
| The worker read its charter and brief | Only Claude gets `--append-system-prompt-file`; Codex, OpenCode and Gemini discover `AGENTS.md` / `GEMINI.md` at cwd (= the worker home). If the worker acts as if it has no brief, instruction discovery is broken. |
| It found the repo | The worktree is `work/` under cwd. The `openconductor-worker` skill tells non-Claude workers to read `work/AGENTS.md` first. |
| `oc runs show` shows `session.resumed` on turn 2 | Codex resumes by thread id, OpenCode by session id, Gemini by session id; Gemini cannot fork. |
| The structured final report parsed | Claude and Codex constrain output with a schema; OpenCode and Gemini need the report parsed out of the final text. |
| `oc usage --scope ticket:ACME-<n>` has real numbers | Usage reporting differs per CLI (`per_turn` vs `session_cumulative` vs none); cost may be labelled `estimated` rather than `reported`. |
| MCP tools were reachable | Each CLI is configured differently (`--mcp-config`, `-c mcp_servers…`, `.opencode/opencode.json`, `.gemini/settings.json`). If `oc_inbox` fails, that is the first thing to check. |

Record anything that differs in `docs/adr/`, per PLAN §8.3.

## 5. Two runtimes at once

Nothing forces a workspace onto one CLI. Hire a second role on the same project with a different
runtime and give each a ticket:

```bash
oc say "hire a second backend engineer for api, on codex, scoped to test and tooling work"
oc decision answer <id> approve
oc role list -p api
oc top
```

Expected: two live workers on the same project in separate worktrees, on different CLIs, with
separate config homes, both reporting into the same tickets and the same usage views.

## 6. The plugin surface

```bash
curl -s https://oc.example.com/api/openapi.json | jq '.info, (.paths | keys | length)'
curl -s https://oc.example.com/llms/api.txt | head -40
```

Expected: an OpenAPI 3.1 document and an agent-readable text summary, both generated from the same
route table, so they cannot drift from the API.

A plugin is an npm package or a relative path listed in `workspace.yaml`:

```yaml
plugins:
  - ./plugins/my-surface          # relative to the workspace directory
  - "@acme/oc-runtime-aider"
```

It default-exports `{ apiVersion: 1, id, version, register(host) }` and registers what it provides:
`host.registerRuntime`, `registerChannel`, `registerSurface`, `registerWorktreeProvider`,
`registerForge`, `registerHook`, `registerAgentTool`. Restart the daemon and check the log:

```bash
journalctl --user -u openconductor | grep -E 'plugin (registered|failed)'
oc presentation set workers.surface <your-surface-kind>
oc presenter
```

Expected: `plugin registered` with the id and version, the new surface accepted by
`oc presentation set`, and agents appearing wherever your adapter puts them. A plugin that throws,
has the wrong `apiVersion`, or exports no `register` is logged and skipped — it never takes the
daemon down. A plugin may not override a core invariant (checkout, approvals, budgets, the project
boundary).

## Acceptance checklist

- [ ] `oc runtime list` reports availability and versions for every installed CLI.
- [ ] `oc runtime login <id>` authenticates inside `<workspace>/.openconductor/runtimes/<id>/` and leaves your personal config untouched.
- [ ] `oc runtime models <id>` returns that runtime's models; `oc role set-model` accepts only those.
- [ ] The M2 flow passes with the role on `opencode`.
- [ ] The M2 flow passes with the role on `codex`. *(unverified live — expect to find bugs)*
- [ ] Two roles on the same project, on different runtimes, run concurrently.
- [ ] A surface plugin loaded from a local path places agents somewhere new.
- [ ] `/api/openapi.json` and `/llms/api.txt` describe the live route set.

## Not yet automated

- **Codex and Gemini are unverified against live accounts.** Everything is implemented and tested
  against recorded fixtures; treat a first live run as the test.
- **There is no `examples/` directory of sample plugins yet.** PLAN §22 M5 asks for sample runtime,
  channel and surface plugins; write yours against `packages/plugin-sdk` and the built-in adapters in
  `packages/surfaces/tmux` (the reference implementation).
- **Webhooks are configured but not dispatched.** `workspace.yaml` accepts a `webhooks:` array with
  URL, events and an `${ENV}` secret, and the durable event outbox exists, but nothing posts to them
  yet. Use the SSE stream (`GET /api/w/<ws>/events`) or an in-process hook plugin
  (`host.registerHook`) instead.
- **There is no `oc project set-runtime`.** Use the API, the web app, or `workspace.yaml`.
