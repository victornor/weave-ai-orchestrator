# M6 — Hardening: restart recovery, stuck workers, curation

Demonstrates PLAN §22 M6: a restart mid-work is a non-event, the stuck-worker ladder recovers without
losing anything, knowledge bases stay inside their budgets through agent-performed curation, and a
long soak leaves no lost wakes, orphan processes or orphan worktrees.

**Takes:** an afternoon, plus a 48-hour soak if you want the full acceptance criterion.
**Needs:** M2 passing, and enough tickets to keep several workers busy.

---

## 1. Restart with work in flight

Get three workers running, then reboot the daemon host (or just restart the service).

```bash
conductor top                                  # note the workers, their tickets and their run ids
conductor runs list -s running
systemctl --user restart agent-conductor.service     # or: reboot
```

After it comes back:

```bash
conductor daemon status
conductor runs list --limit 20
conductor worker list
conductor top
```

Expected:

- Every run whose process is gone is marked `interrupted` by boot recovery, **once**, on the first
  supervisor tick.
- Each interrupted run's wake is re-queued exactly once, so a fresh run starts for the same agent.
- Worker homes and worktrees are byte-for-byte where they were. **Nothing is ever reset** — no
  `git reset`, `clean`, `checkout` or `stash` is ever run in a worker's worktree.
- Sessions resume: `conductor runs show <newRunId>` opens with `session.resumed`, and the worker's turn
  prompt carries a "you were interrupted" note.
- Tickets are in the same statuses as before the restart; no decision was lost or duplicated.
- If you had a presenter running, `conductor presenter` recreates the windows on reconcile rather than
  duplicating them (handles are persisted per presenter and re-verified on start).

```bash
conductor briefing         # the four-section briefing; nothing should be listed as failed
```

## 2. A stuck worker, and the ladder

The supervisor ticks every 15 seconds. A worker is considered stuck when it produces no run events
for `defaults.silenceTimeoutSec` (600 by default) **and** its worktree has no file written inside
that window — write activity defers escalation, so a worker that is quietly compiling is left alone.

Force it. Shorten the timeout first so you are not waiting ten minutes:

```yaml
# workspace.yaml
defaults:
  silenceTimeoutSec: 60
```

Then wedge a running worker:

```bash
conductor runs list -s running
conductor runs show <runId> --json | jq '.pid, .pgid'
kill -STOP <pgid-or-pid>          # silent, alive, no worktree writes
```

Expected, in order:

1. The supervisor marks the worker stalled, sends SIGINT, waits, then kills the process group. The
   run ends `failed` with `error_family: tooling`.
2. **Relaunch**: the same worker, the same home, the same worktree, the same session where possible,
   plus a progress note derived from the ticket (last status, tasks ticked in `tasks.md`, dirty
   files, last commit). It finishes the ticket.
3. A second failure gets the same worker a **new session** with the bootstrap digest.
4. A third failure marks the worker `error`, the ticket `blocked` with `{ owner: conductor }`, and
   wakes the conductor with the evidence. The conductor may cancel and reassign; the replacement
   worker starts from the branch that already exists, never from scratch.

Watch it happen and drive it by hand where you want to:

```bash
conductor worker list -s error,paused
conductor runs list -s failed --limit 5
conductor worker relaunch <workerId> --note "picking up after the stall"
conductor worker cancel <workerId> --reason "reassigning"
conductor runs cancel <runId> --mode kill
```

Also confirm the **liveness** rule: no non-terminal ticket sits without an action path. `conductor briefing`
and the Needs-you view in the web app are the two places this surfaces.

Sessions also age out on their own: a session idle for longer than `defaults.sessionMaxIdleDays`
(14) is marked `stale` and the next turn starts a fresh one with the bootstrap digest, logged as
`session went stale; starting a new one`.

## 3. Knowledge curation

Curation is a scheduled, agent-performed rewrite of one knowledge file. Check the state first:

```bash
conductor knowledge lint
```

Expected: a row per file with its token estimate, budget, last curated date and whether curation is
pending. Budgets: `WORKSPACE.md` 3000, `SHARED.md` 800, `decisions.md` 1500, `PROJECT.md` 1500.

Fill a project KB past 80 % of its budget (a few merged tickets each leaving a learning will do it,
or add notes by hand):

```bash
conductor knowledge note project "Learnings" "2026-09-04 · exports stream through the queue; do not buffer" -p api
conductor knowledge show project -p api
conductor knowledge lint                 # curationPending flips to true past 80 %
```

A write that would take a file **over** budget is rejected with `budget_exceeded`
(`… would be N tokens over a budget of M; curation scheduled`) and schedules curation rather than
silently truncating.

Force a curation now:

```bash
conductor knowledge curate project -p api
conductor ticket list -p api -k task     # a "Curate project knowledge (api)" ticket appears
conductor worker list                    # a curation worker, spawned with noWorktree
conductor attach <workerId>
```

Expected: the curation worker runs from the project's default role on a fresh session with a
read-only checkout of the primary clone as `work/` for fact-checking. It merges duplicates, folds
learnings that became conventions into Conventions, removes entries stale or contradicted by the
repo, tightens wording, keeps every section inside its share of the budget, and **never adds facts**.
It submits with `ac_knowledge_replace`.

Then verify the guarantees:

```bash
conductor knowledge lint                       # at or under budget, lastCuratedAt updated
conductor knowledge revisions project -p api
conductor knowledge show project -p api
ls ~/work/acme/knowledge/projects/api/archive/     # every removed entry, with provenance
conductor knowledge revert project 7 -p api    # if you disagree with the rewrite
```

Workspace files are curated the same way, by the conductor in a dedicated turn:

```bash
conductor knowledge curate workspace
conductor knowledge curate shared
conductor knowledge curate decisions
```

## 4. The soak

Run two workspaces, three projects, four roles and up to twelve concurrent workers for 48 hours with
a steady trickle of tickets. Then check:

```bash
conductor runs list --limit 200 --json | jq '[.runs[].status] | group_by(.) | map({(.[0]): length}) | add'
conductor worker list --all
conductor worktree list
conductor top

# no orphan agent processes belonging to the daemon
pgrep -a -P 1 -f 'claude|codex|opencode|gemini'

# every worktree the daemon knows about still exists, and vice versa
git -C ~/work/acme/projects/api worktree list
```

Expected, per PLAN §22 M6:

- **No lost wakes.** Every wake is `completed`, `coalesced` or `skipped` **with a recorded reason** —
  none left `queued` or `claimed` behind a finished run.
- **No orphan processes.** Nothing spawned by the daemon is reparented to init.
- **No orphan worktrees.** `conductor worktree list` and `git worktree list` agree, and every worktree
  belongs to a live worker or is marked `dirty` pending a decision.
- **No liveness violations older than 5 minutes.** Every non-terminal ticket has an owner and an
  action path.
- **Usage reconciles.** `conductor usage --window all` totals match the sum of the runtime-reported totals in
  `conductor runs list`.

Useful during the soak:

```bash
conductor daemon logs -f                        # or: journalctl --user -u agent-conductor -f
conductor usage --window 24h --grain hour --series
conductor decision list                         # anything that has been waiting too long
```

## Acceptance checklist

- [ ] A restart with three workers running loses nothing: runs marked `interrupted`, wakes retried once, worktrees untouched, sessions resumed.
- [ ] A silenced worker is interrupted, killed and relaunched into the same home and worktree with a progress note, and finishes.
- [ ] A second failure gives the same worker a fresh session; a third blocks the ticket and wakes the conductor.
- [ ] A knowledge file past 80 % of budget is flagged; an over-budget write is refused with `budget_exceeded`.
- [ ] `conductor knowledge curate` spawns a curation worker that brings the file back under budget, archives every removed entry with provenance, and adds no facts.
- [ ] `conductor knowledge revert` restores a previous revision.
- [ ] A 48-hour soak shows no lost wakes, no orphan processes, no orphan worktrees, no stale liveness violations, and usage totals that reconcile.

## Not yet automated

Several M6 items from PLAN §22 are specified but not built. Say so rather than pretending the demo
covers them:

- **No scheduled curation.** Curation fires on the 80 %/over-budget triggers and on
  `conductor knowledge curate`, but the **14-day timer** is not in the supervisor loop. Run it on a cron/timer
  yourself if you want it periodic.
- **No routines (cron) engine.** There is no scheduled-work primitive; `timer` and `routine` exist as
  wake sources but nothing enqueues them on a schedule.
- **No hourly reconciliation against reality.** The supervisor does boot recovery, the silence
  watchdog, worker spawn and retirement, the auto-merge sweep, the liveness scan, decision expiry and
  the conductor digest — but it does not periodically `git fetch`, refresh PR state from the forge, or
  re-read OpenSpec state to repair drift. `conductor project fetch` does the fetch-and-reindex half on demand.
- **No age-based archive purge.** `conductor worker purge <id>` removes one worker's home and worktree;
  `defaults.workerArchiveDays` and `defaults.runLogRetentionDays` are accepted by the schema but
  nothing acts on them.
- **No `conductor workspace pause|resume`.** The endpoints exist (`POST /api/w/<ws>/pause` and `/resume`,
  which stop and start the dispatcher) but there is no CLI verb.
- **The `claude --bg` / `claude attach` interactive spike is not done.** `conductor attach` remains the only
  interactive view of a worker; there is no `interactive: true` role option and no ADR yet.
