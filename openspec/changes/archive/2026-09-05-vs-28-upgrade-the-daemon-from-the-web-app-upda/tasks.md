## 4. The upgrade record and its lifecycle

- [x] 4.1 Add an `UpgradeService` in `packages/server` that creates a record in `queued` (with requester, source, ref and resolved target sha), reads the latest record, and rejects a second request while one is non-terminal with `conflict`; verify with server tests asserting the created record's fields, that a second request while one is in flight is a conflict and creates no row, and that a request after a terminal record creates a new one.
- [x] 4.2 Make the service hold dispatch the moment a record exists — `dispatcher.stop()` on every loaded workspace — and resume it with the existing `undrain` rule (`dispatcher.start()` on every workspace whose row is not `paused`); verify with core/server tests using a fake runtime asserting that a run already executing when the upgrade is requested finishes uncancelled, that an agent woken while the upgrade is pending gets no run and keeps its queued wake, that resuming dispatches that wake, and that a workspace paused before the request stays paused after the resume.
- [x] 4.3 Implement the idle gate: the record moves `queued → waiting`, reports the runs it is waiting for, and moves to `building` only when every loaded workspace reports `dispatcher.running() === 0`, bounded by `upgrade.waitForIdleSec`; verify with tests asserting that the upgrade proceeds as soon as the last executing run finishes, that a request made with nothing running proceeds without waiting, that a `runs` row left `running` by an earlier process does **not** hold it, and that expiry fails the record with a timeout reason, resumes dispatch and creates or changes no release directory or symlink.
- [x] 4.4 Implement cancellation: `queued` and `waiting` records become `cancelled` and resume dispatch; `building` and later reject with `conflict` and leave the record untouched; verify with tests covering both paths and that a cancelled record leaves no pending upgrade behind.
- [x] 4.5 Implement the build stage: `buildRelease` from the recorded source and ref (with the optional test run), its output captured as a bounded tail of `UPGRADE_LOG_LINES = 200` on the record while it runs; a failure fails the record with the reason and that tail, resumes dispatch and leaves `current` untouched; verify with tests asserting a readable tail mid-build, and that a build failure leaves the record failed with the reason and tail, dispatch resumed, and the `current` symlink byte-identical to before.
- [x] 4.6 Implement the switch stage: back up the daemon database and every registered workspace database first (recording their paths on the record), then `switchRelease` and `pruneReleases(upgrade.keep)`; a backup failure fails the record before the symlink changes; verify with tests asserting the backups exist and are recorded before the symlink moved, and that an unwritable backup destination fails the upgrade with `current` unchanged and dispatch resumed.
- [x] 4.7 Implement the hand-off: the record moves to `restarting` with `toRelease`/`toSha` recorded, the runner is spawned detached, and the HTTP request that requested the upgrade has already been answered — the daemon does not terminate while answering it; verify with tests using an injected spawn seam asserting the record reaches `restarting` with the target recorded, that the spawn was requested with the new release's CLI bin and the record id, and that the request completed before the spawn.
- [x] 4.8 Implement startup reconciliation in `packages/server/src/daemon.ts`: a `restarting` record whose target is the release this process runs becomes `completed` with `cameBackVersion`; one that is not, older than the bounded interval, becomes `failed` with an unverified-restart reason; any non-terminal record before `restarting` becomes `failed`; verify with tests over a seeded `daemon.sqlite` covering all three cases and asserting the daemon dispatches normally afterwards in each.
