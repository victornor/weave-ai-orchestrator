## Context

- The secret store (`packages/core/src/secrets/index.ts`, `SecretsService`) already supports exactly this shape of write: `put(actor, {name, envVarName?, scope?}, value)` registers a name and stores the value encrypted on disk (`store.ts`), never in the database. `value()` is deliberately reachable from nowhere but the daemon's own internals (`index.ts:6-7`) — today only `roleSecretsEnv` (`packages/core/src/runs/engine.ts:94-104`) calls it, to build a *worker's* environment. There is no existing path from a secret to a *channel adapter*.
- `TelegramConfigSchema` (`packages/channels/telegram/src/config.ts:4-10`) requires `botToken` and `validateTelegramConfig` (`config.ts:25-34`) rejects an unresolved `${ENV_VAR}` reference. Resolution of `${ENV_VAR}` happens once, generically, when `workspace.yaml` is loaded (`packages/core/src/workspace/loader.ts:46-77`), and is written back as a reference (never a literal) by `saveConfig` (`loader.ts:253-259`).
- `ChannelManager` (`packages/server/src/channels.ts`) starts every configured channel kind exactly once, in `start()` (`channels.ts:49-75`), called once from `loadWorkspaceInto` (`packages/server/src/daemon.ts:195-197`). It has no restart primitive and does not subscribe to `workspace.updated`. `PATCH /config` (`packages/server/src/routes/workspace.ts:24-34`) merges a patch into `workspace.yaml` via `ctx.saveConfig` and emits `workspace.updated`, but nothing consumes that event to restart a channel — confirmed by reading every listener of `ctx.events` in `packages/server/src`.
- **Revision context:** Settings' existing "Allowlist" field (`Settings.tsx:539-547`) writes `channels.telegram.allowlist`; the schema and the adapter both read `allowedUserIds` (`config.ts:7`, `index.ts:107`) — the field the human fills in never reaches the channel. Separately, the adapter's gate is `if (allowed.size && !allowed.has(parsed.userId))` (`index.ts:193`): an *empty* `allowedUserIds` short-circuits the condition to `false`, so every user is admitted. These are two independent bugs that compound: Settings appears to let captain lock the bot down, and in every state it can actually reach today, it either does nothing (wrong key) or admits everyone (empty list). "Enabled" (`Settings.tsx:529-538`) is a third, unrelated dead field — `TelegramConfigSchema` has no `enabled` property at all, and `configuredKinds()` (`channels.ts:44-47`) starts a channel based solely on whether its key is present under `channels:`, never reading a value inside the block. Captain asked that `enabled` be reported, not fixed, here.
- `TelegramClient.getMe()` (`packages/channels/telegram/src/api.ts:137-139`) and `mapTelegramError` (`api.ts:11-36`, HTTP 401 → `PermanentChannelError(..., 'unauthorized')`) already exist and are unused outside tests — they are the validation call and error mapping this change needs.
- `WorkspaceRuntime.channels: ChannelManager | null` (`packages/server/src/types.ts:14`) is already reachable from any route handler via `c.get('ws').channels`.
- The password-change flow (`SecuritySection`, `packages/ui/src/routes/Settings.tsx:660-686`) is the one existing "local pending value → explicit save → clear-on-success → toast-with-server-message-on-failure, leave-input-on-failure" pattern in this codebase; it is the model for the new token field, not the auto-save-on-blur `patch.mutate` pattern the enabled/allowlist fields use, because auto-save can't show a masked "configured" state or block on upstream validation.

## Goals / Non-Goals

**Goals:**
- One new writer of the secret store (alongside the existing decision-card `secret` input): a workspace route that sets/clears the Telegram token, validating against `getMe` before committing.
- A resolver with an explicit precedence rule (secret store first, then a resolved `${ENV_VAR}`) that both `ChannelManager` and the status route use, so the rule is enforced in exactly one place.
- A minimal, generic "restart one channel kind" primitive on `ChannelManager`, exercised here only for `telegram`.
- Settings' allowlist field writes the field the channel reads, an empty allowlist stops meaning "everyone," and an already-open deployment does not go silently deaf when that default flips.

**Non-Goals:**
- Wiring up `enabled`. It is reported (Context, above) but not fixed: it is cleanly separable from both the token and the allowlist fix — nothing in either depends on `enabled`, and `configuredKinds()`'s "presence of the key means configured" behavior is an orthogonal question about whether a channel starts at all, not about who it accepts messages from once it has. Fixing it would mean deciding what "off" should do to a *running* channel with no analogous acceptance-criteria pressure forcing that design now; captain asked for it to be reported, not designed here.
- A generic "any channel can have a secret-backed field" mechanism. Only Telegram needs one today; a second channel needing this can generalize `resolveTelegramToken`'s shape then.
- Migrating an existing `${ENV_VAR}` deployment automatically. It keeps working untouched; moving to Settings is the human's choice.
- An interface control to deliberately opt a workspace into "open to all Telegram users." `allowAll` exists so an already-open deployment isn't silently muted (Decision 7); Settings only ever displays it (Decision 8's third state). Whether captain should be able to turn it *on* on purpose is a product question nobody has asked yet.

## Decisions

**1. A dedicated route, not `PATCH /config`.** `PATCH /config` merges its patch into `ctx.config` and persists the whole thing via `saveConfig` → `workspace.yaml` (`workspace.ts:29-33`, `loader.ts:253-259`). Anything that flowed through it would either have to be written into `workspace.yaml` in the clear (ruled out by criterion 3) or be filtered back out before every save (fragile, and a new special case in a generic merge path). Instead: `packages/server/src/routes/channels.ts` (new), mounted at `ws.route('/channels', channelRoutes())` in `app.ts`, giving `/api/w/:ws/channels/telegram/token`:
   - `POST /telegram/token` — body `{token: string}`. Calls `getMe` against the submitted token via a `TelegramClient` built with `{botToken: token}`; on success, registers it with `services.secrets.put(actor, {name: 'telegram-bot-token', envVarName: 'TELEGRAM_BOT_TOKEN', scope: 'workspace'}, token)`, then calls `ws.channels?.restartChannel('telegram')`, and returns `{ok: true, botUsername}`. On failure, throws `OcError('validation', <getMe's mapped message>, ...)` (mapped through the existing `mapTelegramError`) — nothing is written, nothing restarts.
   - `DELETE /telegram/token` — clears the stored value (a new `SecretsService.clear(actor, name)`, since today's `put`/`get`/`has`/`value`/`list` has no delete — see decision 4) and calls `restartChannel('telegram')`, which will now see no effective token and stop the channel.
   - `GET /telegram/token` — returns `{configured: boolean, source: 'secret' | 'env' | null, botUsername: string | null}` from the same resolver `ChannelManager` uses, never a value.
   All three use the fixed name `telegram-bot-token` — there is exactly one Telegram channel per workspace, so no per-instance naming is needed.

**2. Precedence resolver lives on `ChannelManager`, used by both the manager and the status route.** `resolveTelegramToken(): {token: string; source: 'secret'} | {token: string; source: 'env'} | {token: null; source: null}`:
   1. `services.secrets.value('telegram-bot-token')` — if non-null, `{token, source: 'secret'}`.
   2. else, the configured `channels.telegram.botToken` after the loader's `${ENV_VAR}` resolution, if it is non-empty and not itself an unresolved `${...}` reference (reuse the same regex `validateTelegramConfig` already applies) — `{token, source: 'env'}`.
   3. else `{token: null, source: null}`.
   One place enforces the rule; the spec's "which wins" requirement and the status route's "which source is in effect" requirement both read from it, so they cannot drift apart.

**3. `ChannelManager.restartChannel(kind)`.** New method: stop the running handle for `kind` if present (`this.running.get(kind)?.stop()`, then delete from `running`/`adapters`); then attempt to start it — for `telegram`, build the config passed to `adapter.validateConfig`/`adapter.start` as `{...this.ctx.config.channels['telegram'], botToken: resolved.token}` where `resolved` comes from decision 2; if `resolved.token` is null, leave it stopped (this is criterion 7 — "off because it has no token" — not an error). This reuses the existing per-kind adapter lookup and `ensureChannelRow`/`running`/`adapters` bookkeeping `start()` already has, factored so `start()` calls it too instead of duplicating the start logic (`start()`'s per-kind body becomes a call to a shared `startOne(kind)` helper that `restartChannel` also uses after stopping). `TelegramConfigSchema.botToken` changes from `z.string().min(1, ...)` to `z.string().min(1).optional()` so a workspace with the field absent entirely (fully secret-store-configured) still parses; the "no effective token" case is handled by `restartChannel` never calling `start` on the adapter at all, not by the schema accepting an empty string.

**4. `SecretsService` gains `clear(actor, name)`.** Nothing today deletes a registered secret (`index.ts`'s `put`/`list`/`has`/`value` — no delete). Adding `clear()` removes the DB row and the store's encrypted entry (`store.ts` needs a matching delete of the `name` entry from `secrets.enc`), and records `secret.cleared` activity with the name only — mirroring `put`'s "name and where it came from, never the value" activity shape (`index.ts:47`). This is a capability the store doesn't have yet, but it's a small, direct extension of its existing three operations (put/get/has-by-name against the same file), not a new mechanism.

**5. UI: a new field in `ChannelsSection`, modeled on `SecuritySection`'s password flow, not `patch.mutate`.** Local `useState` for the pending input; a masked `<input type="password">`; "Save" calls `api.ws(ws, '/channels/telegram/token', {method: 'POST', body: {token}})`, clears the input and shows a toast with the returned `botUsername` on success, shows a toast with `e.message` and leaves the input on failure (identical shape to `SecuritySection`'s `.then()/.catch()`, `Settings.tsx:670-682`). A status line above it, from `GET /telegram/token` (via a new `useTelegramTokenStatus()` hook, `useQuery` keyed off the workspace like `useWorkspaceSummary`), reads "Configured (@username)" / "Configured via ${ENV_VAR} in workspace.yaml" / "Not configured — channel is off" per the resolved `source`. "Clear" is a plain button calling `DELETE /telegram/token`, disabled when nothing is configured.

**6. The allowlist field writes `allowedUserIds` directly.** `ChannelsSection`'s allowlist `<input>` (`Settings.tsx:539-547`) changes its `patch.mutate` call from `{allowlist: [...]}` to `{allowedUserIds: [...]}` (parsed as integers — `TelegramConfigSchema.allowedUserIds` is `z.array(z.number().int())`, not strings; the current UI code sends strings from a comma-split, which happens to work today only because nothing downstream ever reads the field at all). This stays on the existing `PATCH /config`/`patch.mutate` path (unlike the token) because it is an ordinary config value with no secrecy or upstream-validation requirement — the same reasoning that already put "Enabled" and the old "Allowlist" there.

**7. `allowAll`, added to `TelegramConfigSchema` as `z.boolean().default(false)`, decides what an empty allowlist means — this is judgement call #1.** The problem: `allowedUserIds: []` means two different things depending on when a workspace was configured — "everyone" under the old gate, "nobody" under the new one — and the stored value cannot tell you which era it's from. Flipping the default outright risks exactly what was flagged: a workspace that has been running open goes silently deaf, with nothing but an unread `log.warn` (`index.ts:197`) to explain why. Leaving the default open, so nothing breaks, keeps every *new* configuration open too, which is precisely the trap this ticket exists to close.

   Resolution: don't try to infer "was this open on purpose" from the stored value at all — gate it on whether the workspace has ever been evaluated under the new rule. A `meta` row (`telegram_allowlist_migrated`, mirroring the `meta`-table pattern the VS-77 model-settings migration already uses at `loader.ts:213-226`, sibling code in the same function) is checked once per workspace, at load. If the row is absent, evaluate the *raw* `channels.telegram` block as read from `workspace.yaml`, before Zod fills in any default:

   - **The `allowlist`/`allowedUserIds` key must never have been set at all — not even to `[]`.** An empty array the human put there themselves through Settings is evidence they went looking for a way to restrict the bot, not evidence of nothing. (Caught against this exact workspace's own config, `channels.telegram: {enabled: true, allowlist: []}` — the naive "no `allowAll`, no ids" check would have grandfathered it to `allowAll: true` the moment a token was first saved, opening it to every Telegram user, on the one workspace the fix exists to protect.) Where the raw `allowlist` array does hold entries, they are migrated into `allowedUserIds` rather than discarded — a human who typed ids in gets the restriction they asked for. Each entry is parsed with `Number()`; a non-finite or non-integer result is dropped and logged (`log.warn({dropped, kept}, 'telegram allowlist: entries that were not valid ids were dropped during migration')`) rather than blocking the migration or being kept as garbage — the same rule the Settings input applies going forward (Decision 6).
   - **A token must actually resolve, right now, for this workspace.** Grandfathering exists to protect a deployment that is accepting messages today; a workspace with no secret-store value and no resolved (non-`${ENV_VAR}`) `botToken` has never accepted a single message under any allowlist rule, so there is nothing to protect and no reason to open it. Checked via `createSecretStore(paths).get('telegram-bot-token')` (constructed directly — this runs before `services.secrets` exists; the store needs only `paths`, per `store.ts`) and the already-`${ENV_VAR}`-resolved `config.channels.telegram.botToken`, same non-empty/not-still-`${...}` check the precedence resolver (Decision 2) uses.

   Only when *both* hold — the allowlist key was truly never touched, and a token resolves — is `allowAll: true` written into `workspace.yaml` once (same `writeYamlFile`/`unresolveEnvRefs` path `saveConfig` uses). The `meta` row is inserted in every case (grandfathered, migrated-ids-only, or neither), so this workspace is never evaluated by this check again — including after it later configures Telegram for the very first time with the row already present, which must default to closed, not open.

   This specifically avoids a simpler-looking alternative I rejected and then had to walk back: gating on "`channels.telegram` present, no `allowAll` key, no ids" alone. That check reads as true forever for any brand-new configuration too — the very first time captain flips "Enabled" on a workspace that has never touched Telegram before, `channels.telegram` becomes present with neither key set, indistinguishable from a workspace that has been running open for months, *and* it does not require a working token, so it would grandfather a channel that was never actually reachable. The `meta` row turns "what does empty mean" from a value-shaped question into a time-shaped one; the token-resolves and key-was-truly-unset conditions turn "was this workspace exposed" from an assumption into a checked fact.

   Result: an already-open, already-reachable deployment keeps working, unattended, through the upgrade (no deafness). A deployment that already went to the trouble of setting an allowlist — even an empty one — keeps meaning what the human set it to mean, restricted, not opened. Every other configuration defaults closed. And per Decision 8, `allowAll: true` is never indistinguishable from "empty" in the interface — the grandfathered case is exactly as visible as if captain had set it on purpose.

**8. The adapter's gate becomes: non-empty list restricts to it regardless of `allowAll`; empty list admits everyone only if `allowAll` is true, otherwise nobody.** In `index.ts`, `const allowed = new Set(cfg.allowedUserIds)` gains a sibling `openToAll = cfg.allowAll && allowed.size === 0`, and the `handleUpdate` gate (`index.ts:193`) becomes `if (allowed.size ? !allowed.has(parsed.userId) : !openToAll)`. A populated list is never treated as "open" regardless of `allowAll` — `allowAll` only has meaning when the list is empty, matching the only two states the old code could ever produce (empty-and-open, or populated-and-restricted). This is also **judgement call #2's answer restated as behavior**: `enabled` is not read here or anywhere in this decision; whether the channel *runs at all* stays exactly as inert as Context describes, unchanged by this ticket.

**9. Settings shows one of three states, computed client-side from `allowedUserIds.length` and `allowAll`, no new route needed.** "Locked to N users" (list non-empty) / "Open to any Telegram user" (list empty, `allowAll` true) / "Off — no user is allowed" (list empty, `allowAll` false or absent). This reads off the same `config.channels.telegram` the section already has via `useWorkspaceSummary` (`Settings.tsx:521-524`); no new endpoint, since none of this is secret.

## Risks / Trade-offs

- **[Risk] `restartChannel` stopping and restarting mid-poll could race with `ChannelManager.drain()` reading `this.adapters`/`this.running` for outbound delivery.** → Mitigation: `restartChannel` removes the kind from both maps before awaiting the adapter's `stop()`, the same order `stop()` already uses; `drain()`'s `pending()` query is keyed by row, not by a live handle reference, so an outbound row for a kind mid-restart is retried on the next sweep exactly as it already is when an adapter's `send()` fails — no new failure mode, only a slightly longer window where sends for that kind fail and retry.
- **[Risk] A route calling `getMe` against an attacker-supplied `apiBaseUrl` override could be used for SSRF.** → Mitigation: token validation uses the channel's already-configured `apiBaseUrl` (if any) exactly as the running adapter would, never a URL from the request body; the route accepts only `{token}`.
- **[Trade-off] The fixed secret name `telegram-bot-token` means only one Telegram bot token per workspace can ever be stored this way.** Matches today's one-Telegram-channel-per-workspace reality (`configuredKinds()` is a `Set` of kind strings, not instances); revisit if multi-bot-per-workspace is ever needed.
- **[Risk] The `allowedUserIds` type mismatch (Decision 6): the current UI sends strings, the schema wants integers.** Today this is invisible because nothing reads the field; once the channel reads it, a string in the array would fail `TelegramConfigSchema.safeParse` and the channel would fail to start with a config-rejected error, which is at least loud rather than silently broken — but the UI change must parse to numbers to avoid hitting it at all. → Mitigation: task list requires the Settings input to `Number()`-parse and filter non-numeric entries before sending, with a test.
- **[Risk] The one-time migration runs inside `loadWorkspaceInto`, alongside the VS-77 model-settings migration and other startup work (`daemon.ts:170-204`).** A bug in it could make workspace loading throw, which is a bigger blast radius than the allowlist bug it fixes. → Mitigation: same pattern as the existing migration (read-modify-write against already-parsed/validated config, wrapped in the same error handling the surrounding loader code has); unit tests load fixture workspaces covering the full matrix — no `channels.telegram` block; block present with no allowlist key and a resolvable token (grandfather); block present with no allowlist key and *no* resolvable token (do not grandfather — never reachable); block present with `allowlist: []` and a resolvable token (do not grandfather, matches this workspace's own shape verbatim per the conductor's finding); block present with populated `allowlist` ids and a resolvable token (migrate ids to `allowedUserIds`, do not grandfather) — plus a second load of each proving idempotency.

## Migration Plan

`TelegramConfigSchema.botToken` becoming optional is backward compatible with every existing `workspace.yaml`. A workspace already running on a resolved `${ENV_VAR}` token keeps working via the precedence resolver's second branch without any action from captain.

The allowlist default change is a real, one-time data migration (Decision 7): on first load under this change, a workspace that was both never touched by an allowlist edit (not even to `[]`) *and* already had a resolvable token — meaning it was actually accepting messages from anyone — gets `allowAll: true` written into `workspace.yaml` once, gated by a `meta` row so it never re-runs. A workspace whose allowlist was ever touched gets its ids (if any) migrated into `allowedUserIds` instead. Rollback: reverting the code leaves `allowAll: true` sitting unused in `workspace.yaml` (schema-optional, ignored by the old code) and the gate reverts to the old "empty means everyone" behavior for everyone — including workspaces that migrated to a restricted, non-empty `allowedUserIds` (the old code reads that field too, so a populated list still restricts correctly after rollback) and workspaces that started fresh under the new default with a genuinely empty allowlist, which would revert to open. That second case is a real rollback risk worth stating plainly rather than glossing over: rolling back this change after new workspaces have configured Telegram under the closed default would silently open them. Out of scope to solve here (a rollback is an operational decision, not a shipped behavior), but noted for whoever runs one.
