## Context

VS-355's scout report (read via `weave_ticket_document_get(VS-355, "report")`) already did the file-by-file investigation this design builds on; citations below point at the same lines. Today, `KnowledgeService.write()` (`packages/core/src/knowledge/service.ts:223-267`) is the only writer of any knowledge file, always against `<workspaceRoot>/knowledge/**` (`ctx.paths.knowledge`, `packages/core/src/context.ts:57`) — never a project's own repo (`<workspaceRoot>/projects/<id>/**`, a sibling directory). `openspec.enabled` (`packages/shared/src/config.ts:91`) is the existing precedent for a per-project boolean flag: a dedicated `projects.openspec_enabled` column (`packages/db/src/migrations/0001_init.sql:16`), read as `project.openspecEnabled` (`packages/shared/src/types.ts:5`), set in `createRow`/`update`/`configFor` (`packages/core/src/projects/index.ts:156,175,335`).

`mergeDone` (`packages/core/src/tickets/service.ts:1113`) already runs a per-project critical section (`serialize(project.id, ...)`, line 1138) that ends with `landDelivery` (`packages/core/src/tickets/land.ts:129`) leaving `project.clonePath` checked out at the new landing tip, for both `local-branch` (fast-forward) and `pr` (fetch + verify-contained) delivery modes. `archive-before-merge.ts` already has the scratch-worktree primitives (`scratchLandWorktree`, `scratchBranchFrom`, `rebaseOntoLanding`) that OpenSpec archive backfill (`packages/core/src/openspec/index.ts:183-240`) uses to commit onto a fresh branch and open a PR with `ForgeAdapter.createPullRequest` — including the "check for an existing branch/PR before opening a second one" pattern (`openspec/index.ts:193-212`) this design reuses.

`spawnCurator` (`packages/core/src/workers/index.ts:259-269`) always spawns with `{ noWorktree: true }`; `spawn()` (`workers/index.ts:102-186`) already knows how to give an agent a worktree and branch when `noWorktree` is false, and does the checkout via the project's registered `WorktreeProvider` — nothing there is curation-specific.

The knowledge tool handlers (`packages/server/src/tools.ts:544-587`) call straight into `KnowledgeService`; `ToolCtx` (`tools.ts:34-37`) carries `claims` (workspace/agent/project ids) and `actor`, and `svc(ctx).workers.get(ctx.claims.agentId)` (used at `tools.ts:1007-1008` for `weave_worktree_status`) is how a handler learns an agent's `worktreePath`.

## Goals / Non-Goals

**Goals:**
- An opted-in project's worker, curation and weaver knowledge writes all eventually reach `.weave/knowledge/` in that project's repo, through the same review path their other changes already use.
- The workspace's own knowledge store stays the one thing every existing feature (search, budgets, curation, links, health, bootstrap digests) reads, unmodified.
- The path-prefix boundary is a single, tested enforcement point, not convention.

**Non-Goals:**
- Migrating an existing project's knowledge into or out of the repo when the flag is flipped (follow-up ticket, per the ticket's Out of scope).
- Any repo-visibility (public/private) signal or warning (follow-up ticket).
- Committing artifacts as files.
- Changing anything about an opted-out project.

## Decisions

### 1. `knowledgeRepo.enabled` follows `openspec.enabled`'s exact shape

Add `knowledgeRepo: z.object({ enabled: z.boolean().default(false) }).default({ enabled: false })` to `ProjectConfigSchema` (`packages/shared/src/config.ts:91`, next to `openspec`), and a `knowledge_repo_enabled INTEGER NOT NULL DEFAULT 0` column on `projects` (new migration `0036_project_knowledge_repo.sql`, following `0001_init.sql:16`'s `openspec_enabled` column). `packages/db/src/repos.ts`'s `projectRow` gains `knowledgeRepoEnabled: bool(r.knowledgeRepoEnabled)`, and `packages/shared/src/types.ts`'s `Project` gains the field. `createRow`, `update` and `configFor` (`packages/core/src/projects/index.ts:156,175,335`) read/write it exactly where they already read/write `openspecEnabled`. Default `false` on both the schema and the column means an existing project, and a project declared with no `knowledgeRepo` block, is unaffected — this is what the opt-in capability's "off is unchanged" requirement rests on.

**Alternative considered:** nest it under `ProjectPoliciesSchema` instead of a dedicated column, since policies are already a JSON blob needing no migration. Rejected: `openspecEnabled` is a first-class column precisely because code branches on it in hot paths (`workers/index.ts:150`, `mergeDone`); this flag is checked in the same kind of hot path (every knowledge write, every `mergeDone`), so it gets the same treatment for the same reason.

### 2. The secret check moves to a shared helper `files.ts` exports

`putDoc`'s regex (`service.ts:614`) becomes a named export, e.g. `SECRET_SHAPED_RE`, in `files.ts` (alongside `EXPIRY_RE` and the other pattern constants). `note()` (`service.ts:369`) tests `trimmed` against it right after the 60-word check and before the near-duplicate check, throwing the same `validation` `OcError` `putDoc` throws. This is a plain, unconditional addition — no opt-in check — matching the ticket's "applies to every project."

### 3. A single mirror-write, threaded through `write()` — computed against the worktree's own copy, never the workspace body

**Revised after plan review (2026-09-13):** the first version of this decision mirrored `write()`'s own `body`/`next` — the new *workspace* content — straight into the worktree. That is wrong: `note()`'s `body` is read from the *current workspace* file (`service.ts:376`), which by the time ticket B calls it may already carry ticket A's or a weaver PR's own unmerged note on the same hub (nothing stops two tickets writing the same project's hub concurrently — the workspace copy is shared and updates live). Mirroring that combined body into B's worktree would commit A's unreviewed note as part of B's diff, and B's PR would carry content nobody but A wrote.

The fix: `mirror` carries the content to write, computed by the **caller** against the worktree's *own* current copy of the file, never against the workspace body:

- `note()` (`service.ts:369`) already computes `entry` (the one `- ${today} · ${bare}` line) before appending it to the workspace body. When `mirror` is requested, it separately reads the worktree's own current mirror file — `readMirrorFile(worktreePath, repoRelPath)`, new in `files.ts`, returning the file's content or, if the worktree has no such file yet (a first write since the project opted in, before any backfill), a fresh `seedBody`/`''` — and computes `mirrorNext = appendEntry(doc ? mirrorFileBody : mirrorFileBody, section, entry)` against *that*, not against the workspace's `body`. Only `entry` — this call's own contribution — ever crosses from the workspace side to the mirror; the rest of the mirrored file is whatever was already on disk in the worktree (the landing version plus this ticket's own earlier writes).
- `putDoc()` and `replace()` are different in kind: their caller already supplies the complete target body directly (`text`/`body`), not derived from ambient workspace state the way `note()`'s append is. Mirroring that same caller-supplied value carries no risk of smuggling another ticket's content, because it was never read from the shared workspace copy in the first place.

`write()` itself (`service.ts:223`) takes the now-fully-computed `mirror: { worktreePath: string; projectSlug: string; body: string } | undefined` and only does the mechanical part: `repoKnowledgePath(row.path, mirror.projectSlug)` (`files.ts`, new — requires `row.path` to start with `projects/${projectSlug}/`, throws `OcError('internal', ...)` otherwise; this is requirement `repo-write-boundary`'s single enforcement point) then `mkdirSync` + `writeFileSync(mirror.body)` at `join(worktreePath, '.weave', 'knowledge', repoRelPath)`. `write()` never decides *what* to mirror, only *whether* and *where*.

`packages/server/src/tools.ts`'s three handlers build the `{ worktreePath, projectSlug }` half (via `svc(ctx).workers.get`/`svc(ctx).projects.get`, gated on `ctx.claims.agentKind === 'worker'`, scope `'project'`, the agent's own opted-in project, and a real worktree — unchanged from before); `note`/`putDoc`/`replace` build the `body` half as described above.

#### Test

Two tickets (two worktrees, sharing the same opted-in project) each call `weave_knowledge_note` on the project hub. Assert: each worktree's mirrored `PROJECT.md` contains the landing content plus *only that ticket's own* entry — neither worktree's file contains the other's.

**Alternative considered:** do the mirror write in `tools.ts` itself, after calling the existing `note`/`putDoc`/`replace`, re-reading the body with `knowledge.get`/`getDoc`. Rejected both before (duplicates the path-prefix guard, untestable from `core`) and now (that re-read is exactly the workspace body this revision is removing from the mirror path).

### 4. Curation gets a worktree exactly when the project is opted in

`spawnCurator` (`workers/index.ts:259-269`) changes one line: `noWorktree: !project.knowledgeRepoEnabled` instead of the unconditional `true`. Nothing else about curation changes — it is already an ordinary `task` ticket (`workers/index.ts:263-267`) assigned to the project's active role, so once it has a worktree and branch, the existing worker delivery flow (PR or local-branch, per the project's `deliveryMode`) applies with no new code, and `weave_knowledge_replace`'s handler mirrors into that worktree under Decision 3 like any other project write.

### 5. The weaver's out-of-ticket write gets a fire-and-forget commit-and-PR job

A weaver write with no ticket behind it (`actor.runId` resolves to a run with no `ticketId` — the same lookup `write()` already does for provenance, `service.ts:236`) to an opted-in project is not turned into a synchronous git/network operation inside `note`/`putDoc`/`replace`: those calls stay synchronous and their effect on the workspace's own knowledge store is immediate, exactly as `requestCuration`'s callers already expect the DB write to be visible before the async part runs. After that same condition is met, the write fires `fireKnowledgeRepoPr`, mirroring `fireCuration`'s existing fire-and-forget shape (`service.ts:317-319,390,397`).

`requestKnowledgeRepoPr` (new, `packages/core/src/knowledge/repoDelivery.ts`) reuses `archive-before-merge.ts`'s primitives and the "check for an existing branch or PR before opening a second one" pattern already proven in `openspec/index.ts:193-212`, with a fixed branch name per project (`ac/knowledge-<projectSlug>`) — but **revised after plan review (2026-09-13)**: the first version always branched fresh from the landing tip with `scratchBranchFrom`, so a second out-of-ticket write before the first PR merged would recreate the branch from `HEAD` and push over the first commit, losing it (`git push` to a branch whose remote history the local branch does not contain would itself fail non-fast-forward without `--force`, and forcing it is exactly the data loss the review flagged). The corrected sequence:

1. `git ls-remote --exit-code --heads origin ac/knowledge-<projectSlug>` (as `openspec/index.ts:193` already does for archive backfill).
2. **Branch exists:** check it out with `scratchLandWorktree` (checks out an *existing* branch, unlike `scratchBranchFrom`, which always creates a new one), fetch and rebase it onto the current landing tip with `rebaseOntoLanding` if it has fallen behind, then add this write's file change as a new commit on top of whatever is already there.
3. **Branch does not exist:** `scratchBranchFrom` from the landing tip, exactly as before, for the first out-of-ticket write.
4. Push with `--force-with-lease` (safe: this scratch worktree, like `attemptArchiveThenMerge`'s, is the only writer of this branch) and open the PR only if one is not already found via `forge.pullRequestForBranch`/the existing-PR check; otherwise the push alone updates the open PR's diff.

**Corrected after a third plan review (2026-09-13), two more findings:**

1. **The committed content still leaked another ticket's unmerged note.** The first version passed `fireKnowledgeRepoPr` the same workspace `body` Decision 3 had just stopped using for the worktree mirror — the identical leak, just on the out-of-ticket path: `note()`'s `body` is the *shared* workspace file, which by the time an out-of-ticket weaver write runs may already carry a different ticket's own still-unmerged note on the same hub, and the weaver's PR would then commit that unreviewed entry into the repo — landing it twice (once through the weaver's PR, once through the ticket's own PR later) as a duplicate or a conflict. `write()` now takes an additional optional `repoBody?: (current: string) => string`, defaulting to `() => body` (correct for `putDoc`/`replace`, whose content was never derived from ambient workspace state); `note()` passes its own `applyEntry` closure — the *same* closure Decision 3's mirror already uses, just handed to `fireKnowledgeRepoPr` instead of read against a worktree — so `requestKnowledgeRepoPr` computes the commit against the branch's own current file (via `readMirrorFile` against the scratch checkout), never the workspace body.
2. **Concurrent out-of-ticket writes could race and silently lose one.** `requestKnowledgeRepoPr` is fire-and-forget with nothing awaiting it, so two weaver writes in one turn (or a weaver write racing curation) could both see no remote branch and both push, or both take the existing-branch path and collide on `--force-with-lease` — the loser only logs a warning, so the write silently never reaches the repo. A dedicated `createSerializer()` instance (`packages/core/src/util/serialize.ts`, the same primitive `landLock` is one instance of) keyed by project id now wraps the whole function, so concurrent writes for one project run one at a time and each sees the previous one's already-pushed branch. Deliberately not `landLock` itself: that lock is the ticket-landing critical section, and a knowledge PR must never queue behind, or block, a merge.

Each write's mirror-safety otherwise follows Decision 3's principle: the file committed is `repoKnowledgePath`-validated content the *caller* computed, never re-derived from whatever else happens to be on the branch — a second write to a *different* file lands as an independent commit alongside the first, and a second write to the *same* file (e.g. two "Current focus" edits before the PR merges) simply becomes this call's new content committed on top, which is the correct "last edit wins" semantics for a single writer (the weaver) editing its own pending PR.

#### Tests

- Two out-of-ticket weaver writes to different files in the same opted-in project, before either PR merges: assert one PR exists carrying both files' commits, neither commit lost.
- Ticket A notes the hub and does not land; the weaver notes the same hub out of ticket. The weaver's PR branch file contains only the landing content plus the weaver's own entry, not A's.
- Two out-of-ticket writes fired without awaiting between them (a `Promise.all`, no serialization from the caller): both commits land on the one branch and PR, neither lost.
- `computeBody` receives the branch's own current file content, not a value pre-mixed with anything else — proven directly, not only inferred from the end-to-end outcome.

**Alternative considered:** make the out-of-ticket write itself async and block until the PR is open. Rejected: it would make an ordinary weaver `note()` call latency- and network-dependent, and a forge outage would then block a knowledge write the workspace-side store has no reason to reject.

### 6. Merge-time reconciliation is diff-scoped and merges, never overwrites the whole tree

**Revised after plan review (2026-09-13):** the first version walked the *entire* `.weave/knowledge/**` tree on every landing and overwrote or deleted any workspace file that differed from the repo. That silently reverts or deletes live, unmerged work the workspace copy is the only home for: ticket A's note that has not merged yet, or a weaver's out-of-ticket edit whose PR is still open, both live in the workspace copy today (by design — Decisions 3/5 keep it immediate) but are absent from what *this* landing's repo state shows, so a naive overwrite-to-match-repo would erase them the moment an *unrelated* ticket B lands.

The corrected `reconcileProjectKnowledgeFromRepo(ctx, deps, project, beforeSha, afterSha, landingTicketId)` (`packages/core/src/knowledge/repoSync.ts`), called immediately after `landDelivery(...)` succeeds inside `serialize(project.id, ...)` (`tickets/service.ts:1138-1207`, right after line 1206) with `landingTicketId` set to `t.id`, does two things differently:

1. **Scoped to what actually landed.** `beforeSha` is `project.clonePath`'s `HEAD` on the landing branch, read *inside* `serialize(project.id, ...)`, immediately before the call to `landDelivery(...)` — **corrected after a second plan review (2026-09-13)**: an earlier draft of this step read it before `serialize(...)` was even called. Two tickets for the same project can both reach `mergeDone` and queue on the same lock; if `beforeSha` were captured before acquiring it, a ticket that waited on the lock while a different ticket for the same project landed first would compute its diff from a `beforeSha` that is now stale, and its diff would include that other ticket's knowledge changes too — not corrupting data (the merge in point 2 is idempotent against re-seeing an entry already present), but scoping the diff to more than this landing actually changed, which is exactly what this point exists to avoid. Captured inside the lock, `beforeSha` is always this landing's own true starting point. `afterSha` is the same read *after* `landDelivery` returns, still inside the lock. `git diff --name-status beforeSha afterSha -- .weave/knowledge/` lists exactly the paths this landing changed. A landing that never touched `.weave/knowledge/` (the common case — most tickets are not knowledge tickets) does no reconciliation work at all, and, just as importantly, an unrelated ticket's landing can never touch a knowledge file it did not itself change — closing the exact hole plan review found.
2. **Merges instead of overwriting, for each changed path:**
   - **The hub file** (and any other entry/section-shaped file `entriesOf`/`appendEntry` already model): compute `base` = that file's content at `beforeSha`, `landed` = its content at `afterSha`, `workspace` = the current workspace copy. The reconciled result is `workspace`'s current entries, plus any entry present in `landed` but not in `base` and not already in `workspace` (content this landing actually added, folded in — normally a no-op since the live write already put it there, but this is also what correctly picks up a resolved merge conflict's final text), minus any entry present in `base` but removed in `landed` (a deletion this landing made, e.g. curation archiving something, applied even though the workspace copy still shows it). An entry that is in `workspace` but in neither `base` nor `landed` — another ticket's still-unmerged note, or a still-open weaver PR's edit — is **kept**, untouched, because it is in `workspace` and nothing in this landing's diff says to remove it. This is the same three-way-merge shape `git` itself would apply, expressed at `entriesOf`'s entry granularity instead of the line granularity a text merge would use, since a knowledge hub's *unit of change* is a dated bullet, not a line.
   - **A linked document** (`isDocPath`, always a full-body `putDoc` replace, with no append/entry model to merge at): apply `landed` as the workspace copy's new body, or remove it if this diff deleted it, only when `safeToApply(workspaceRel)` says so. **Corrected after a third plan review (2026-09-13):** the first version compared `knowledge_revisions.created_at` against `git show -s --format=%aI afterSha` — the landing commit's own author date. This repo squash-merges, so every landing is exactly one commit whose author date *is* the merge time; that comparison could never distinguish "the landing ticket's own edit" from "an unrelated concurrent edit that happened to land a moment earlier or later," and would have applied a stale landed body over a genuinely newer concurrent write. The corrected `safeToApply` is anchored on the workspace's own revision history instead of any commit date, using `landingTicketId`:
     - No workspace row for this path yet (a document that never reached the workspace at all) — nothing to clobber; always safe.
     - The landing ticket has its own revision of this path (`knowledge_revisions.ticket_id = landingTicketId`): safe exactly when no *later* revision (`revision >` the ticket's own, by a different ticket or by none) exists. Revisions are a strictly increasing counter per file, so "later" needs no timestamp comparison at all.
     - The landing ticket has no revision of this path (it changed the file by hand in git — a resolved conflict, a direct edit — never through a knowledge tool call): there is no ticket-authored baseline to compare against, so this is left alone and logged rather than guessed at.

Each changed write records a new revision with reason `'merge-sync'` (added to `KNOWLEDGE_REVISION_REASONS`, `packages/shared/src/enums.ts:205`) and the system actor, through the existing `knowledge.replace()`/`putDoc()`/`deleteDoc()` methods — reconciliation is a caller of those, not a new write path, so indexing and search pick it up exactly as any other write does.

This still runs synchronously inside `mergeDone`'s existing per-project critical section, not deferred like the spec reindex `schedule(100, ...)` a few lines below it (`tickets/service.ts:1257`): it is local filesystem and DB comparison only (the clone is already on disk and current, `beforeSha`/`afterSha` are already-resolved local refs — no network call), the diff scoping from point 1 above means the common case (no knowledge change in this landing) is a single cheap `git diff --name-status` with nothing further to do, and running inside the `serialize()` section that already holds this project's landing lock avoids reopening the race a second, separate critical section would. The spec reindex stays deferred because it shells out to `openspec` and reparses a potentially large spec tree unconditionally; this does neither.

#### Tests

- Ticket A notes the hub and does not merge; ticket B (an unrelated change) lands. Assert A's note is still present in the workspace copy after B's landing, and B's landing's own reconciliation reported no change to the hub (A's note was never in the diff `beforeSha..afterSha` of B's own landing).
- A weaver's out-of-ticket PR is open with an edit to a document; an unrelated ticket lands. Assert the pending edit's workspace-side content survives.
- A ticket's own landing legitimately changed the hub (added and removed entries); assert the workspace copy reflects exactly that landed add/remove, without disturbing an unrelated entry another ticket added to the workspace copy in the meantime.
- Two tickets for the same opted-in project both reach `mergeDone` and queue on the project's landing lock, each changing a different knowledge file. Assert each landing's own reconciliation diff contains only its own changed path, never the other queued ticket's.
- Ticket A's own revision of a document is what lands; before reconciliation runs, a different (or no) ticket writes a newer revision of the same document to the workspace — the landing must not overwrite it, even though the landing commit's own author date (a squash merge's timestamp) would read as later than that concurrent write.
- The landing ticket's own revision of a document is deleted and lands; reconciliation removes it from the workspace copy, since nothing newer exists.
- The landing ticket has no revision at all for a changed document (a hand-edited file); reconciliation leaves the workspace copy alone and logs why.

**Alternative considered:** a supervisor-pumped deferred reconciliation, like the spec reindex. Rejected for the reasons above, and because a worker calling `weave_ticket_merge_done` benefits from knowing, the instant that call returns, that the workspace copy already reflects what it just landed — a deferred pump would leave a window where a differently-behaving read is possible with no signal that it is stale.

### 7. The boundary guard is one function, exercised from both directions

`repoKnowledgePath(rel, projectSlug)` (Decision 3) and its inverse used by reconciliation (Decision 6) are the two, and only two, places a path crosses between the workspace's knowledge tree and a project's repo. Neither can be reached with a workspace-scope (`workspace/**`) path or another project's slug: `repoKnowledgePath` throws before Decision 3's mirror write for any input that is not `projects/<projectSlug>/**`, and Decision 6's reconciliation is only ever invoked with one specific `project` and only ever computes destinations of the form `knowledge/projects/<thatProject.slug>/**` — there is no code path in either direction that takes an arbitrary caller-supplied scope. `knowledge-repo/repo-write-boundary`'s tests exercise `repoKnowledgePath` directly (a workspace-scope path, a shared-scope path, the decisions log, a foreign project's path — each rejected) rather than only asserting the end-to-end behavior, so the guard's own logic is what is tested, not just its callers' current care.

## Risks / Trade-offs

- **A worktree mirror write fails after the workspace write already succeeded** (disk full, permission) → the tool call still reports the workspace write's success (its documented contract), the mirror failure is logged, and the discrepancy is visible to the worker as an unexpected `git status` before it delivers — no silent data loss, since the workspace copy (the source every reader uses until the ticket merges) is unaffected.
- **A concurrent ticket's or weaver PR's unmerged knowledge write could be reverted or deleted by an unrelated landing** → mitigated by Decision 6's diff-scoped, merge-not-overwrite reconciliation: a landing only ever touches the knowledge paths its own diff changed, and even for those, an entry present in the workspace but absent from both the pre- and post-landing repo state is kept, not clobbered. Covered by the three tests listed under Decision 6.
- **A worker's git-committed knowledge file, or an out-of-ticket weaver PR, could carry another ticket's unreviewed content** → mitigated by Decision 3's and Decision 5's revisions: both the worktree mirror and the out-of-ticket PR commit content computed against their own current copy of the file (the worktree, or the scratch branch) plus this call's own delta, never against the shared workspace body. Covered by the tests listed under Decisions 3 and 5.
- **A second out-of-ticket weaver write could overwrite the first, unmerged one on the shared `ac/knowledge-<slug>` branch, or two concurrent writes could race and silently lose one** → mitigated by Decision 5's revisions: an existing branch is rebased and committed onto, never recreated from the landing tip, and a dedicated per-project serializer (not `landLock`) makes concurrent writes for one project run one at a time. Covered by the tests listed under Decision 5.
- **A linked document's merge-time reconciliation has no sub-file merge unit** (unlike the hub's entries) → accepted, scoped limitation stated in Decision 6: a guard anchored on the workspace's own revision history and `knowledge_revisions.ticket_id` (never a commit date, which a squash-merging repo makes indistinguishable from the merge time) skips overwriting a document a concurrent, non-landing-ticket write has since touched, rather than attempting a merge a full-body replace has no smaller unit for.
- **`note`/`putDoc`/`replace`'s signatures widen** → the new parameter is optional and trailing; every existing call site and test is unaffected.
- **A project's repo is public and this surfaces knowledge a human did not expect to be public** → explicitly deferred to the named follow-up (the public-repo warning); this ticket's only mitigation is the pre-existing (and, after this ticket, note-covering) secret-shaped-content refusal, which is not a privacy control.
- **Reconciliation adds work inside `mergeDone`'s critical section** → bounded by both knowledge budgets (small files) and Decision 6's diff scoping (a landing that touched no knowledge file does one cheap `git diff --name-status` and nothing more); accepted per Decision 6.

## Migration Plan

Purely additive: the new migration adds a column defaulting every existing project to `knowledge_repo_enabled = 0`, and the new config field defaults to `false`. No existing project's behavior changes until a human explicitly opts it in through Settings. Rollback is a plain revert — the workspace's own knowledge store, which every feature reads, was never made to depend on the repo mirror existing.
