## Context

See `proposal.md` — Why. The authoritative design is the project knowledge documents `builtin-agent-runtime-details` (tools and permissions, section 5/6), `builtin-agent-design` (isolation, loop) and `builtin-agent-slices` (S2); this document records only what S2 decides where those leave a choice or where the code as merged in S1 differs.

S1 (merge `1fb042cf`) already provides: the `ToolDefinition` registry (`packages/agent/src/tools/index.ts`), `read` and `bash`, the loop's tool dispatch with `tool.call`/`tool.result`, a `restricted` mode that exposes only `read`, and a case-insensitive `allowedTools`/`deniedTools` filter with no aliases. The `weave` adapter's `EVENT_TYPES` already carries `file.changed`, `command.executed` and `tool.denied`, so this slice adds emitters and a forwarding test rather than new event types. `run.cwd` is the agent home; `run.worktree.path` is the worktree; `run.configHome` is `<workspace state>/runtimes/weave` and is **not** on the `init` line yet.

## Goals / Non-Goals

**Goals:** a worker turn can create, edit and search files with the same output shapes and safety rules the design specifies; nothing in the workspace's own state is writable through a file tool; the three modes are enforced before a tool runs, with `restricted` hiding the write-capable tools from the request body; the run page already shows the work without a renderer change.

**Non-Goals:** an OS sandbox (`bwrap`), an approval round-trip, `todo_write`/`skill`/`task`/`web_fetch`/images (later slices), any change to `read`'s or `bash`'s existing caps, and any change to another runtime.

## Decisions

1. **Confinement roots and protected paths are computed in the child, with the state directory derived from `run.configHome`.** Allowed roots are the worktree and the agent home. The protected set is: `<worktree>/.git/hooks` and `<worktree>/.git/config`; the home's discovery files `<home>/AGENTS.md`, `<home>/CLAUDE.md`, `<home>/.claude`, `<home>/.agents`, `<home>/.opencode`; and the **workspace state directory** `dirname(dirname(configHome))` with everything under it, which is where `secrets.enc`, `secrets.key`, the daemon SQLite files, `runtimes/` and other agents' homes live. `path` is resolved against the worktree, `realpath`'d, and only then tested, so a symlink is judged by its target. The child therefore needs `configHome` on the init line: this is an additive field on the existing `v:1` `run` object, not a protocol bump, because the child and the daemon ship in one release ([[release-and-upgrade]]).
   - *Known gap, stated rather than hidden:* the daemon's own config directory (`daemon.yaml`, `workspaces.yaml`, the daemon database, `credentials/`) is not an ancestor of any path the child receives, so it cannot be derived in the child. It is a follow-up when `RuntimeHost` gains a paths accessor (S3 already widens `RuntimeHost`); until then it is reachable only through `bash`, exactly as it is through the three CLIs' `auto`/`bypass` postures. The comment in `confine.ts` names the gap.
   - Reads outside the roots are limited to `/usr`, `/etc/os-release`-class system paths and the run's spill directory, only in `auto`/`bypass`.
2. **The read ledger is per turn and in memory.** The child is spawned per turn, so a resumed turn starts with an empty ledger and the model must re-read before an edit. Persisting the ledger in the session would add a format concern for a safety check whose failure mode (an extra `read`) is cheap. Entries key on the `realpath`'d path and hold `mtimeMs`, `size` and a SHA-1 of the bytes; a `write` to an existing file and every `edit` compare stat-plus-hash first, and a successful write refreshes the entry.
3. **The edit chain stops at the first stage with any match, and ambiguity is terminal.** Stages in order: exact, line-trimmed, whitespace-normalised, indentation-flexible, smart-quote-normalised. A stage that finds exactly one match is applied; a stage that finds more than one without `replace_all` is an error naming the count (the search does not continue into a fuzzier stage that might accidentally find one). With `replace_all`, the first stage that finds at least one match replaces all of them. `old_string == new_string` is an error before matching. The written bytes re-apply the detected CRLF endings and byte-order mark, and the replacement is atomic (temp file in the same directory, flush, rename, mode preserved, temp unlinked on failure) shared with `write`.
4. **`grep`/`glob` prefer `rg` and fall back to a built-in walker.** `rg` is probed once at the start of the turn (`spawnSync('rg', ['--version'])`); the chosen implementation is logged once as a child `log` line. The `rg` invocation respects ignore files and excludes `.git`; the fallback is a synchronous walk with a small `.gitignore` matcher and JavaScript `RegExp`, which is slower and is the reason `rg` wins when present. Both must produce the same rows for the same query (a parity test runs the query twice, once with `PATH` stripped).
5. **Permission is decided in one place, in the loop, before a tool runs.** `permission.ts` exposes the mode → tool-set table and a `check(name, args, mode, config)` that returns either `allowed` or a refusal reason. The loop keeps two maps: every tool that exists (`read`, `write`, `edit`, `bash`, `grep`, `glob`, MCP) and the active set after mode and allow/deny filtering. A call to a name in the full map but not the active set produces the `Denied by permission mode "<mode>"` result and emits `tool.denied`; a name in neither is the existing unknown-tool error. Checking before execution is what keeps `tool.denied` from being followed by a `tool.result` that would open a second transcript row.
   - *Alternative rejected:* letting each tool refuse itself. It would put mode logic in six tools and make the denial path untestable in one table.
6. **Bash deny patterns live in `permission.ts` as named regexes over the raw command text.** They are a best-effort guard against the accidents recorded in the shared conventions (a worker's broad `pkill` killed the live daemon), not a containment boundary; the refusal names the rule. A role's configured list is appended. `bypass` does not apply them, matching the CLIs' posture; the file-tool protected list still does.
7. **Tools emit their own events through `ToolCtx`.** `ToolCtx` gains `emit(type, payload)`, `ledger` and the resolved roots; `write`/`edit` call `emit('file.changed', …)`, `bash` calls `emit('command.executed', …)` between the loop's `tool.call` and `tool.result`. This replaces S1's loop-side `command.executed` special case so every tool owns its own payload. `file.changed` needs no adapter change (already in `EVENT_TYPES`); a test pins the translation.
8. **The render golden is written from a real capture, not from a guess.** During apply a mock-provider loop test records the child's NDJSON for an `edit` turn and a `bash` turn; the render test's payloads are copied from those bytes (the VS-186/VS-214 rule). If the renderer needs a change to render the payload, the change is in `packages/render`, not in the agent's output shape.
9. **The screenshot is produced with the existing static-render harness** ([[ui-screenshot-harness]]) from the run page's transcript route with mocked fetch, in dark and light at desktop and phone widths, saved outside the worktree and attached to the ticket.

## Risks / Trade-offs

- **`bash` remains unconfined at the OS level** (as for pi and the three CLIs). The deny patterns and the file-tool protected list are hygiene, not a boundary; the design says so and S9's `bwrap` option is the real fix. → Stated in the result comment; no over-claim in the PR.
- **The daemon config directory is not protected** because the child cannot derive it (Decision 1). → Recorded as a named gap with its follow-up; not presented as covered.
- **The per-turn ledger forces a re-read after a resumed turn.** → Accepted; the stale-check correctness is worth more than the token saving, and the refusal text tells the model exactly what to do.
- **A fuzzy edit stage can match the wrong text** if a stage's normalisation is too loose. → A stage is only applied on exactly one match, ambiguity is terminal, and stale detection catches an edit that changed a file the model had not re-read. The stage fixtures are written from real files in the repo.
- **`rg`'s output is parsed, so a version change could alter rows.** → The parity test compares against the built-in walker, which cannot drift with a binary; a mismatch fails the test.
- **Size: medium, one turn.** Tasks are ordered so each compiles and commits (confinement and ledger first, tools next, permissions, then events and the golden) so a 45-minute cut-off leaves landed work.

## Migration Plan

Additive only: new modules, a new tool set on the `weave` runtime, and one optional `configHome` field on the child's init line. Older child processes are never spoken to (the child ships in the daemon's own release), so no version negotiation is needed. Rollback is removing the new tools from the `weave` runtime's registry; no persistent state changes.
