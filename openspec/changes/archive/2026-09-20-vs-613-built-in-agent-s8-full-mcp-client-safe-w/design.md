## Context

The authoritative design is the project knowledge documents `builtin-agent-runtime-details` (section 8 MCP, section 5 images and web policy) and `builtin-agent-slices` (S8); this document records only what S8 decides where those leave a choice or differ from the code S1–S3 merged.

What already exists on this branch (read 2026-09-20):

- `packages/agent/src/mcp/http.ts` — `McpHttpClient` with `initialize`/`listTools`/`callTool` and a hard-coded `MCP_RESULT_MAX_CHARS` cap. No interface, no `close()`.
- `packages/agent/src/loop.ts` — constructs one `McpHttpClient` per `init.mcpServers` entry, names non-Weave tools `mcp__${server}__${tool}` with a naive `.replace(...).slice(0, 64)` (collisions silently overwrite in the `all` map) and special-cases the server literally named `weave-ai`. It has no client abstraction to hang a second transport on.
- `packages/agent/src/protocol.ts` — `InitMessage.mcpServers` is `Record<string, { url; headers? }>`; `packages/runtimes/weave/src/child.ts` drops anything whose `type !== 'http'`. `McpServerConfig` in `runtime-sdk` already carries `type: 'http' | 'stdio'`, `command`, `args`, `env`, so only the child mapping is missing.
- `packages/agent/src/types.ts` — `ContentBlock` has no image form; `Message.user` is `{ text }`. `codec/params.ts` `toWireMessages` emits string content for user and tool messages only.
- `packages/shared/src/config.ts` — `ProviderCompatSchema` has no `image.input`.
- `packages/agent/src/tools/read.ts` — refuses any file with a NUL in its first 8 KB as `Error: binary file`, before any image check.

## Goals / Non-Goals

**Goals:** a stdio MCP server is usable exactly like the HTTP one; every non-Weave MCP tool has a stable, collision-free name within 64 characters while `weave_*` names are untouched; a tool result over 50 KB is capped with a marker the model can act on; `web_fetch` reaches public http(s) and refuses loopback/private/link-local/metadata targets directly, through redirects and against a resolver that answers differently on the second lookup; `read` of a png/jpg/gif/webp returns an image the model receives under the profile's `image.input` mode.

**Non-Goals:** sourcing non-Weave MCP servers from workspace or role config (no such config exists today — the engine builds only the `weave-ai` HTTP entry; this slice proves the client with fakes and leaves the config surface to later work); MCP OAuth, elicitation, tool-search deferral, `tools/list_changed`; web search; an OS sandbox; user-attached or pasted images; a second fetch tool (`http_request`); markdown typography beyond a small html→text reduction.

## Decisions

1. **One `McpClient` interface, two transports.** `mcp/http.ts` and the new `mcp/stdio.ts` both implement `{ initialize(signal); listTools(signal): Promise<McpTool[]>; callTool(name, args, signal): Promise<{ text; isError; images? }>; close(): Promise<void> | void }`. A factory `createMcpClient(cfg, deps)` picks by `cfg.type` (defaulting to `http` when a `url` is present, for the old shape). The loop keeps a `clients: McpClient[]` and closes every one in a `finally`, so a stdio child process never leaks on a cancelled or crashed turn. `McpHttpClient.close()` is a no-op (aborting the turn's signal already ends its request); `McpStdioClient.close()` kills its child.
   - *Alternative rejected:* teaching the loop both protocols inline. The loop already owns naming, permission and event emission; a second protocol there would be untestable in isolation and would duplicate the cap and timeout logic.
2. **The stdio transport is newline-delimited JSON-RPC over the spawned child's stdio.** `spawn(command, args, { env, stdio: ['pipe','pipe','pipe'], windowsHide: true })`. One JSON object per `\n` on stdout; anything on stderr becomes a child `log` line. `initialize` and `tools/list` use the list timeout (30 s), `tools/call` the call timeout (60 s); a per-request `AbortSignal.any([turnSignal, AbortSignal.timeout(ms)])` and a `notifications/cancelled` on abort, matching the HTTP client. The client's `close()` sends SIGTERM and, after a short grace, SIGKILL. The spawned server is **not** detached and is killed by pid, never by pattern — the shared conventions forbid pattern kills, and this child is our own process, not a system service.
   - *Alternative rejected:* a single long-lived stdio server shared across turns. Each turn is a fresh child of the agent, so a per-turn server is the only lifecycle that needs no supervision.
3. **Naming is computed once, from a `taken` set seeded with the Weave tools.** `mcp/naming.ts` exposes `sanitizeSegment(s): string` and `assignMcpToolNames(servers, taken): Map<wireName, {server, tool}>`. The Weave server (`weave-ai`, `MCP_SERVER_NAME`) is passed its tool names through unchanged and those names are inserted into `taken` first. Every other tool becomes `mcp__<san(server)>__<san(tool)>`, truncated to 64 characters, and a collision (with a Weave name or another server's) gets `_2`, `_3`, … appended within the 64-character budget. Sanitisation replaces every character outside `[A-Za-z0-9_-]` with `_`; an empty segment becomes `server`/`tool`. The mapping is returned so the loop can send the original `(server, tool)` to `callTool` while the model sees the wire name.
   - *Why a `taken` set rather than a per-server suffix:* the acceptance is "collisions handled", and the only way to guarantee that is one namespace across all servers.
4. **The 50 KB cap and text concatenation live in one shared helper.** `mcp/result.ts` exports `capMcpResult(text)` (keep the existing marker `[truncated at <n> characters]`) and `McpToolResult`. Both transports call it. The cap is applied to the concatenated text, not per part.
5. **MCP image content parts become `ContentBlock` images.** A `tools/call` result may carry `{ type: 'image', data, mimeType }`; `callTool` returns those as image parts alongside the text, and the loop lifts them exactly like a `read` image (Decision 7). A non-text, non-image part is noted as `[<type> content omitted]`, as the HTTP client already does.
6. **`web_fetch` connects to the address it resolved.** `net/ssrf.ts` splits the policy (pure) from the transfer (injectable):
   - `isBlockedAddress(ip, family)`: IPv4 loopback `127/8`, private `10/8`, `172.16/12`, `192.168/16`, link-local `169.254/16`, CGNAT `100.64/10`, `0.0.0.0/8`, broadcast, and the metadata pairs carried by link-local; IPv6 `::1`, `fc00::/7` unique-local, `fe80::/10` link-local, unspecified `::`, and IPv4-mapped addresses judged by their embedded IPv4. This is a pure table, unit-tested by address.
   - `resolveHost(host, resolve)`: `resolve` defaults to `dns.promises.lookup(host, { all: true })`; the host is refused when any returned address is blocked (refuse on the whole answer, not only the address chosen, so a multi-answer rebind fails closed) or when nothing resolves.
   - `fetchWithPolicy(url, { resolve, request, signal })`: parses the URL, allows only `http:`/`https:`, resolves and checks the current host, then issues the request **with the resolved address pinned** — `node:http`/`node:https` `request(..., { lookup: (_h, _o, cb) => cb(null, address, family), servername: host, headers: { host } })` — reads at most `maxBytes` (5 MB default), and follows at most 5 redirects, re-parsing each `Location`, re-resolving and re-checking every hop. No second DNS lookup happens for a connection, so a rebinding resolver that answers public first and private second cannot redirect the socket. `request` is injectable so tests exercise the happy path, redirects and rebinding without a public network.
   - Result: a status line, then the body reduced to text — `text/html` through a small tag-stripper and entity decoder, other textual types verbatim, a binary type refused — capped at 50 KB. A refusal is an ordinary `Error:` result naming the reason (`loopback address`, `private address`, `link-local address`, `metadata address`, `redirect limit`, `unsupported scheme`), never a thrown exception.
   - *Alternative rejected:* `fetch` plus a preflight DNS check. `fetch` re-resolves internally, so the check and the connection can disagree — the exact DNS-rebinding hole the acceptance names.
7. **`web_fetch` is opt-in and denied in `restricted`.** It joins `read`, `write`, `edit`, `bash`, `grep`, `glob` in the core-name registry so `modeToolNames` and `modeAllows` treat it like the write-capable tools: `restricted` never offers it and a forced call gets the standard `Denied by permission mode "restricted"`. In `auto`/`bypass` it is added to the active set only when `run.options.webFetch === true`; a call while it is disabled (or before the option is set) returns `Error: web_fetch is disabled; enable it with the webFetch option`. `webFetch` is added to the adapter's `configSchema` so the Settings UI can set it; unknown option keys do not error in this runtime, so the flow is `role/worker option` → `input.options` → `run.options`, unchanged.
8. **Images are one new content block and one new compat flag.** `ContentBlock` gains `{ type: 'image'; mediaType: string; dataBase64: string }`; `Message.user` and `Message.toolResult` gain an optional `images?: ImagePart[]`. `ProviderCompatSchema` gains `image: { input: z.enum(['none','user','user_and_tool']).optional() }`, `Compat`/`DEFAULT_COMPAT` gain `image: { input: 'user' }`. `toWireMessages` emits `{ type: 'image_url', image_url: { url: 'data:<media>;base64,<data>' } }` parts (user content as an array when images are present, tool content as an array only in `user_and_tool`).
   - `read` detects a supported image by magic bytes (`\x89PNG`, `\xFF\xD8\xFF`, `GIF8`, `RIFF….WEBP`) **before** the NUL-based binary check, up to 5 MB, and returns text `Read image <path> (<type>, N bytes)` plus the image part. In `image.input:none` it returns `Error: this model cannot read images` and no part. Otherwise the loop appends the tool result and, for `user`, a following synthetic user message carrying the image; for `user_and_tool` the image rides in the tool message itself. A larger or unsupported file keeps the existing binary/too-large refusals.
   - *Why `user` is the default:* OpenAI tool messages do not accept image parts universally; a following user message does on every probed endpoint, and the design names `user_and_tool` as the exception a profile opts into.
9. **The child init line stays `v:1`.** `mcpServers` entries gain optional `type`, `command`, `args`, `env`; the child ships in the same release as the daemon, so there is no stale-child negotiation ([[release-and-upgrade]]). `child.ts` maps a `McpServerConfig` to the child shape for both transports and drops an entry that has neither a `url` (http) nor a `command` (stdio) with a `log`.

## Risks / Trade-offs

- **The stdio server is a child process of the agent child.** A hung server is bounded by the per-call timeout and by `close()` on turn end; a server that ignores SIGTERM is SIGKILLed after the grace. A turn killed by the daemon takes the stdio server with it because the agent child is its parent and process-group leader. → A test spawns a fake server that ignores SIGTERM and asserts it is reaped.
- **HTML reduction is approximate.** A tag-stripper is not a browser; some pages read poorly. → Accepted for v1; the tool returns the bytes it reduced and the model can tell. No third-party parser dependency is added.
- **`isBlockedAddress` can miss a range we did not enumerate.** → The table is the acceptance surface and is unit-tested address by address; the design's list (loopback, private, link-local, metadata) is covered, with CGNAT/unique-local as the obvious neighbours. A miss is a security bug and the test table is where a fix lands, not a guess.
- **The three `image.input` modes need a fixture per mode** and no real provider is contacted from the ticket (the AGENTS.md rule). → Tests use the mock provider and assert the **recorded request body** (image part present in the user message vs the tool message vs absent), which is what the acceptance asks for.
- **Size: medium-to-large, likely two turns.** The task list is ordered so each task compiles and commits (client interface and stdio first, then naming/cap, then SSRF, then `web_fetch`, then images, then docs). **Split point if the first turn runs short:** after MCP completeness (tasks 1–3); images and `web_fetch` continue in a second turn via `in_progress`.

## Migration Plan

Additive only: new modules, a new optional tool, two additive fields on the child init line and one on the provider compat schema. Old child processes are never spoken to (the child ships in the daemon's release). Rollback is removing `web_fetch` from the registry and the stdio branch from the factory; no persistent state changes.
