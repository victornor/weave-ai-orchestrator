## Context

See `proposal.md` — Why. The authoritative design is the project knowledge documents `builtin-agent-runtime-details` (section 8 MCP, section 6 permission model) and `builtin-agent-slices`; this document records only what this change decides where those leave a choice or differ from the code S1–S8 merged.

What exists on this branch (read 2026-09-20):

- `packages/core/src/runs/engine.ts` builds `mcpServers` as exactly `{ ['weave-ai']: http(url, Authorization: Bearer <run token>) }` (line ~467), writes it to `<runDir>/mcp.json`, and passes it to the adapter through `TurnInput.mcpServers`. Role secrets are resolved by `roleSecretsEnv` and their values are added to `redactionSecrets` for `makeRedactor`.
- `packages/runtime-sdk/src/index.ts` `McpServerConfig` already carries `type | url | command | args | headers | env`.
- `packages/runtimes/weave/src/child.ts` maps `TurnInput.mcpServers` to `InitMessage.mcpServers`; `packages/agent/src/mcp/{client,http,stdio}.ts` implement the transports with hard-coded 30 s / 60 s timeouts; `packages/agent/src/loop.ts` builds one client per entry, names non-Weave tools `mcp__<server>__<tool>`, and seeds the Weave server's unprefixed names.
- `packages/server/src/routes/providers.ts` is the pattern for a workspace admin route with secret state and no secret value; `packages/ui/src/v2/settings/sections/Providers.tsx` is the pattern for the Settings section and masked secret input; `ProjectConfigSchema`, `RoleSpecSchema` are the config shapes.

## Goals / Non-Goals

**Goals:** a human defines MCP servers once in the workspace, references their secrets, allows them per role, and gets only those servers in a built-in-agent run; a Settings section can add/edit/remove/test a server and a role can allow them; no secret value is ever stored in config or emitted.

**Non-Goals:** mirroring workspace servers into the CLI runtimes' own MCP configs; MCP OAuth, elicitation, `tools/list_changed` and tool-search deferral (still later); per-server tool allow/deny lists beyond the role's server list; a `weave_*` MCP tool for managing servers (the human's Settings path only); any change to how the CLI runtimes resolve their MCP servers.

## Decisions

1. **Definitions live under a top-level `mcpServers` map on the workspace config, keyed by server name.** Shape: `{ type, url?, headers?, command?, args?, env?, listTimeoutMs?, callTimeoutMs?, readOnly? }`, defaulting `args`/`env`/`headers` to empty, `listTimeoutMs` 30000, `callTimeoutMs` 60000, `readOnly` false. A Zod `.superRefine` requires `command` for `stdio` and `url` for `http`, and the map key is validated as `[a-z0-9][a-z0-9_-]*` and forbidden the value `weave-ai`.
   - *Alternative rejected:* nesting under `weaver` or a new `mcp:` object. The run's own field is already called `mcpServers`, the plan's §9 config expects providers-style records, and a top-level name reads as what it is.
2. **Secrets are referenced with `${NAME}` in any `env` or `headers` value.** A reference is resolved from the workspace secret store by `deps().secrets.value(name)` at the moment the run's servers are built; the resolved value is added to `redactionSecrets`, exactly as a role secret is. A value may be a plain literal (e.g. `NODE_ENV: production`) and is then used as is; only `${NAME}` is store-resolved. A server with a reference that resolves to nothing is **omitted** from the run with a log line, so a misconfigured server never starts half-authenticated.
   - *Alternative rejected:* making every `env` value a bare secret name (disallows literal non-secret env); a separate `secrets:` sub-map (two ways to say one thing); accepting the value inline (violates the no-secret-in-config rule the ticket states, and the config would leak it on backup or copy).
   - *Naming:* the ticket's `MCP_<SERVER>_<NAME>` convention is the suggested default the UI prefills, not a constraint the schema enforces — a user's own name is accepted so an existing secret can be reused.
3. **`mcp.json` is a redacted debug view, not the child's input.** The engine builds the resolved server map for `TurnInput` (values substituted) and writes `mcp.json` from a redacted copy: references stay `${NAME}`, the Weave entry's `Authorization` header value becomes `[redacted]`. The only copy of a resolved value is the child's `init` line on stdin, which is never written to disk. A test asserts no stored secret value appears in `mcp.json`, in any persisted event, or in a log line.
   - *Why now:* the file today already carries the run token; adding user secrets without redaction would put them on disk in plaintext. Redacting both is a small, safe tightening.
4. **Timeouts travel as optional `McpServerConfig` fields.** `listTimeoutMs`/`callTimeoutMs` are added to `McpServerConfig` (runtime-sdk), `InitMessage.mcpServers` (protocol — additive to `v:1`, the child ships in the daemon's own release), `McpClientConfig`, and passed to the HTTP and stdio clients in place of their hard-coded defaults. No negotiation, no version bump: S8 already established that the child is released with the daemon.
5. **Selection is one allow list per role plus one for the weaver.** `RoleSpecSchema.mcpServers: z.array(z.string()).default([])` and `WorkspaceConfigSchema.weaver.mcpServers: z.array(z.string()).default([])`. The engine resolves `agent.kind === 'weaver' ? config.weaver.mcpServers : role?.mcpServers ?? []`, dedupes, drops names with no definition (with a log), and always keeps `weave-ai`. A persistent session is an agent with a `roleId`, so its role list covers it; a planner likewise gets only what its role names. The allow list is consulted only for `setting.runtime === 'weave'`, so a CLI runtime is untouched.
   - *Alternative rejected:* a workspace-wide "all servers to all agents" switch. It is the opposite of least privilege, and the ticket asks for a role list defaulting to none.
6. **`restricted` keeps only explicitly read-only user servers.** In `restricted`, the loop drops every user `mcp__…` tool unless its server's definition sets `readOnly: true` and the server was allowed by the role (which the engine already enforced when building the map). The run-scoped Weave server's `weave_*` tools stay, since they are gated server-side by the run token and by the first-turn allowlist. This narrows the spec's existing "`restricted` exposes … the MCP tools" for user servers only.
   - *Why a config flag rather than trusting the MCP `readOnlyHint` annotation:* the annotation comes from the server itself and is advisory; a wrong or absent hint would silently widen a restricted run. `readOnly` is a human declaration; the Settings copy says so plainly and warns that it is a declaration, not enforcement.
   - *Alternative rejected:* dropping all user MCP tools in `restricted` unconditionally — the ticket allows read-only servers explicitly, and a read-only docs server is the common case.
7. **The workspace definitions feed the `weave` runtime only.** `MCP_SERVER_NAME` and the user map are merged only into the `weave` run's `mcpServers`; the engine does not translate them into `--mcp-config` files, `.opencode`, `config.toml`, `.gemini/settings.json` or `.cursor/mcp.json`. The CLI runtimes already support their own MCP config and their own credential handling; duplicating the workspace store into each would mean five copies of every credential and five behaviors to keep in step. Stated again in the Settings section copy.
8. **New `/mcp` route group, modeled on `/providers`.** `GET /mcp` returns the definitions with secret-set booleans (never a value) and the set of referenced names; `PUT /mcp/:name` upserts a definition (validated against `McpServerSchema` plus `WorkspaceConfigSchema`); `DELETE /mcp/:name` removes it; `POST /mcp/:name/test` connects and lists tools with a 15 s timeout; `POST /mcp/secrets/:name` / `DELETE /mcp/secrets/:name` set/clear a referenced secret through `SecretsService` (the same masked-input path the provider key uses). Secrets are set by name, not by server, because a name may be shared by several servers and predate them.
   - *Alternative rejected:* a generic `/secrets` route. Scoping the write to the MCP settings keeps the surface the human actually drives; a general secret editor is a wider change with its own scope.
9. **UI: a new `McpServers` section and a role control.** Register `{ key: 'mcp', label: 'MCP servers', scope: 'workspace' }` in `V2_WORKSPACE_SECTIONS` after `providers`, render `McpServers.tsx` from `V2Settings.tsx` following `Providers.tsx` (expandable rows, masked `SecretRow`, `Test` button), and add a multi-select of server names to `RolesPage`'s role detail saved through `PATCH /roles/:id { patch: { mcpServers } }`. UI acceptance captures both themes at desktop and phone width and attaches them to the ticket.

## Risks / Trade-offs

- **A stdio server is arbitrary code the human chose to run on the host**, with the daemon's uid; the minimal environment is hygiene, not a sandbox. → The Settings section says so in the same way the Providers section names the data-flow risk; no OS sandbox ships in v1, consistent with the CLIs' `auto`/`bypass` and with `builtin-agent-design`'s decision 3.9.
- **A `${NAME}` literal typed as a secret in config is indistinguishable from a non-secret literal.** → The rule is documented and the UI only writes references; the redactor still scrubs any resolved value, and a stored secret never enters the config through our own routes.
- **The redactor ignores values shorter than 8 characters** (`makeRedactor`), so a very short secret could survive in an event. → Same existing limitation as role secrets; the Settings copy states secrets should be real credentials, and the test uses a realistic-length fixture.
- **A server whose `tools/list` is slow delays the turn.** → Bounded by `listTimeoutMs` (default 30 s) and, for the Weave server, unchanged `mcp_unavailable` semantics; a user server that times out is skipped with a log like any other failed server.
- **Size: large, likely two turns.** Task groups are ordered so each commits and compiles: config + engine resolution + tests first; then adapter/child timeouts and the `restricted` filter; then the server routes; then the UI; then docs and the full suite. **Split point if the first turn runs short:** after task group 4 (engine and child wiring) — routes and UI continue on the same branch via `in_progress`.

## Migration Plan

Additive only: a new config map with defaults, two optional allow lists defaulting to empty, optional fields on `McpServerConfig`/`InitMessage`, a new route group and a new UI section. An existing workspace validates unchanged and behaves exactly as before (no server allowed → only `weave-ai`). Rollback removes the route group, the UI section and the `restricted` filter; no persistent state changes, no migration.

## Open Questions

None blocking. Two assumptions stated rather than asked, both inside the ticket's "decide and state in the plan":
- the weaver's allow list lives at `weaver.mcpServers` because the weaver agent has `roleId: null`;
- `readOnly` is a per-server config flag the human sets, not the MCP `readOnlyHint` annotation.
