## Context

Worker options are already daemon-level: `daemon.yaml` `models.workerOptions` overlays every workspace (VS-185) and an option is `{runtime, model, options}`; for `weave` the model is `<providerId>/<modelId>`. `runtime-options.ts` does not validate the provider id. So a `weave` option already exists in every workspace; what fails is resolving its provider, because `createRuntimeHost` and the engine read `ctx.config.providers` of the run's workspace only. No option-catalog change is needed: only provider/MCP resolution moves. (To be re-verified in task 1.)

## Decisions

1. **Merge = whole-entry replace by id, computed by one pure function** `mergeScoped(daemon, workspace, disabled) -> { entries, source }` in `packages/core`, used by the runtime host, engine, routes and repl. Reason: predictable and testable; deep merge would make an override that drops a field impossible to express. `source` is `daemon | workspace | override`.
2. **Disable via two string lists** on the workspace (`disabledProviders`, `disabledMcpServers`), not `enabled:false` on an entry (a disabled entry would still need a valid `baseUrl`/`type`) and not null entries (changes the record's type at every call site). Additive fields, so older daemons ignore them on rollback.
3. **Daemon secrets: a second file pair `daemon-secrets.enc/.key` in the daemon config dir**, built with `createSecretStore`, the same AES-256-GCM 0600 shape as `push-vapid.enc`. Not the VAPID store: that one holds a signing key we never want reachable from an admin route. Resolution `workspace store -> daemon store`, in one `resolveSecret(name)` used by the adapter's `providerKey`, `buildMcpServers`, and redaction. The daemon secret is entered in Settings (daemon scope) with the existing write-only secret input; routes return `configured: bool` only. Redaction: the engine already registers resolved provider/MCP values; it now takes them from the merged resolver, so daemon values are covered by the same path.
4. **Runtime host**: `createRuntimeHost(workspaces, configDir, daemonConfig)`; `providers(workspaceId)` returns the merged set, `providerKey` uses the merged owner: an override uses workspace-then-daemon store for its own `apiKeySecret`. The no-workspace aggregate (runtime catalogue) returns daemon providers first, then the first workspace's additions.
5. **Config plumbing**: `ctx.daemon` is the one live daemon-config object (the daemon routes mutate it in place, as the model overlays do), so `effectiveProviders(ctx)` / `effectiveMcpServers(ctx)` in core compute the merge on demand from `ctx.daemon` and `ctx.config`; a Settings edit applies to the next run with no restart and nothing is cached.
6. **Missing allowed MCP server fails the run** (engine, before spawn) with role and server named. A server whose `${SECRET}` has no value keeps today's behaviour (omitted, warned); only "unknown at both levels" is fatal, as the ticket requires.
7. **API**: `/api/daemon/providers[/:id[/secret|/test]]`, `/api/daemon/mcp-servers[...]` mirror the workspace handlers by extracting the handler bodies into a scope-parameterised factory (workspace scope = config + workspace store; daemon scope = `daemon.yaml` via `writeDaemonConfig` + daemon store). Workspace GET responses only gain `source` and `disabled`; the PUT/DELETE shapes are unchanged. Workspace secret/test routes for an inherited entry are refused with a message pointing at the daemon scope (or "Override").
8. **UI**: Providers and MCP sections take a `scope` prop and are registered in both scopes; the workspace variant renders the merged list with a "from daemon" badge, Override (copies the daemon entry into the workspace, then edit) and Remove override. Connection test works from both scopes.
9. **repl**: `loadReplConfig` reads `<configHome>/daemon.yaml` as the lowest source, below `agent.yaml`. The existing order of the other layers is unchanged (a workspace entry replaces an `agent.yaml` one, as before), so the terminal agent's precedence is daemon < `agent.yaml` < workspace < flags. Key and `${NAME}` resolution gain the daemon secret store after the workspace one. Literal `apiKey` allowed only in `agent.yaml`, unchanged.
10. **Upgrade safety**: no migration, no field removed or moved; workspace-level entries load as before. Not a new migration number.

## Risks

- Runtime catalogue calls with no workspace id: covered by decision 4.
- Concurrent writes to `daemon.yaml`: reuse `writeDaemonConfig`, as the models route does.
- Secret-name collision between scopes is intended (workspace wins) and shown in the UI as "overridden by workspace".
