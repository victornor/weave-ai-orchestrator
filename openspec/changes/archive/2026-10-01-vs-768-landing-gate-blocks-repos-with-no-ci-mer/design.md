## Context

`attemptArchiveThenMerge` decides, for an absent rollup (`ciState === 'none'`) with `requiresCi` (the default), between "wait", "merge as a no-CI repository" and, since VS-466/467, "wait for a run and retrigger it". Its only inputs for that are `forge.hasCiWorkflows` (`true | false | null`) and per-process maps keyed by pull request or clone. Cause analysis and file:line evidence are in `proposal.md`; the live repository cannot be read from this project, so which of the two leading causes (cached failed query, dynamic workflows) hit VAPIAuto is not proven. The change fixes both and every path that makes the wait unreliable, and each is covered by its own test.

## Decisions

1. **Classification counts workflow files, not workflow records.** The jq filter becomes `[.workflows[] | select(.state == "active" and (.path | startswith(".github/workflows/")))] | length` on `actions/workflows?per_page=100`. Real output for this repository (captured with `gh api`) is `{"path":".github/workflows/ci.yml","state":"active"}`; the `.github/workflows/` prefix is therefore safe for file workflows. That dynamic workflows use a path outside that prefix is from GitHub's documented behaviour, not captured here — the fixture for it is hand-written and the PR says so. A repository whose every workflow file is disabled has no run that can ever appear, so it is correctly "no CI". `workflowCountFromGh` keeps parsing a bare integer.
2. **A failed query is retried, never cached.** `repoHasCiWorkflows` caches only definite `true`/`false` (still 5 minutes), asks up to three times with a short delay (`classifyRetryDelayMs`, default 2000 ms, a test passes 0), and returns `null` only if all fail.
3. **The unclassified wait is anchored per (pull request, head).** `noneSinceByPr` becomes `noneSinceByHead` keyed by `${prUrl}@${expectedHead}`. The entry is set on the first attempt that cannot classify and waits (same `changed || changedDraft || has` condition as now), and is deleted only when the sequence merges, finds a classification, or sees a rollup appear — not on a head mismatch or a `pending` read. A different head (a rebase push) starts a fresh wait, which is right: that head has not been observed. The `CI_NONE_GRACE_MS` constant is unchanged.
4. **Comment on the clean no-CI landing.** A new optional `onNoCiRepository` callback fires once when the sequence merges because `hasCiWorkflows === false` with an absent rollup under `requiresCi`. `service.ts` wires it to a system comment (`landed without CI: the repository has no GitHub Actions workflows`). The existing `onNoCiTimeout` wording stays. `requireCi: false` does not comment.
5. **Combined status is pinned, not changed.** A gh fixture of `statusCheckRollup: []` through `GhForge.prState` asserts `ciState: 'none'`, so the gate cannot start reading an empty pending combined status as pending without a test failing.
6. **VS-466 untouched.** The `hasWorkflows === true` branch, the head-match check and the trigger logic are not edited; a regression test with workflows and an all-skipped rollup, and one with a success on the head, run alongside.

## Risks

- Filtering to `.github/workflows/` could misclassify a repository whose only CI is a Dependabot/CodeQL dynamic workflow that does report check runs on PRs. Those run as checks on the rollup, so a non-empty rollup is read normally; only the empty-rollup case changes, and an empty rollup with no workflow file for a full grace-less landing is the case being fixed.
- A transient classification failure now costs up to ~4 s of retries per attempt.
